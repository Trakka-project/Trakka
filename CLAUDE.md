# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Trakka is an ultra-lightweight Go backend (target: <20MB RAM at runtime) for shopping lists and to-do lists, exposed as a JSON REST API and served alongside static PWA assets. It is designed to run identically under Docker and Podman rootless, and is held to explicit security rules (parameterized SQL only, strict URL scheme validation, hardened HTTP response headers) — see the "Security rules" section below before touching handlers or the frontend.

## Commands

```bash
go build -o trakka ./cmd/server    # compile
go vet ./...                       # static checks
gofmt -l .                         # list any non-gofmt-formatted files (should be empty)
go mod tidy                        # sync go.mod/go.sum after dependency changes

# Run locally (no container needed — pure Go, no CGO)
PORT=8080 DB_PATH=./trakka.db STATIC_DIR=./static TEMPLATES_DIR=./templates go run ./cmd/server
```

There is no test suite yet (`go test ./...` has nothing to run). If you add tests, standard `go test ./...` applies; there's no custom test runner or build tag scheme.

### Container workflow

```bash
docker compose up -d --build              # Trakka only
docker compose --profile calendar up -d   # Trakka + Radicale (CalDAV sync)
podman-compose up -d                      # same compose.yml works unchanged
```

## Architecture

The backend is split into a thin entry point plus several internal packages, deliberately separated so persistence, HTTP concerns, auth logic, and shared types don't bleed into each other:

```
cmd/server/main.go     entry point: config, wiring, graceful shutdown, -healthcheck probe
internal/config/       env-var config loading
internal/models/       House/List/Item/User/Session/HouseMember structs shared by db and handlers
internal/db/           all database/sql usage lives here — nowhere else imports it
internal/auth/         non-HTTP auth logic: bcrypt, session tokens, hand-rolled OIDC client
internal/handlers/     routing, request validation, JSON responses, session middleware, /auth/... handlers
internal/validate/     small reusable input validators (currently: URL scheme)
internal/scraper/      best-effort background price lookup for an item's URL (OpenGraph/JSON-LD/microdata)
internal/webpush/      hand-rolled Web Push: VAPID (RFC 8292) JWT signing, aes128gcm (RFC 8291) payload encryption, delivery
static/                PWA assets served at "/" (index.html, js/, locales/ (FR/EN dictionaries), sw.js, manifest.json, icons/)
templates/             login.html, rendered via html/template
```

`templates/login.html` (via `html/template`, `Content-Type: text/html`) is the one exception to "no server-side rendering" — it genuinely needs server-injected per-request data (whether OIDC is configured, login-vs-register mode, a canned error message), which nothing else in this app does. `internal/handlers.Routes()` still serves `static/` purely via `http.FileServer`; don't add further `html/template` rendering unless something else genuinely needs server-injected per-request data the same way.

- **`internal/handlers` never imports `database/sql`** — it only calls methods on `*db.DB` (e.g. `GetList`, `CreateItem`) and checks for the sentinel `db.ErrNotFound` to decide between a 404 and a 500. Keep that boundary: if a handler needs a new query, add a method to `internal/db`, don't reach around it.
- **Routing** uses the Go 1.22+ standard-library `http.ServeMux` method-pattern syntax (`mux.HandleFunc("GET /api/v1/lists", ...)`) in `internal/handlers/app.go` — there is no router dependency (no Gin, no chi). Unmatched methods on a registered path pattern get an automatic 405 from the stdlib mux; don't hand-roll that check in handlers.
- **Database**: `modernc.org/sqlite` (pure Go, no CGO) — this is load-bearing for the static-binary/no-CGO build in the Dockerfile. Do not swap in `mattn/go-sqlite3` or any CGO-based driver.
  - The DB connection pool is deliberately capped at `SetMaxOpenConns(1)` / `SetMaxIdleConns(1)` (see `Open()` in `internal/db/db.go`). SQLite only allows one writer at a time and modernc's driver gains nothing from pooling; this avoids `SQLITE_BUSY` errors under concurrent requests. Don't "fix" this by raising the pool size without understanding why it's there.
  - Schema lives in a versioned sequence of migration files, `internal/db/migrations/NNNN_description.sql` (which is why that directory must live inside the `internal/db` package, not at the repo root), embedded into the binary via `//go:embed migrations/*.sql` and applied by the engine in `internal/db/migrate.go`, tracked through SQLite's built-in `PRAGMA user_version` rather than a separate version table or a third-party tool like `go-migrate` (kept in-house per the "standard library wherever possible" convention below). Each migration runs inside its own transaction that also bumps `user_version` on success, so a crash mid-migration can never leave the schema and its recorded version disagreeing with each other; each is applied at most once per database, ever, so — unlike the old idempotent-`schema.sql` approach this replaced — a migration file needs no `IF NOT EXISTS`/existence guards of its own. A database that predates this system (tables already exist, but `user_version` is still `0`, SQLite's untouched default) is detected (`hasExistingSchema`) and adopted directly at the latest version without re-running any migration SQL, rather than replaying scripts that would fail outright on already-existing tables/columns. Before applying a pending migration to an already-versioned, non-empty database, `backupBeforeMigration` snapshots it via `VACUUM INTO` (a single ordinary SQL statement, no CGO backup API needed) to `<DB_PATH's directory>/backups/` — `/data/backups/` for the default `DB_PATH`. To evolve the schema, add a new `internal/db/migrations/NNNN_description.sql` file rather than editing an already-shipped one in place (existing deployed `/data/trakka.db` files have already recorded that migration as applied and will never run it again). One migration (widening the `lists.type` `CHECK` constraint, which needs `PRAGMA foreign_keys = OFF` set *outside* any transaction — something the engine's generic one-script-one-transaction wrapper can't express) is registered as Go code instead of a `.sql` file; see `internal/db/migrate_list_types.go`. See [docs/DATABASE.md](docs/DATABASE.md#evolving-the-schema) for the full design.
- **Go version pinning is intentional and fragile**: `go.mod` currently declares `go 1.27.0` and pins `modernc.org/sqlite v1.57.0` (its own `go.mod` requires `go 1.25.0`, comfortably under 1.27.0), matching the `golang:1.27.0-alpine` build stage in the `Dockerfile`. These three numbers (go.mod's `go` directive, the sqlite driver version, and the Dockerfile's builder image tag) must move together. Running `go mod tidy` carelessly (e.g. `go get -u`) will pull a newer `modernc.org/sqlite` that bumps the required Go version past what the Dockerfile's builder image provides, silently breaking the Docker build stage without touching the Dockerfile. If you upgrade the driver, bump the Dockerfile's builder image in the same change (pin an exact `golang:<version>-alpine` tag — Docker Hub publishes one per patch release — rather than a floating minor-only tag, so the build doesn't depend on when that tag last moved) and verify `go.mod`'s `go` directive still matches.
- **Config is env-var only**, loaded once in `internal/config.Load()`: `PORT` (default `8080`), `DB_PATH` (default `/data/trakka.db`), `STATIC_DIR` (default `/app/static`), `TEMPLATES_DIR` (default `/app/templates`), `BASE_URL` (required only if OIDC is configured), `OIDC_ISSUER`/`OIDC_CLIENT_ID`/`OIDC_CLIENT_SECRET` (all-or-nothing — `Config.Validate()`, called from `main.go` right after `Load()`, errors out at startup if only some are set), `SESSION_COOKIE_SECURE` (default `true`), `SESSION_TTL_HOURS` (default `720`), `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` (all-or-nothing, same pattern as OIDC — see the "Web Push notifications" bullet below), `NOTIF_RECURRING_TASK_LEAD_TIME` (default `24h`; accepts a plain Go duration or a whole number of days with a `d` suffix, e.g. `1d`), `NOTIF_RECURRING_SCAN_INTERVAL_MINUTES` (default `30`), `SCRAPE_INTERVAL` (default `12h`, same duration-parsing rules as `NOTIF_RECURRING_TASK_LEAD_TIME` — see the "Target-price background scan" bullet below), `DEFAULT_APP_LANGUAGE` (default `en`, validated against `internal/validate.SupportedLanguages` — falls back to `en` if unrecognized; see the "Header cleanup" bullet below for what this drives). No config file, no flags other than `-healthcheck` and `-generate-vapid-keys` (prints a fresh VAPID key pair and exits).
- **Healthcheck is in-process**: `trakka -healthcheck` (implemented in `cmd/server/main.go`) does an HTTP GET against its own `/healthz` and exits 0/1. This is what `Dockerfile`'s `HEALTHCHECK` and `compose.yml`'s `healthcheck.test` both call — it exists specifically so the runtime image doesn't need `curl`/`wget` installed. If you change the healthcheck behavior, update both call sites.
- **Graceful shutdown**: `cmd/server/main.go` selects on a signal channel and a server-error channel; on SIGINT/SIGTERM it calls `srv.Shutdown(ctx)` and only then returns from `main`, which runs the deferred `database.Close()`. Don't call `os.Exit()` on the shutdown path — it would skip that deferred close.
- **Logging** uses `log/slog` (structured JSON to stdout), not the plain `log` package. `internal/handlers.Recover` is a last-resort panic safety net, not a substitute for the explicit `if err != nil` handling used everywhere else — every predictable failure path already returns an error before it would reach that middleware.
- **API shape**: `/api/v1/houses` (groups lists; a list belongs to exactly one house via `house_id`; a house has one or more members via `house_members`), `/api/v1/houses/{id}/members` (roster + invite-by-email + remove), `/api/v1/lists` (filterable by `?house_id=`/`?type=`/`?shared_with_me=true`; a list `GET` by id embeds its `items`), `/api/v1/items` (filterable by `?list_id=`, with `PATCH` supporting partial updates like toggling `done` without resending the whole item), `/api/v1/custom-categories` (`GET`/`POST`/`PUT /{id}`/`DELETE /{id}`, no partial `PATCH`), and `/api/v1/custom-categories/{id}/share`/`/api/v1/lists/{id}/share` (granular sharing — see the dedicated bullet below). Full endpoint reference: [docs/API.md](docs/API.md).
- **Custom categories ("Spaces")**: a `CustomCategory` (`id`, `user_id`, `name`, `icon`, `color`, `position`, `created_at`) is a personal, freeform way to organize lists beyond the fixed `lists.type` enum — e.g. "Vacances", "Anniversaire de Léo" — orthogonal to `type` rather than a replacement for it. Unlike every other grouping concept in this app (`houses`, shared by all `house_members`), a category is owned by exactly one user (`user_id`) and is never itself shared: `internal/db/custom_categories.go`'s `GetCustomCategoryForUser`/`UpdateCustomCategoryForUser`/`DeleteCustomCategoryForUser` all scope their `WHERE` clause on `user_id`, so a category can only ever be found, edited, or deleted by whoever created it — a mismatched owner comes back as the same `ErrNotFound` as a nonexistent id (never a separate 403), the same "don't let a lookup confirm another user's data exists" reasoning `UpdateCustomCategoryForUser` shares with `authorizeHouseAccess`'s sibling checks. `lists.custom_category_id` (`INTEGER`, nullable, `addColumnIfMissing`-guarded like `house_id`, `REFERENCES custom_categories(id) ON DELETE SET NULL`) is how a list attaches to one — `ON DELETE SET NULL` rather than `CASCADE` is deliberate, since deleting a category should only unassign it from any list that used it, not delete the list itself. Any member of the list's house can associate or dissociate a category via `POST`/`PUT /api/v1/lists` (`custom_category_id` in the request body; omitted/`null` on the `PUT` full-replace dissociates, matching how `type` already resets to its default when omitted there), but the id must reference a category the *requesting* user owns (`internal/handlers.validateCustomCategoryOwnership`, `internal/handlers/lists.go`) — a shared list can be tagged with one member's personal category, but not with a category belonging to someone else in the house. `GET /api/v1/lists`/`GET /api/v1/lists/{id}` embed the attached category's full row (`custom_category`) via a `LEFT JOIN` in `internal/db.listSelect`, visible to every house member regardless of who owns the category, since seeing a shared list's category tag doesn't require owning it. The frontend (`static/js/spaces.js`) is a fourth dashboard tab, "Espaces" (`#tab-spaces`/`#spaces-view`), rendering each category as a collapsible `<details>` section (mirroring `#done-section`'s chevron/`group-open:` idiom) holding every list attached to it regardless of `type` — see the "Custom categories frontend" bullet below for the full design.
- **Granular sharing (Spaces & Lists)**: beyond house membership, a Space (a `custom_categories` row) or an individual List can be shared directly with one other user by email, giving them `read` or `write` access to it without adding them to the whole parent house — two new tables, `space_shares` and `list_shares` (`id`, `custom_category_id`/`list_id`, `shared_with_user_id`, `permission` ∈ `read`/`write`, `created_at`, each with a `UNIQUE (…, shared_with_user_id)` constraint so re-sharing with a different permission upserts via `internal/db.CreateOrUpdateSpaceShare`/`CreateOrUpdateListShare` rather than erroring). `internal/db.AccessLevelForList` is the single place that combines the three access sources into one verdict for a given user and list — house membership (always `write`, unchanged from before this feature), a `list_shares` grant on the list itself, and a `space_shares` grant on the list's `custom_category_id` if any, taking the higher of the two shares when both apply. `internal/handlers.authorizeListAccess`/`authorizeItemAccess` (`internal/handlers/rbac.go`) replace the old house-only checks on every list/item read and mutation handler, each now taking a `requireWrite bool` — read-only handlers (`GET`) accept `read`, mutating ones (`POST`/`PUT`/`PATCH`/`DELETE`) require `write` — with one deliberate exception: `DELETE /api/v1/lists/{id}` stays House-membership-only even for a `write` share holder, since destroying a whole list (and everyone else's items in it) is a house-management-level action, not just editing. Sharing a **Space** is the owning user's call alone (`internal/handlers.authorizeSpaceOwner`, the same check as renaming/deleting the category); sharing a **List** requires actual House membership of it (`authorizeHouseAccess`, not merely `write` access via another share), so access granted through a share can never itself be used to extend further access. `internal/handlers/shares.go` exposes `GET`/`POST /api/v1/{custom-categories,lists}/{id}/share` and `DELETE .../{id}/share/{userId}` (mirroring the roster/invite/remove shape of `/houses/{id}/members`); `GET /api/v1/lists?shared_with_me=true` (`internal/db.ListSharedListsForUser`) is the reverse query backing the "Partagé avec moi" dashboard tab — every list reachable via either share table, excluding any whose house the caller is already a plain member of (already visible the ordinary way). The frontend (`static/js/shares.js`) owns a shared create/revoke modal (`#share-modal`, opened via `openShareModal({kind, id, name})` from a 👥 button on every list card/space section and the list-detail header) and the fifth dashboard tab (`#tab-shared`/`#shared-view`, wired into `planning.js`'s `setActiveTab` switcher alongside the other four); a card reached via `?shared_with_me=true` shows a 👥 "Partagé" badge (from `list.access_source`, a response-only field like `Item.PriceStatus`) and no edit/share/delete controls, since managing a list requires actual House membership. Full design and endpoint reference: [docs/API.md](docs/API.md#sharing) and [docs/DATABASE.md](docs/DATABASE.md#space_shares-and-list_shares).
- **Pinning shared lists (and shared Spaces) to the dashboard**: the recipient of a share can choose to have it show up alongside their own house's lists on the main dashboard, instead of having to go find it in the "Partagé avec moi"/"Espaces" tabs every time. Two independent pin flags, combined via OR: `list_shares.is_pinned_to_dashboard` (`INTEGER NOT NULL DEFAULT 0`, migration 11) pins one List, toggled via `PATCH /api/v1/lists/{id}/share/pin` (`internal/handlers.handleListSharePin`/`internal/db.SetListSharePinned`); `space_shares.is_pinned_to_dashboard` (migration 12) pins a whole Space — every List reachable through it, present and future, no per-list action needed — toggled via `PATCH /api/v1/custom-categories/{id}/share/pin` (`internal/handlers.handleSpaceSharePin`/`internal/db.SetSpaceSharePinned`). Both endpoints' only authorization check is "does the caller hold a share row for this List/Space at all" (surfaced as `404`, not `403`, matching this file's existing "don't distinguish nonexistent from unauthorized" convention) — there's no house-membership or ownership check, since this is the recipient's own preference about their own dashboard, not a change to who can access anything. A List reached *only* through a shared Space (no `list_shares` row of its own yet) can still be pinned individually: `SetListSharePinned` auto-creates that row on demand, scoped to exactly the permission the Space already grants for that List (via a `lists JOIN space_shares` lookup on `custom_category_id`), so the insert can never itself change the recipient's `AccessLevelForList` verdict — it just gives the individual pin flag somewhere to live. `db.ListSharedListsForUser` (the same query backing `?shared_with_me=true`) surfaces the combined state as `List.IsPinnedToDashboard`, a response-only field alongside `AccessSource`/`AccessPermission`: for a `space_share`-sourced row this now comes from `space_shares.is_pinned_to_dashboard` directly (pinning the Space) rather than a hardcoded `false`; when a List is reachable both via its own `list_shares` row and via its Space, whichever source says pinned wins — the same "OR", not "AND", the higher-of-two-permissions dedup already uses — so unpinning one List individually cannot override its parent Space being pinned as a whole; the Space-level pin is the "master" pin for everything reachable through it. `db.ListSpacesSharedWithUser` (backing `GET /api/v1/custom-categories?shared_with_me=true`) is the Space-level "shared with me" query, the category-level equivalent of `ListSharedListsForUser`, surfacing `AccessPermission`/`IsPinnedToDashboard` response-only fields on `CustomCategory` the same way. The frontend has no server-side "house lists plus pinned shares in one call" endpoint to lean on: `static/js/app.js`'s `loadDashboard` fetches its usual `?house_id=` listing, then separately calls `static/js/shares.js`'s `loadPinnedSharedLists` (a thin wrapper around `?shared_with_me=true`, filtered to `is_pinned_to_dashboard`) and merges the two client-side before splitting into the three dashboard grids — a best-effort merge (`.catch(() => [])`) so a failure fetching pinned shares can never block the rest of the dashboard from rendering, and, like the rest of the sharing feature, with no offline mirror (pinned shared cards simply aren't shown while offline). `buildListCard` (`app.js`) grows a 📌/📌-filled pin/unpin button (`toggleListPin`, a plain await-then-`refreshVisibleView()` mutation, not the coalesced-optimistic pattern item quantity/urgent toggles use, since this is an infrequent deliberate action rather than a rapid-fire control) shown for both `list.access_source === 'list_share'` and `'space_share'` — the same 👥 "Partagé" badge the granular-sharing feature already renders for any `access_source` is reused as-is for the "distinguish a pinned card from an owned one" requirement, plus a small 📌 "Épinglée" badge shown whenever `is_pinned_to_dashboard` is true, independent of the button's own state. `static/js/spaces.js`'s "Espaces" tab gains an "Espaces partagés avec moi" section (`buildSharedCategorySection`) listing every Space shared with the caller (pinned or not, so there's somewhere to discover and toggle the pin in the first place) with a `[⋮]` kebab opening `#space-card-actions-sheet` for the pin/unpin toggle — a Space's own lists there are drawn from `?shared_with_me=true`, filtered to `custom_category_id`s actually present in that shared-categories list (so a List shared *individually* that happens to sit in the owner's other, unshared category is never incorrectly grouped under a "shared space" section). Full design and endpoint reference: [docs/API.md](docs/API.md#patch-apiv1listsidsharepin), [docs/API.md](docs/API.md#patch-apiv1custom-categoriesidsharepin) and [docs/DATABASE.md](docs/DATABASE.md#space_shares-and-list_shares).
- **Recurring items**: an item can carry `recurrence_rule` (`TEXT`, nullable — one of `DAILY`/`WEEKLY`/`MONTHLY`/`YEARLY` or the custom `EVERY_X_DAYS:<n>` form, validated by `internal/validate.Recurrence`), `due_date` (`TEXT`, `YYYY-MM-DD`, validated by `internal/validate.Date`), and `recurrence_end_date` (same format/validator). All three are `addColumnIfMissing`-guarded the same way as `price`/`target_month`. `items.is_recurring` (`INTEGER NOT NULL DEFAULT 0`) is never a separate input anywhere in the stack — `internal/db.CreateItem`/`UpdateItem` always write it as `recurrence_rule IS NOT NULL`, so the two columns can never disagree. The behavior that makes this "recurring" rather than just three inert columns lives in `internal/handlers.applyRecurrenceCompletion` (`internal/handlers/recurrence.go`), called from `handleItemsUpdate`/`handleItemsPatch` right before the final `db.UpdateItem`: when a recurring item's `done` transitions `false → true` (checked against the item's *previous* `Done`, the same pattern `previousURL` already uses for the image-invalidation logic), it computes the next occurrence's `due_date` via `nextDueDate` (advancing from the item's current `due_date`, or from today if it has none yet, by the rule) and flips `Done` back to `false` — the item is un-checked with an advanced date instead of staying marked done, and instead of cloning a new row per occurrence, so a recurring chore never accumulates one item per completion (the "décale simplement la date" alternative, chosen for exactly that reason). If `recurrence_end_date` is set and the computed next occurrence would land after it (a plain string comparison, since both are `YYYY-MM-DD` and stay lexicographically comparable), the item is left `done: true` instead and never advances again. Clearing `recurrence_rule` (empty string via `PATCH`, or omitting it via `PUT`) clears `due_date`/`recurrence_end_date` along with it, since neither means anything once an item stops recurring. The frontend's recurrence `<select>` (`static/js/list_view.js`, in both the create-item form and the edit-item modal, not gated by `data-shopping-only` since a recurring chore applies to `todo` lists just as naturally as a shopping item) only offers the four fixed cadences — `EVERY_X_DAYS:<n>` is API-only, accepted for forward compatibility but with no UI to set it yet. A recurring item's row shows a small 🔄 badge with the translated frequency (`recurrenceBadgeLabel`/`buildRecurrenceBadge`) that stays in place across completions. Because the PATCH that checks an item off can be queued offline, `static/sw.js` carries a hand-kept JS port of the same completion logic (`applyRecurrenceCompletionOffline`/`nextDueDateOffline`, called from `applyOptimisticEdit` and `resolveAgainstPendingCreate`) so a recurring item checked off while offline advances immediately in the local optimistic state instead of sitting "done" until the sync queue flushes and a refetch corrects it — **any change to the Go rule-handling must be mirrored there by hand**, since there's no code sharing between the two runtimes. Verified end-to-end in three real headless-Chromium (Playwright) sessions: create-with-recurrence via the item form and badge rendering, the edit-modal round-trip (open → empty prefill → set MONTHLY → save → badge appears → re-open shows MONTHLY prefilled → clear → badge gone), and — with `BrowserContext.setOffline(true)`, after confirming the service worker actually controlled the page first — checking a recurring item off while offline: it stayed in the active section with its badge (not moved to "done"), confirming `applyRecurrenceCompletionOffline` fired. No console errors in any of it.
- **Automatic price & image lookup**: when an item is created, or its `url` changes, `internal/handlers.scrapeProductInfo` (`internal/handlers/scrape.go`) kicks off a detached goroutine — never `r.Context()`, which is canceled the moment the response is written — that calls `internal/scraper.FetchProductInfo(ctx, url)` **once** and writes back whichever of `price`/`image_url` the item is still missing (an explicit `price` in the request only skips price detection — the image is still looked up) via `db.UpdateItemPriceIfMissing`/`db.UpdateItemImageIfMissing`. Both of those methods' `WHERE ... AND url = ? AND <column> IS NULL` guards are what makes this safe to run detached from the request: a slow scrape can never clobber a price/image the user already has, or one for a since-changed `url`, no matter how the race resolves. Unlike a purely fire-and-forget design, `handleItemsCreate`/`Update`/`Patch` (`internal/handlers/items.go`) each wait up to `syncScrapeTimeout` (2.5s) on that goroutine before responding: if it lands in time, the response already carries the real `price`/`image_url` and a response-only `price_status: "found"` field (`models.Item.PriceStatus`, `json:"price_status,omitempty"`, never persisted, never present on a plain `GET`); if not and a price was still needed, `scrapeProductInfo` returns `"pending"` and the goroutine keeps running in the background exactly as the original fully-async design always did — but if only the image was still outstanding (price was already known), it returns `"found"` instead, since price detection genuinely isn't pending; the image is treated as a best-effort enhancement that simply shows up next time the item is fetched if it's slow to arrive. `price_status` is `"none"` when there was nothing to scrape (no `url`, or no price found within the wait) — this is unaffected by whether an image was found. This bounded wait is what lets `static/js/list_view.js` update the DOM straight from the POST/PATCH response instead of reloading or polling — see the frontend bullet below — while still never blocking indefinitely on a slow or unresponsive site. `items.price_auto` (`INTEGER NOT NULL DEFAULT 0`, same 0/1-boolean convention as `done`) records whether the current `price` came from this lookup rather than a user — the frontend shows a small badge next to an auto-detected price, clickable to open the same edit-item modal used everywhere else; sending `price` in any request (including an explicit `null`) always resets it to `false`, since a manual value was supplied. `items.image_url` (`TEXT`, nullable) is scraper-only — there is no request field to set it manually — and is cleared back to `nil` whenever `url` changes to something new (both `PUT` and `PATCH` in `internal/handlers/items.go` compute this before calling `db.UpdateItem`), since an image found for the previous `url` no longer describes the item. `internal/scraper.FetchProductInfo` parses the page once (`extractProductInfo`) and looks for a price, an image, and a title (the last currently extracted but not yet consumed by any caller — see below) using `golang.org/x/net/html` rather than regex-scraping raw HTML. The request carries a real desktop-Chrome `User-Agent` and an `Accept-Language: fr-FR,fr;q=0.9,en-US;q=0.8,en;q=0.7` header (`internal/scraper/scraper.go`'s `userAgent`/`acceptLanguage` consts) — several storefronts this targets (Reichelt and Amazon in particular) block or serve a stripped page to a generic/library User-Agent, and this is purely to see the same page an ordinary visitor's browser would for a URL the user themselves added to their own list. Price priority order: Schema.org JSON-LD (`price` inside an `Offer`), OpenGraph/`product:` meta tags (`og:price:amount`/`product:price:amount`), a Twitter Card `twitter:dataN` value whose paired `twitter:labelN` reads as "Price"/"Prix" (`resolveTwitterPrice` — some storefronts expose a price only this way), then classic microdata (`itemprop="price"`, read off either a `content` attribute or the element's text — checked on every element, including a `<meta itemprop="price" content="...">`, not just non-`<meta>` tags). Image priority order: on an Amazon host (`isAmazonHost` — `amazon.*`, `amzn.to`, `amzn.eu`) only, Amazon's own product-image element (`id="landingImage"`/`id="imgBlkFront"`)'s `data-old-hires` or `data-a-dynamic-image` attribute first (`amazonLandingImage`/`bestDynamicImage` — Amazon's own `og:image` is frequently the site logo or a nav icon, never trusted first there); then, on every host, Schema.org JSON-LD (`image`, as a string, array, or nested `ImageObject`), `og:image` (skipped when the URL contains an Amazon-chrome term — `amazon-logo`/`nav2`/`favicon`/`tile` — `isAmazonGenericImage`, checked regardless of host but only ever matches on Amazon's own asset URLs in practice), classic microdata (`itemprop="image"`, off a `content`/`src` attribute), and the Twitter Card tag (`twitter:image`) as a last resort. Title priority order: JSON-LD (`name`, preferring an object whose own `@type` is `"Product"` over an unrelated `name` elsewhere on the page — `findJSONTitle`/`searchJSONProductName` — a page frequently carries more than one JSON-LD block), `og:title`, then the page's own `<title>`. None of this changes how a price is *stored* or *displayed*: `ProductInfo.Price` stays a bare `float64` with no currency symbol, exactly as before — `parsePriceString` just has to parse the number correctly (it already tolerates both `"15,90 €"`-style and `"15.90"`-style input), and the frontend's existing hardcoded EUR `Intl.NumberFormat` (`static/js/list_view.js`'s `euroFormatter`) renders it with a currency symbol on display as it always has. A relative image URL is resolved to absolute against the page's own URL (`resolveImageURL`, `url.ResolveReference`) and only accepted if the result is `http`/`https` with a non-empty host — the same rule `internal/validate.URL` applies to `item.url` — so a `javascript:`/`data:` URI can never end up as an item's `image_url`. Because this makes the server fetch an arbitrary URL a user typed into the `url` field, its `http.Client`'s `Transport.DialContext` is replaced with an SSRF guard (`safeDialContext` in `internal/scraper/scraper.go`) that resolves the host itself and only ever dials a public IP (rejecting loopback/private/link-local/multicast, which also covers the `169.254.169.254` cloud metadata address) — dialing the checked IP literal directly, rather than letting the transport re-resolve the hostname, is what closes the DNS-rebinding TOCTOU gap a naive "check then dial" would leave open. Every failure mode (network error, timeout, blocked host, no recognizable price/image/title markup) is treated identically as "nothing found" — this feature must never fail item creation/update outright, and the bounded wait keeps it from blocking indefinitely either.
- **Authentication & authorization**: local email+password (bcrypt) and generic OIDC/OAuth2 SSO (Authelia/Authentik/Keycloak/Google, ...) both establish the same opaque, server-side session — an HTTP-only, `SameSite=Lax` cookie whose value hashes to a row in the `sessions` table (`internal/auth.Service`); see the CSRF bullet below for why Lax is still safe here, and the "Mobile/PWA login loop" bullet in the handoff log for why it isn't `Strict`. Every `/api/v1/...` request is gated as a whole behind `(*handlers.Application).RequireSession` (wrapped once around a sub-`http.ServeMux` in `Routes()`, not per-route) — deliberately **not** a separate `internal/middleware` package, since that middleware needs `*db.DB` and `internal/handlers` needs to call it to build routes, which would be an import cycle either direction; it lives as an `*Application` method next to every other handler instead. `/auth/...` (login page, register/login/logout submit, OIDC redirect/callback) and all static assets stay unauthenticated by design — gating static files would break the service worker's cache-first app-shell strategy, so the auth boundary is the JSON API, and `static/js/app.js`'s `apiRequest()` handles the client-side redirect-to-login on a `401`. A house's lists/items are only visible to its members (`internal/handlers/rbac.go`'s `authorizeHouseAccess`/`authorizeHouseOwner`, checked against `house_members` via `internal/db`); `CreateHouseWithOwner` (the only way a house gets created through normal use) is the one place in `internal/db` that opens an explicit `sql.Tx`, so a house is never left without an owner. The OIDC client (`internal/auth/oidc.go`, `jwt.go`) is hand-rolled — discovery, Authorization Code + PKCE, JWKS fetch/cache, RS256 id_token signature verification — using only the standard library plus `golang.org/x/crypto/bcrypt` (the one new dependency this feature added), rather than pulling in `coreos/go-oidc`/`golang.org/x/oauth2`, per the "standard library wherever possible" convention below.
- **Web Push notifications**: `internal/webpush` is a from-scratch implementation of Web Push (RFC 8030), VAPID application-server identification (RFC 8292), and the `aes128gcm` payload encryption a push message is carried in (RFC 8291) — `GenerateVAPIDKeys`/`vapidPrivateKeyFromB64` build on `crypto/ecdh`/`crypto/ecdsa` (bridged via `ecdsa.PrivateKey.ECDH()`/`ecdh.PublicKey.Bytes()` rather than the deprecated `crypto/elliptic` point-arithmetic helpers), `signVAPIDJWT` hand-rolls the ES256 JWT the same way `internal/auth/jwt.go` already hand-rolls OIDC's, and `encryptPayload` hand-rolls HKDF (RFC 5869, on top of `crypto/hmac`/`crypto/sha256` rather than depending on exactly which Go toolchain version first shipped a dedicated `crypto/hkdf` package) plus AES-128-GCM framing — all per the "standard library wherever possible" convention, the same reasoning that already justified hand-rolling OIDC/JWT rather than pulling in a third-party Web Push library. `internal/webpush/webpush_test.go`'s `TestEncryptPayloadMatchesRFC8291Example` drives the encryption path with RFC 8291 Appendix A's own published key pairs/salt and asserts every intermediate value (ECDH secret, IKM, PRK, CEK, nonce) and the final ciphertext match the RFC's own worked example byte-for-byte — the strongest correctness signal available for this code short of a live push service, and how a subtle HKDF/framing bug would be caught here rather than only silently failing to deliver against a real browser. `Send`'s `http.Client` carries its own independent copy of `internal/scraper`'s SSRF dial guard (`internal/webpush/ssrf.go` — see the SSRF security rule above for why a push subscription's `endpoint` needs the same defense as an item's `url`).

  A user opts in from the "Paramètres" modal's "Activer les notifications push" toggle (`static/js/push.js`, `#user-settings-push-toggle` in `static/index.html`): it calls the browser's own `Notification.requestPermission()` (nothing server-side can skip or pre-empt that native prompt), subscribes via `PushManager.subscribe({applicationServerKey: ...})` using the public key from `GET /api/v1/push/vapid-public-key`, and registers the resulting subscription (`endpoint`/`keys.p256dh`/`keys.auth`) via `POST /api/v1/push/subscribe` (`internal/handlers/push.go`, stored in the new `push_subscriptions` table, upserted on `(user_id, endpoint)` so a browser key rotation or re-enabling push refreshes the row rather than erroring). `refreshPushToggleUI` re-derives the toggle's checked/disabled state and an explanatory status line every time the settings modal opens — unsupported browser, push not configured on this instance (`{"enabled": false}` from the vapid-public-key endpoint), permission previously denied (only undoable via the browser's own site settings, never re-promptable from script), or the ordinary on/off state of an actual subscription — rather than caching a stale answer, since permission can change outside the app at any time. `internal/handlers.sendToUsers` (`push.go`) is the single delivery fan-out both use cases below call: best-effort and concurrent across every recipient's subscriptions (one slow/dead device never blocks another), deleting a subscription outright on `webpush.ErrSubscriptionGone` (RFC 8030 §7.3's `404`/`410` "this no longer exists" signal) and just logging anything else, since a push notification is always a secondary effect of an action that already succeeded and must never be able to make that action look like it failed.

  **Use case 1 — shared list changes**: `internal/handlers.notifyListChange` (`push.go`) fires, in a detached goroutine on its own bounded context (never `r.Context()`, the same "canceled the moment the response is written" reasoning `scrapeProductInfo` already follows), from exactly two call sites — `handleItemsCreate` (unconditionally, every created item) and `handleItemsUpdate`/`handleItemsPatch` (only on a `done` `false → true` transition, captured *before* `applyRecurrenceCompletion` runs, since that call flips a recurring item's `Done` back to `false` the moment it detects the same transition — checking `Done` afterward could no longer tell a genuine check-off apart from an item nobody touched). Deliberately scoped to just "added" and "checked off", per the feature's own spec, not every field edit (a price/quantity/rename edit stays silent). Recipients are every *other* user with access to the list — `internal/db.ListNotificationRecipients(ctx, listID, excludeUserID)`, a plain `UNION` of the same three sources `AccessLevelForList` already combines (House membership, `list_shares`, `space_shares` via the list's `custom_category_id`), inverted from "can this user see the list" to "who can see the list", excluding whoever's own action triggered it (an id of `0` — no real user ever has it — excludes nobody, the shape the due-date scan below uses instead). The notification's `Notification` options set `silent: true` (no sound/vibration, but still a real, visible notification — browsers restrict/penalize genuinely data-only "silent push" with no UI at all, so this is what satisfies "notification silencieuse" without going there) and `data: {url: "/?list={id}"}` for `notificationclick` routing (see the frontend paragraph below).

  **Use case 2 — recurring task due-date reminders**: two new nullable `items` columns, `recurrence_lead_minutes` (an optional per-item override of the instance-wide default lead time, exposed through `POST`/`PUT`/`PATCH /api/v1/items` exactly like `is_urgent`/`target_month` — see [docs/API.md](docs/API.md#items) — but, like `EVERY_X_DAYS:<n>` before it, API-only for now: there is no frontend input to set it yet, only the four-cadence recurrence `<select>` in `static/js/list_view.js`) and `due_reminder_sent_for` (internal bookkeeping only, never in `models.Item` or the JSON API — the exact `due_date` value a reminder has already been sent for). `internal/handlers.RunRecurringDueScan`, wired to a ticker in `cmd/server/main.go` (`runRecurringNotifyScanLoop`, mirroring `runPriceAlertScanLoop`'s "run once immediately, then on `NOTIF_RECURRING_SCAN_INTERVAL_MINUTES`" shape, gated on both a positive interval and `Config.PushEnabled()`), calls `db.ListItemsForRecurringNotifyScan` — every recurring, not-done item with a `due_date` whose `due_reminder_sent_for` doesn't already match it — and, for each one whose due date is now within its lead time (the item's own `recurrence_lead_minutes` if set, else `NOTIF_RECURRING_TASK_LEAD_TIME`, default `24h`; accepts a plain Go duration or a whole number of days via a hand-rolled `d`-suffix parser in `internal/config`, e.g. `1d`, since `time.ParseDuration` has no day unit), notifies every user with access to its list (again via `ListNotificationRecipients`, this time with no actor to exclude) and calls `db.MarkRecurringReminderSent(itemID, dueDate)`. Storing the *due date value itself* rather than a boolean/timestamp flag is what makes this re-arm automatically the moment `due_date` next changes for any reason (the item's own recurrence advancing on completion, or a manual edit) — the stored value simply stops matching the new `due_date`, with no explicit "clear the flag" step needed anywhere in the codebase.

  Server-composed notification text (both use cases) is always French, regardless of the recipient's own FR/EN choice — there is no per-user language preference stored server-side to localize it with (`static/js/i18n.js`'s toggle is a client-side-only `localStorage` choice), the same reasoning that already leaves `templates/login.html` French-only. `static/sw.js`'s `push` listener parses the (already browser-decrypted) JSON payload (`{title, body, url}`) and calls `showNotification`; its `notificationclick` handler closes the notification and either focuses an already-open tab — `postMessage`-ing it `{type: 'trakka-notification-click', url}` rather than relying on the unevenly-supported `WindowClient.navigate()`, handled by `app.js`'s `handleNotificationClickMessage` — or, with no tab open, calls `clients.openWindow(url)`, which lands on a fresh load of the SPA that itself reads the same `?list=` query param at boot (`app.js`'s `handleDeepLinkOrRestore`, spliced into `init()` in place of a bare `restoreLastView()` call: a `?list=` deep link takes priority over the ordinary last-visited-tab/list restore, and is stripped via `history.replaceState` once consumed so a later reload doesn't keep re-triggering it). `trakka -generate-vapid-keys` (`cmd/server/main.go`) prints a fresh key pair for `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` and exits, needing no configuration itself. Verified: `internal/webpush`'s RFC 8291 conformance test above, DB-layer tests for the subscription upsert/batch-lookup, the recipient-resolution `UNION` across all three access sources, and the scan-query re-arm behavior, plus handler tests for subscribe/unsubscribe validation and idempotency — `go build`/`go vet`/`gofmt -l .`/`CGO_ENABLED=1 go test -race ./...` all clean. **Not yet done**: never exercised against a real browser or a real push service (FCM/Mozilla autopush/...) — no browser automation tooling was available in the sandbox this was built in, the same caveat nearly every other frontend-touching feature in this log carries, and additionally there is no local way to receive a real push at all without an actual subscribing browser; the async `notifyListChange`/`RunRecurringDueScan` → `sendToUsers` → `webpush.Send` delivery path specifically could not be integration-tested end-to-end even with tooling, since `webpush.Send`'s own SSRF guard correctly refuses to dial `httptest.NewServer`'s loopback address (the same limitation `internal/scraper`'s tests already document for the identical reason). Try it against a real subscribed browser and a real recurring item nearing its due date before relying on it.
- **Docker build is multi-stage and CGO-free by requirement**: builder stage `golang:1.27.0-alpine` compiles `./cmd/server` with `CGO_ENABLED=0` to a static, stripped binary (`-ldflags="-s -w"`); runtime stage is `gcr.io/distroless/static-debian12` (no shell, no package manager — chosen over an Alpine runtime specifically to shrink the attack surface, since this binary needs nothing beyond CA certificates, which that image already ships), running as a fixed non-root numeric UID:GID (`10001:10001`), chosen specifically so it maps cleanly under Podman's rootless user-namespace remapping — don't switch to a named `USER` (or to distroless's own built-in `nonroot` user, which is UID `65532`) without keeping the numeric UID pinned. Because distroless has no shell to run `adduser`/`mkdir` in, the `/etc/passwd`/`/etc/group` entries for that UID and an empty, correctly-owned `/data` directory are created in the *builder* stage and `COPY --from=build`'d into the runtime stage, alongside `static/` and `templates/` (the latter for `login.html`). Distroless ships no `tzdata`; this is a non-issue since the app never calls `time.LoadLocation` and every timestamp it stores or logs is UTC by convention, and `compose.yml` no longer sets `TZ` (it would be silently ignored). `compose.yml`'s `trakka` service also sets `read_only: true` (with `/data` and a small `tmpfs` at `/tmp` as the only writable paths) and `cap_drop: [ALL]` — a plain HTTP+SQLite server needs no Linux capabilities, not even `NET_BIND_SERVICE`, since it binds an unprivileged port.
- **`compose.yml`** must stay valid for both `docker compose` and `podman-compose` — avoid Compose fields that only one of the two supports. The `radicale` (CalDAV) service is optional and gated behind the `calendar` profile; it should never start by default.
- **PWA/offline (`static/sw.js`, `static/js/db.js`)**: full design in [docs/PWA.md](docs/PWA.md) — read it before touching either file. The short version: `db.js` is loaded both as a page `<script>` and via the service worker's `importScripts()`, so it must never reference `window`/`document`, only `indexedDB` and `self`. `sw.js` transparently intercepts every `fetch()` from `app.js`; offline mutations get a temporary `temp-list-*`/`temp-item-*` id and are queued in IndexedDB, and `remapTempId()` patches any still-queued request that depended on one once it gets a real server id. `app.js` also reads (never writes) `TrakkaDB.getQueue()` directly, purely to show the "N en attente" badge — the service worker remains the only writer of the queue/mirror stores; don't add a second writer. Houses get the same read-only mirror (`TrakkaDB.getHouses`/`putHouses`/etc.) but are deliberately **not** offline-writable — creating/renaming/deleting a house while offline returns a `503` rather than being queued, because queueing it would require a second level of temp-id chaining (list → house, on top of the existing item → list) that the offline design explicitly doesn't support; see "Houses are read-mirrored but not offline-writable" in [docs/PWA.md](docs/PWA.md). Session cookies are ambient/browser-managed, so a queued write replayed later by `flushQueue()` automatically carries whatever cookie is present at replay time — no header snapshotting needed — but `flushQueue()` special-cases a `401` reply (expired session) by leaving the entry queued instead of discarding it like an ordinary rejected `4xx`, so a session expiring mid-queue can't silently drop an offline edit; see "Session expiry vs. the offline queue" in [docs/PWA.md](docs/PWA.md). `/auth/...` requests bypass the service worker entirely (checked first in the `fetch` handler) — never cache-first-served, never offline-queued. **Service workers require a secure context** (`https://` or exactly `http://localhost`) — they silently don't register anywhere else, which is why `compose.yml` serving plain HTTP is only enough for `localhost` testing (see [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)).

## Security rules

These are standing constraints for this codebase, not just how the current code happens to be written — preserve them in anything new:

- **SQL**: every query goes through `database/sql` parameter placeholders (`?`), exclusively inside `internal/db`. Never build a query string by concatenating or `fmt.Sprintf`-ing a user-supplied value into it.
- **URLs**: any user-supplied URL (currently: an item's `url` field) must pass `internal/validate.URL`, which requires an absolute `http://` or `https://` URL with a non-empty host — this blocks `javascript:`, `data:`, and similar schemes from ever being persisted. Apply the same validator to any future field that accepts a URL. The frontend (`static/js/app.js`) re-checks the scheme client-side before ever setting an `<a href>`, as defense in depth — keep that check if you touch the rendering code.
- **Response encoding**: JSON responses rely on `encoding/json`'s default `SetEscapeHTML(true)` behavior (escaping `<`, `>`, `&`) — never call `SetEscapeHTML(false)` on the encoder in `internal/handlers/json.go`.
- **Response caching**: `writeJSON` (`internal/handlers/json.go`) sets `Cache-Control: no-store` on every `/api/v1/...` JSON response — never remove this or add a competing `Cache-Control`/`Expires` header elsewhere for an API route. It exists so the browser's own HTTP disk cache (a layer entirely separate from the service worker's Cache Storage API, which `static/sw.js` never uses for `/api/v1/...` at all) can never hand `fetch()` a stale `GET` response instead of a genuine network round trip or, offline, the service worker's IndexedDB-backed fallback — see the "Offline consistency hardening" entry in the session log below.
- **Frontend DOM**: `static/js/app.js` builds all dynamic content with `textContent`/`createElement`, never `innerHTML` with interpolated data. Keep that pattern for any new UI code.
- **HTTP security headers**: `internal/handlers.SecurityHeaders` sets `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, a `Content-Security-Policy`, and `Referrer-Policy: no-referrer` on every response, including static files. The CSP has two deliberate exceptions: `script-src` trusts `https://cdn.tailwindcss.com` (the Tailwind Play CDN script `static/index.html` and `templates/login.html` both load), and `style-src` allows `'unsafe-inline'` because that script generates utility CSS into a `<style>` tag at runtime rather than an external file — there was no way to use Play CDN without it; and `img-src` trusts any `http:`/`https:` source (not just `'self' data:'`) because an item's scraped product thumbnail (`items.image_url`, see the price & image lookup bullet above) can point at any storefront's CDN, with no fixed host list to name in advance — the same reasoning that already lets `item.url` link out anywhere, just extended to `<img src>` now that thumbnails render inline instead of only linking out. Everything else stays strict: no `'unsafe-eval'`, no other inline scripts, no other allowlisted hosts. If you add any other inline `<script>`/`<style>`, move it to an external file instead of widening this further. If Play CDN's ~400KB runtime cost ever needs to go away, switch to a precompiled Tailwind build (Tailwind CLI, output to `static/js/` or a new `static/css/`) instead of the CDN script — that would let `style-src` drop `'unsafe-inline'` again. The OIDC login flow is entirely server-mediated redirects (never a page-JS `fetch` to the IdP), so none of this needed loosening for OIDC support.
- **Passwords & sessions**: passwords are hashed with `golang.org/x/crypto/bcrypt` (`internal/auth.HashPassword`/`VerifyPassword`) — never store or log a plaintext password. Session tokens are `crypto/rand`-generated and stored **hashed** (`internal/auth.HashToken`, SHA-256) in the `sessions` table — the raw token exists only in the cookie and in-flight, so a database leak alone can't hand out live sessions. `Authenticate()` runs a dummy bcrypt comparison even on an unknown email/OIDC-only account, so failed-login timing doesn't reveal whether an email is registered.
- **CSRF**: two independent layers, both in `internal/handlers/csrf.go`. Layer 1 — the session cookie is `SameSite=Lax` (changed from `Strict` — see the mobile-login-loop fix below), which is the app's primary CSRF defense for `/api/v1/...`: Lax omits the cookie from every cross-site request except a top-level GET navigation, and it's never attached to a cross-site `fetch`/XHR (the only way this SPA issues `POST`/`PUT`/`PATCH`/`DELETE`) or a cross-site form POST. Every `GET` route this app exposes is a pure read (`internal/handlers/app.go` — no route mutates state on `GET`), so the one thing Lax additionally allows over Strict — a cookie attached to a cross-site top-level GET navigation — cannot be turned into a state change. `requireSameOriginWrite` backs this up on every `/api/v1/...` write (and on `/auth/logout`) by rejecting a `POST`/`PUT`/`PATCH`/`DELETE` whose `Origin` (or, when `Origin` is absent/`"null"`, `Sec-Fetch-Site`) says the request came from another site — see the "login/register rejected with cross-origin request rejected" fix further down this file for the `Origin: "null"`-on-a-legitimate-navigation edge case this had to account for. Layer 2 — `/auth/login` and `/auth/register` are the one place `SameSite=Lax` protects nothing, since neither carries a pre-existing session cookie for Lax to withhold: a cross-site form POST there can't steal a session, but it can still silently sign a victim into an *attacker-chosen* account ("login CSRF"), after which anything the victim subsequently enters lands in a house the attacker controls. `ensureCSRFToken`/`checkCSRFToken` defend against exactly that with a signed-nothing, compare-everything double-submit: `GET /auth/login` mints (or reuses) a token, sets it as an HttpOnly `trakka_csrf` cookie (scoped to `/auth`, 12h `MaxAge`), and renders it into both forms' hidden `csrf_token` field; the `POST` handlers reject the request (`?error=csrf_failed`) unless the submitted field matches the cookie. A scripted login/registration (curl, a test harness, `docs/DOC_TEST_PRICE_ALERTS.md`'s bootstrap) must therefore `GET /auth/login` first and carry both the cookie and the extracted token into its `POST` — see [docs/API.md](docs/API.md#authentication) for the exact two-step curl recipe. Don't loosen either layer (e.g. `SameSite=None`, or dropping the `csrf_token` requirement) without adding an equivalent defense first, and don't add a state-mutating `GET` handler without revisiting this reasoning.
- **OIDC id_token verification**: hand-rolled in `internal/auth/jwt.go`/`oidc.go` — hard-rejects any `alg` other than `RS256` *before* any key lookup (alg-confusion defense), verifies the RSA signature before ever trusting the claims, and checks `iss`/`aud`/`exp`/`iat` afterward. If you touch this code, preserve that ordering; don't reorder "check claims" before "verify signature".
- **SSRF (server-side request forgery)**: `internal/scraper.FetchPrice` and `internal/webpush.Send` are the two places this server makes an outbound HTTP request to a URL a user supplied (an item's `url` field; a Web Push subscription's `endpoint`, submitted via `POST /api/v1/push/subscribe`) rather than one hard-coded at deploy time. It's the same category of risk as a Slack/Discord link-unfurler, and both are defended the same way: each package's `http.Client` uses its own custom `Transport.DialContext` (`safeDialContext`) that resolves the target host itself and only ever connects to a public IP — rejecting loopback, private/ULA ranges, link-local (including the `169.254.169.254` cloud metadata address), multicast, and unspecified addresses — and dials that checked IP literal directly rather than letting the transport re-resolve the hostname, closing the DNS-rebinding TOCTOU gap a "resolve, check, then dial the hostname" approach would leave open. `internal/webpush` carries its own independent copy of this guard rather than importing `internal/scraper`'s (the two packages have no other reason to depend on each other) — any future feature that makes the server fetch a user-supplied URL must reuse an existing guard or add an equivalent one, never call `http.Get`/`http.Client.Do` directly against untrusted input.

## CI/CD & Sécurité

`.github/workflows/ci.yml` is Trakka's GitHub Actions pipeline. It runs on every push to `main`, every `v*.*.*` tag, every pull request targeting `main`, every published GitHub Release, and on-demand via `workflow_dispatch` (with `image_tag`/`push_to_ghcr` inputs for manual/nightly-style builds). Superseded runs on the same branch/PR are cancelled automatically (`concurrency`).

### Pipeline shape

Four jobs, the last depending on the first three (`needs: [lint, test, security-scan]`):

1. **`lint`** — `gofmt -l .`, `go vet ./...`, `go mod verify`, then `golangci-lint run` (via `golangci-lint-action`, version pinned through the `GOLANGCI_LINT_VERSION` workflow env var). `go mod verify` confirms every module in the build matches the checksums recorded in `go.sum`, so a tampered or corrupted dependency can never silently compile in.
2. **`test`** — `go test -v -race -cover ./...`. The race detector needs `CGO_ENABLED=1` (it links a small C runtime) — this is set for this one step only and has no bearing on the shipped binary, which the `Dockerfile` still always builds with `CGO_ENABLED=0` (see "Go version pinning is intentional and fragile" above; `modernc.org/sqlite` is pure Go either way, so enabling cgo here changes nothing about which SQLite driver gets used).
3. **`security-scan`** — `govulncheck ./...` (native to the Go ecosystem, maintained by the Go team; flags only vulnerabilities your code actually reaches, not every CVE sitting in an unused transitive dependency), `gosec` (Go SAST, SARIF output), a Trivy filesystem/dependency scan (`go.sum` CVEs, SARIF output), and `gitleaks detect` (secret scanning, SARIF output) — checked out with `fetch-depth: 0` specifically for this job (every other job uses the default shallow clone), since gitleaks scans the *full commit history*, not just the tree at HEAD: a credential removed in a later commit is still compromised for good, so only ever scanning the current checkout would miss exactly the case this tool exists for. All three SARIF files upload to the repo's **Security → Code scanning** tab (`github/codeql-action/upload-sarif`, tagged with a `category` — `gosec` / `trivy-fs` / `gitleaks` — so the tools' findings don't overwrite each other there) and this job needs `security-events: write` to do that. `gitleaks` is installed via `go install github.com/zricethezav/gitleaks/v8@${GITLEAKS_VERSION}` (an exact pinned version, same convention as `govulncheck`/`gosec` below) rather than a marketplace Action, and run with `--redact` so a matched secret's actual value never appears in the job log or the uploaded SARIF. A local, opt-in pre-commit hook (`.githooks/pre-commit`, enabled via `git config core.hooksPath .githooks`) runs `gitleaks protect --staged` for faster feedback before a push — see [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md#preventing-committed-secrets) — but CI is what actually gates a merge; the hook is a convenience, not the enforcement point, and silently no-ops (rather than blocking) if gitleaks isn't installed locally.
4. **`build-scan-push`** — builds the Docker image (linux/amd64 only, loaded locally) purely to run a Trivy **image** scan (SARIF, `category: trivy-image`) before anything is pushed anywhere; only if that passes does it build the real multi-arch (linux/amd64+arm64) image and push it to `ghcr.io` — and only when the run isn't a pull request (a PR gets the build+scan but never the push; see the `policy` step's logic) — then attests build provenance for the pushed image via `actions/attest-build-provenance` (a GitHub-native SLSA attestation, keyless via OIDC — hence this job's `id-token: write`/`attestations: write` — verifiable later with `gh attestation verify`). Tags follow `docker/metadata-action`: a sanitized branch-name tag and a `sha-<short>` commit tag on *every* push (including feature branches, for traceability), the tag's own semver on a `v*.*.*` push, `latest` *only* on that same `v*.*.*` tag push (`enable=${{ startsWith(github.ref, 'refs/tags/v') }}` — deliberately not `{{is_default_branch}}`, so `latest` no longer moves on an ordinary push/merge to `main`), plus the manual `image_tag` input on a `workflow_dispatch` run.

Both Trivy scans and gosec are hard gates (`exit-code: "1"` on any unfixed `CRITICAL`/`HIGH` finding) — they still upload whatever SARIF they produced first (`if: always()` on the upload step), so a failing run still shows its findings in the Security tab rather than only in the job log.

### Permissions model

The workflow denies everything by default (`permissions: read-all` at the top level) and each job then declares only what it actually needs, narrowing below even that default:

| Job | Permissions | Why |
|---|---|---|
| `lint` | `contents: read` | just needs to check out the code |
| `test` | `contents: read` | same |
| `security-scan` | `contents: read`, `security-events: write`, `actions: read` | the second grant is for uploading SARIF; the third is required by `upload-sarif` itself to look up the current workflow run (only actually enforced on a private repo, but harmless to grant regardless) |
| `build-scan-push` | `contents: read`, `packages: write`, `security-events: write`, `actions: read`, `id-token: write`, `attestations: write` | pushing to GHCR, uploading the image-scan SARIF, minting the provenance attestation, and (same as `security-scan`) letting `upload-sarif` read the current workflow run each need their own scope |

No job gets `write` access it doesn't use — in particular, only `build-scan-push` can ever push anything, and only on a non-PR event.

**Gotcha discovered the hard way**: `github/codeql-action/upload-sarif` calls the GitHub REST API to look up the current workflow run (used to correlate the SARIF upload with it) — this needs `actions: read`, which is *not* covered by `security-events: write`. On this originally-private repo, omitting it made every `upload-sarif` step fail with `Error: Resource not accessible by integration - .../actions/workflow-runs#get-a-workflow-run`, and because the *next* step in `security-scan` (`Trivy filesystem scan`) had no `if: always()`, that failure skipped it too — so the following `Upload Trivy filesystem SARIF` step (which *does* have `if: always()`) then failed a second, different way: `Error: Path does not exist: trivy-fs-results.sarif`, because the scan that would have produced it never ran. Both symptoms had the single root cause above. Any job that calls `upload-sarif` needs `actions: read` alongside `security-events: write`, even though GitHub's own quickstart examples often show only the latter.

### The golden rule: pin every action to a commit SHA

Every `uses:` in this workflow is pinned to a full 40-character commit SHA, never a floating tag (`@v4`) or branch — a tag can be force-moved to point at different code (the exact "GitHub Action supply-chain poisoning" class of attack this defends against), a SHA cannot. **Any new action added to this workflow, or a version bump of an existing one, must follow the same rule**: resolve the release tag to its commit SHA and pin that, with a `# vX.Y.Z` trailing comment so a human can still tell which release it is at a glance:

```yaml
uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
```

To find the SHA for a tag: `git ls-remote --tags https://github.com/<owner>/<repo>.git <tag>` locally, or `gh api repos/<owner>/<repo>/tags` (the *tags* endpoint, not `git/refs/tags`, which can return the wrong SHA for an annotated tag — the tags endpoint always returns the dereferenced commit; this actually happened while pinning this workflow: `golangci-lint-action`, `trivy-action`, and `codeql-action`'s tags are annotated, and `git/refs/tags` returned each tag object's own SHA rather than the commit it points to). The GitHub web UI's release page also shows the tag, which you can resolve the same way. Never trust a SHA pasted from anywhere you can't independently re-derive.

`.golangci.yml` configures `errcheck` to exclude the `Close`/`Rollback` deferred-cleanup pattern already used throughout `internal/db` (`defer rows.Close()`, `defer tx.Rollback()`, etc.) — checking the return value of a cleanup call made *after* the operation that actually mattered (the query, the write, the commit) already returned and was checked is a near-universal, low-risk Go idiom that most real-world `errcheck` configs exclude the same way; without it, turning on `golangci-lint` here would fail on pre-existing, harmless findings unrelated to whatever a given PR actually changed. A handful of `#nosec G101`/`#nosec G124` comments in `internal/settings/settings.go`, `internal/handlers/auth.go`, and `internal/auth/service.go` document specific gosec false positives the same way (a settings-table key name and a map of UI strings that only *look* like credentials to a naive string-matcher; and four `http.Cookie` literals gosec's G124 check can't recognize as secure because their `Secure` field is a variable — `s.CookieSecure`/`app.Auth.CookieSecure`, wired from `SESSION_COOKIE_SECURE` — rather than a literal `true`). Three more, added when Web Push notifications first turned on a clean `gosec ./...` gate: `#nosec G115` in `internal/webpush/encrypt.go` (`byte(len(asPub))` — `asPub` is always exactly 65 bytes, an internally-generated `ecdh.P256()` ephemeral public key, never user-controlled, so this can never overflow a byte); `#nosec G201` in `internal/db/push_subscriptions.go` (`ListPushSubscriptionsForUsers`'s `fmt.Sprintf`-built `IN (...)` clause — only the placeholder count is interpolated, every id is still bound as a parameter, the same "variable-length IN clause" idiom the function's own doc comment already explains); and `#nosec G118` in `internal/handlers/push.go`'s `sendToUsers` (the per-subscription cleanup delete deliberately uses its own `subscriptionCleanupTimeout`-bounded `context.Background()`, not the batch's own `ctx`, since that may already be at or past `pushSendTimeout`'s deadline by the time an individual delivery goroutine gets there). Don't add a new blanket exclusion without the same kind of one-line justification these carry; a real finding should get fixed, not silenced.

  **A second report, with actual server logs, pointed at a real bug — but not the endpoint above.** The logs showed `GET /api/v1/lists` and `GET /api/v1/price-alerts` both `403`ing immediately on an ordinary dashboard reload (no `PATCH .../share/pin` anywhere in them), followed a few milliseconds later by `GET /api/v1/houses` `200` and the *same* two endpoints succeeding — a transient race, not a permanent authorization bug, but `loadDashboard()`'s error handling treats a `403` as a genuine failure (unlike a network error) and calls `showError()`, so it briefly flashed the same "not a member of this house" text as a banner right on the dashboard. Root cause: `state.currentHouseId` is only *authoritative* once `loadHouses()` has validated it against a live `GET /api/v1/houses` — before that it can hold whatever `hydrateFromCache()` derived from the IndexedDB mirror (itself possibly stale, e.g. left over from a different account previously signed into the same browser). Several independent triggers can call `loadDashboard()`/`loadNotifications()` — the initial `init()` sequence itself, `i18n.js`'s `trakka:lang-changed` event (dispatched on every `loadLang()` call, **including the very first, page-bootstrap one** — not just a genuine user-initiated switch), the `visibilitychange`/`online` listeners, and a `trakka-sync-complete` message from the service worker — and none of them coordinated with each other about whether `loadHouses()` had actually resolved yet.

(2) The deeper, structural fix: `static/js/app.js` gained `ensureHousesLoaded()` — a promise-memoized gate (`housesLoadedOnce`/`housesLoadingPromise`) that `loadDashboard()` now awaits at its very top, and that `init()` calls instead of `loadHouses()` directly — so `state.currentHouseId` is *guaranteed* validated against the live server before any house-scoped fetch fires, no matter which of the independent triggers calls it first or how they're timed relative to each other. `notifications.js`'s `loadNotifications()` (the other `state.currentHouseId`-scoped loader, called from the same set of triggers) awaits the same gate. `planning.js`/`urgent.js`/`spaces.js`/`shares.js`'s own tab loaders needed no equivalent change: none of them can become the active tab before `restoreLastView()` runs at the tail of `init()`, by which point `ensureHousesLoaded()` has already resolved via `loadDashboard()`'s own call earlier in the same sequence.

- **Fix: `/auth/login`/`/auth/register` rejected with "cross-origin request rejected" in every real browser**: a genuine regression from the security-audit commit (`13cdb01`, 2026-08-30), reported live against a running local instance and root-caused from the browser's own raw request headers rather than guessed at. `requireSameOriginWrite` (`internal/handlers/csrf.go`) rejected any request whose `Origin` header wasn't a real matching host — including the literal string `"null"`, treated identically to an attacker-controlled origin. That's correct for the case it was written for (a sandboxed iframe forging a CSRF POST — an opaque origin, serialized as `"null"`), but incomplete: per the [Fetch spec](https://fetch.spec.whatwg.org/#origin-header)'s Origin-header algorithm, a **navigational** (non-`fetch()`) request — an HTML `<form method="post">` submission — whose page has `Referrer-Policy: no-referrer` in effect *also* serializes `Origin` as `"null"`, even when the request is genuinely same-origin. `SecurityHeaders` (`internal/handlers/middleware.go`) sets `Referrer-Policy: no-referrer` on every response, and `/auth/login`/`/auth/register` (`templates/login.html`) are the *only two* navigational, non-`fetch()` POSTs anywhere in this app — every `/api/v1/...` write goes through `apiRequest()`'s `fetch()`, whose response tainting is always `"cors"`, which the same spec algorithm exempts from the no-referrer nulling (the real `Origin` is always sent for a `fetch()` call regardless of referrer policy). That's exactly why this broke login/register specifically, in literally every standards-compliant browser (reproduced live in Brave, Edge, and a fresh Firefox install — the browser was never the variable), while the rest of the app kept working. Fixed by treating an `Origin` of `""` (absent) or `"null"` identically: both now fall back to the `Sec-Fetch-Site` check instead of rejecting outright. - **Offline sync engine: fixed a "ghost item" bug (a permanently-rejected queued mutation silently discarded, leaving its IndexedDB mirror row orphaned forever) and a header-badge lag when editing an item still awaiting its own offline create**: reported as two symptoms — editing an item made while offline seemed to "erase" its pending-sync indicator, and items left in the local cache without ever reaching the server became invisible to the sync engine, never retried again. The report's own framing (a `static/js/sync.js` file, `_pending`/`client_id` fields, an `offline_sync_queue` store) doesn't match this codebase's actual architecture — there is no `sync.js`; the offline write queue and its replay logic live in `static/sw.js` (`queueOfflineWrite`/`flushQueue`/`resolveAgainstPendingCreate`), backed by `static/js/db.js`'s `STORE_QUEUE`, using `temp-list-*`/`temp-item-*` ids rather than a separate `_pending`/`client_id` pair — but investigating the actual code surfaced two real, confirmed bugs matching the reported symptoms, both in `static/sw.js`.

  **Bug 1 (the header badge, not the data itself)**: `resolveAgainstPendingCreate` — the function that folds an edit to a still-unsynced `temp-item-*`/`temp-list-*` object into its existing queued "create" entry rather than issuing a contradictory request against an id the server has never heard of — correctly preserved the entry's pending status (the DELETE branch already called `broadcastQueueState`, and every response it returns already carries the `X-Trakka-Queued: true` header `apiRequest`'s own per-call `refreshPendingChangeIndicators()` reacts to, so the per-item "⏳ Non synchronisé" dot was never actually wrong), but its non-DELETE (edit) branch never called `broadcastQueueState()` — so the header's own pending-count badge (`#pending-badge`, driven by the service worker's `postMessage`) could lag behind reality after editing a pending item, until some unrelated queue mutation happened to fire it. Fixed by adding the same `broadcastQueueState(false)` call the DELETE branch already had.

  **Bug 2 (the real "ghost" data-loss bug)**: `flushQueue`'s replay loop treated *any* resolved non-401 response as "done" — a genuine `2xx` success and a `404`/`400`/`403`/even a `5xx` server error were all unconditionally `dequeue()`d and counted as synced, with no distinction and no cleanup. For a queued **create** (a `temp-item-*`/`temp-list-*` entry) that the server permanently rejected — e.g. its parent list itself failed to sync first, or a validation error — this silently dropped the one queue entry that would ever have retried it, while leaving the object sitting in the IndexedDB mirror forever: present locally, absent on the server, and never touched again — exactly the "ghost" the report described. Worse, a transient `5xx` (a momentary backend hiccup) was treated identically to success, discarding a perfectly good pending edit that should have been retried. Fixed with `isDefinitiveClientError(status)` (true for 400-499 except 401/408/429 — statuses no amount of identical retrying can ever turn into a success) and `discardRejectedEntry(entry, status, queue)`: a `5xx`/unexpected status now stops the loop and leaves the entry (and everything queued after it) queued for the next attempt, exactly like a network failure already did; a definitive rejection of a still-pending **create** removes the orphaned local object (and, for a list, cascades to cancel any queued item-creates that were waiting on it and deletes their own local rows too — mirroring the cancellation logic `resolveAgainstPendingCreate`'s own DELETE branch already used for an explicit user cancellation); a `404` on an edit/delete of an **already-synced** resource deletes its now-nonexistent local mirror row; and any other definitive rejection of an edit (400/403/409) drops the queued mutation and re-fetches its parent list (`reconcileListFromServer`, reusing the existing `mirrorReadResponse`) to pull the mirror back in line with whatever the server's true state actually is, rather than leaving a change the server never applied silently stuck in the local cache.

  Also added `syncOnStartup()` (`static/js/app.js`, called from `init()` right after `hydrateFromCache()`, fire-and-forget) — waits on `navigator.serviceWorker.ready` and, if online, immediately posts `{ type: 'flush-queue' }` to the active worker, forcing an eager retry of anything still queued from a previous session rather than relying on an incidental fetch or the `online` event to eventually trigger one. This doesn't scan IndexedDB itself (the existing `flushQueue`/`getQueue` already is that scan — there's exactly one queue store, not scattered `_pending` flags to hunt across every item/list row) — it just guarantees that scan-and-retry actually runs promptly at boot instead of only opportunistically.

## Project conventions

Inventory of conventions established while building Trakka, to be followed for any future contribution.

### Backend (Go)

- Standard library only wherever possible: `net/http` (no third-party framework/router), `log/slog` for structured JSON logging, `database/sql` for data access, a hand-rolled OIDC/JWT client (`crypto/rsa`, `crypto/sha256`, `encoding/json`, `net/http`) rather than a third-party OIDC library. The only notable external dependencies are `modernc.org/sqlite`, `golang.org/x/crypto` (bcrypt only), and `golang.org/x/net/html` (used by `internal/scraper` to parse a fetched product page's HTML rather than regex-scraping it) — the two `golang.org/x/...` packages are quasi-stdlib, maintained by the Go team itself, so neither is really a step away from this convention.
- Strict package split (`cmd/server`, `internal/config`, `internal/models`, `internal/db`, `internal/auth`, `internal/handlers`, `internal/validate`) with a hard boundary: `internal/handlers` never imports `database/sql` and only knows about the methods exposed by `*db.DB` and the `db.ErrNotFound` sentinel. `internal/auth` holds non-HTTP auth logic (bcrypt, session tokens, the OIDC client) and is imported by `internal/handlers`, never the reverse.
- Routing via the `mux.HandleFunc("METHOD /path", ...)` syntax from the Go 1.22+ stdlib, never a third-party router (no Gin/chi/etc.).
- All SQL queries are parameterized (`?`), confined to `internal/db`, never built by concatenation/`fmt.Sprintf`.
- Schema versioned through a sequence of numbered migration files (`internal/db/migrations/NNNN_description.sql`), embedded via `//go:embed` and tracked through `PRAGMA user_version` (`internal/db/migrate.go`) — no third-party migration framework, consistent with the stdlib-first convention above; an already-shipped migration file is never edited in place, and a pending migration against an already-versioned database is preceded by an automatic `VACUUM INTO` backup.
- SQLite booleans stored as `0`/`1`, converted to Go `bool` in the `scan*` functions.
- Timestamps in UTC, ISO-8601 with milliseconds; IDs are positive `AUTOINCREMENT` integers.
- Config exclusively via environment variables, loaded once in `internal/config.Load()` — no config file, no CLI flags other than `-healthcheck`.
- Predictable errors handled explicitly (`if err != nil`) everywhere; the `Recover` middleware is a safety net for panics, not a normal error-handling mechanism.
- JSON responses go through centralized helpers (`decodeJSON`/`writeJSON`/`writeError`/`pathID` in `internal/handlers/json.go`) rather than per-handler duplicated code; unknown JSON fields in a request body are rejected (`400`), body capped at 1 MiB.
- `go build`, `go vet ./...`, `gofmt -l .`, and `golangci-lint run ./...` (config: `.golangci.yml`) must stay clean on every change — all four are enforced in CI (see "CI/CD & Sécurité" above).

### Frontend (PWA, `static/`)

- Vanilla ES6+ JavaScript (`async`/`await`), **no dependencies, no build step, no framework**. Several classic `<script>` tags (`app.js`, `list_view.js`, `db.js`) share the same global scope instead of using ES modules — identifiers (`state`, `els`, `apiRequest`, etc.) are therefore shared implicitly across files.
- Every network call goes through the `apiRequest()` helper (never a raw `fetch` elsewhere), which centralizes error handling via an on-page error banner and redirects to `/auth/login` on a `401` (the single choke point that auth-gates the whole SPA). `/auth/...` endpoints (login, register, logout, OIDC) are classic form-`POST`s with full-page redirects instead, served from `templates/login.html` — not part of the `apiRequest()`/JSON world.
- DOM built exclusively via `document.createElement`/`textContent`, **never** `innerHTML` with interpolated data — defense in depth against XSS.
- Any URL rendered as an `<a href>` is re-validated client-side (`http(s)` scheme only) before use, mirroring the server-side validation (`internal/validate.URL`).
- CSS: Tailwind CSS via the "Play" CDN (`https://cdn.tailwindcss.com`), no local Tailwind build; supplemented by a minimum of custom CSS (`static/css/tokens.css` for design tokens, `static/css/base.css`).
- `db.js` never references `window`/`document` (only `indexedDB`/`self`) since it's loaded both as a page script and via the service worker's `importScripts()`.
- The service worker (`sw.js`) is the **sole writer** of the IndexedDB mirror and the offline write queue; `app.js`/`list_view.js` only read (`TrakkaDB.getQueue()`) to display a badge.
- Service worker caches are version-suffixed (`trakka-shell-v1`, etc.) — bump the suffix on every `APP_SHELL` change.
- **UI language: an FR/EN toggle, picked from the "Paramètres" modal, with a server-side per-account default** — `static/js/i18n.js` (loaded before every other page script) resolves the pre-auth first paint from `navigator.language` or a saved `localStorage['trakka:lang']` choice, fetches `static/locales/{fr,en}.json`, and applies it to any element flagged `data-i18n`/`data-i18n-placeholder`/`data-i18n-aria-label`; the interactive picker itself is the `#user-settings-language` `<select>` inside the "Langue" section of `#user-settings-modal` (`static/js/settings.js`, alongside the "Apparence" theme `<select>` — see the "Header cleanup" bullet below for why both moved there from the header). Once `GET /api/v1/me` resolves, `app.js`'s `init()` reconciles the account's own server-side `language` (always `"fr"`/`"en"`, resolved from `models.User.Language`/`internal/handlers.resolveUserLanguage`, defaulting to the instance's `DEFAULT_APP_LANGUAGE` env var — see the Config bullet above — for an account that never set its own preference) against whatever the pre-auth guess already applied, so a brand-new account lands in the instance's configured default language rather than the browser's own. Static markup goes through those `data-i18n*` attributes; dynamic strings built in JS (`app.js`, `list_view.js`, `planning.js`) call `window.TrakkaI18n.t('some.key', vars)` (or the local `t()` wrapper in `app.js`) instead of hard-coding text — as of the "dynamic JS-built strings" fix in the handoff log above, this covers essentially every dynamic string in `app.js`/`list_view.js`/`planning.js` and every other frontend file — `templates/login.html` (French-only, unauthenticated, never loads `i18n.js`) and `i18n.js`'s own hardcoded-French bootstrap fallback object (used only for the brief window before the real `fetch()` resolves, already out of sync with `fr.json` and not worth fully reconciling) remain the two known exceptions. Still, grep for a literal French string before assuming new code is already wired up. Code, comments, and documentation stay in English regardless of UI language.

### Docker / deployment

- Multi-stage build: `golang:X.Y.Z-alpine` (builder, `CGO_ENABLED=0`, static + stripped binary) → `gcr.io/distroless/static-debian12` (runtime — no shell, no package manager). The Dockerfile's Go version, `go.mod`'s `go` directive, and the `modernc.org/sqlite` version must stay in sync (see the Architecture section above); the distroless runtime tag isn't part of that lockstep and should be pinned to a digest for production.
- Prefer a shell-less distroless/Chainguard-style runtime base over a general-purpose one (Alpine, Debian) whenever the compiled artifact is a static binary with no runtime dependency on a package manager or shell — smaller attack surface, no incentive to `apk add`/`apt install` something later. Alpine stays fine for a *builder* stage, which needs a shell/package manager to compile.
- Non-root user with a **fixed numeric UID:GID** (`10001:10001`, via `adduser -u 10001` then `USER 10001:10001`), never a symbolic `USER` — needed for predictable behavior under Podman rootless.
- `compose.yml` must stay valid for both `docker compose` **and** `podman-compose` at once — avoid any Compose field not supported by both.
- Named volumes only (never bind mounts), to avoid UID permission issues under rootless.
- Optional services (e.g. `radicale`) gated behind a Compose profile (`calendar`), never started by default.
- `security_opt: no-new-privileges:true`, no privileged capabilities, no host networking.
- Trakka's own service runs `read_only: true` with `cap_drop: [ALL]`, since a static Go binary talking to SQLite over a local named volume needs to write nowhere but `/data` (and, defensively, `/tmp`) and needs no Linux capability at all. This is specific to `trakka` itself, not a blanket rule for every service in `compose.yml` — a third-party image like `radicale` that wasn't built with a read-only root filesystem in mind is left out of it.
