## PWA / offline design

- **PWA/offline (`static/sw.js`, `static/js/db.js`)**: full design in [docs/PWA.md](../docs/PWA.md) — read it before touching either file. The short version: `db.js` is loaded both as a page `<script>` and via the service worker's `importScripts()`, so it must never reference `window`/`document`, only `indexedDB` and `self`. `sw.js` transparently intercepts every `fetch()` from `app.js`; offline mutations get a temporary `temp-list-*`/`temp-item-*` id and are queued in IndexedDB, and `remapTempId()` patches any still-queued request that depended on one once it gets a real server id. `app.js` also reads (never writes) `TrakkaDB.getQueue()` directly, purely to show the "N en attente" badge — the service worker remains the only writer of the queue/mirror stores; don't add a second writer. Houses get the same read-only mirror (`TrakkaDB.getHouses`/`putHouses`/etc.) but are deliberately **not** offline-writable — creating/renaming/deleting a house while offline returns a `503` rather than being queued, because queueing it would require a second level of temp-id chaining (list → house, on top of the existing item → list) that the offline design explicitly doesn't support; see "Houses are read-mirrored but not offline-writable" in [docs/PWA.md](../docs/PWA.md). Session cookies are ambient/browser-managed, so a queued write replayed later by `flushQueue()` automatically carries whatever cookie is present at replay time — no header snapshotting needed — but `flushQueue()` special-cases a `401` reply (expired session) by leaving the entry queued instead of discarding it like an ordinary rejected `4xx`, so a session expiring mid-queue can't silently drop an offline edit; see "Session expiry vs. the offline queue" in [docs/PWA.md](../docs/PWA.md). `/auth/...` requests bypass the service worker entirely (checked first in the `fetch` handler) — never cache-first-served, never offline-queued. **Service workers require a secure context** (`https://` or exactly `http://localhost`) — they silently don't register anywhere else, which is why `compose.yml` serving plain HTTP is only enough for `localhost` testing (see [docs/DEPLOYMENT.md](../docs/DEPLOYMENT.md)).

A large number of offline-sync bugs and hardening passes (the reorder-queueing fix, the offline sync visual indicators, the "ghost item"/ orphaned-queue-entry fix, the `X-Trakka-Offline` error-banner-suppression fix, the dashboard order/count consistency fix, the `Cache-Control: no-store` hardening, etc.) were each found and fixed through scripted/manual testing across many sessions — the full root-cause account for each lives in [status.md](status.md); skim it before assuming a given offline-edge-case is unhandled.

## Web Push: frontend delivery & routing

The server side (VAPID, encryption, the two notification triggers) is documented in [backend.md](backend.md)'s "Web Push notifications" section. On the client: `static/sw.js`'s `push` listener parses the (already browser-decrypted) JSON payload (`{title, body, url}`) and calls `showNotification`; its `notificationclick` handler closes the notification and either focuses an already-open tab — `postMessage`-ing it `{type: 'trakka-notification-click', url}` rather than relying on the unevenly-supported `WindowClient.navigate()`, handled by `app.js`'s `handleNotificationClickMessage` — or, with no tab open, calls `clients.openWindow(url)`, which lands on a fresh load of the SPA that itself reads the same `?list=` query param at boot (`app.js`'s `handleDeepLinkOrRestore`, spliced into `init()` in place of a bare `restoreLastView()` call: a `?list=` deep link takes priority over the ordinary last-visited-tab/list restore, and is stripped via `history.replaceState` once consumed so a later reload doesn't keep re-triggering it). Server-composed notification text is always French regardless of the recipient's own FR/EN choice — there was originally no per-user language preference stored server-side to localize it with, the same reasoning that leaves `templates/login.html` French-only; the later "Header cleanup" session (see [status.md](status.md)) added a per-account `users.language`, which this notification-composition code has not yet been revisited to use — a known, minor inconsistency.

**Task due dates & reminders**: the create-item form (`#create-item-form`) and the edit-item modal (`#edit-item-modal`) each gained a `data-item-field="due-date"`-gated `<input type="date">` (`#item-due-date`/`#edit-item-due-date`) plus a reminder `<select>` (`#item-reminder`/`#edit-item-reminder`, options "Par défaut"/"Le jour même"/"La veille"/"Personnalisé"/"Désactivé") — shown for `todo`/`recurring_shopping` lists (`FIELD_VISIBILITY_BY_TYPE`'s new `dueDate` flag, `static/js/list_view.js`), the same two types that already show the recurrence control. There was previously no frontend way to set a due date on any item at all, so this is the feature's first UI for it, not just for the reminder layered on top. `reminderSelectionToPayload`/`reminderItemToSelection` (`list_view.js`) convert between the select's value (plus, for "Personnalisé", its own inline offset/time inputs, revealed only then via `updateReminderCustomFieldsVisibility`) and the `reminder_enabled`/`reminder_offset_days`/`reminder_time` API fields (see [backend.md](backend.md)'s "Use case 2" and [docs/API.md](../docs/API.md#reminders)) — "Le jour même"/"La veille" are fixed, no-further-input presets (`(0, "09:00")`/`(1, "20:00")`); "Par défaut" deliberately sends `reminder_offset_days: null, reminder_time: ""` rather than omitting them, the one representation that means "use my current default" under both a POST/PUT full payload and a PATCH's absent/null/value convention. The user's own global default (`reminder_default_offset_days`/`reminder_default_time`, `PATCH /api/v1/me`) is set from a parallel preset select in the "Paramètres" modal (`#user-settings-reminder-preset`, `static/js/settings.js`) — there, unlike the per-item select, the time input stays visible and editable even for the two named presets (only the offset is fixed), since a personal default benefits from being tunable to a preferred hour without dropping into "Personnalisé".

## Security & DOM conventions

- **Frontend DOM**: `static/js/app.js` builds all dynamic content with `textContent`/`createElement`, never `innerHTML` with interpolated data — defense in depth against XSS. Keep that pattern for any new UI code.
- Any URL rendered as an `<a href>` (or `<img src>`) is re-validated client-side (`http(s)` scheme only) before use, mirroring the server-side `internal/validate.URL` check — see [backend.md](backend.md)'s "URLs" security rule.
- This is one item in a larger, non-negotiable list — see [backend.md#security-rules](backend.md#security-rules) for the complete set (SQL, CSRF, SSRF, CSP, response caching, etc.), several of which directly constrain frontend code: in particular, the CSP's `script-src`/`style-src` exceptions exist *only* for the Tailwind Play CDN script — don't add another inline `<script>`/`<style>` tag without revisiting `internal/handlers.SecurityHeaders` first.

## PWA lifecycle & mobile layout rules

These two rules exist because both were violated by real regressions — a stale branch that reintroduced a cluttered per-button header, and a service worker that stopped surfacing new deployments on mobile without a manual cache clear. Preserve both in anything new; don't let either drift back.

1. **Service worker update detection must stay proactive, never passive-only.** Don't rely solely on a browser's own opportunistic check of `sw.js` (which normally only happens on a full page navigation) to notice a new deployment — that's what let updates go unseen for days on a phone left open on its home-screen icon. `static/js/app.js`'s `registerServiceWorker()` keeps the active `registration` around specifically so `checkForServiceWorkerUpdate()` can force a real `registration.update()` from three independent triggers, and all three must keep firing: the `visibilitychange` listener (a backgrounded mobile PWA being resumed), the `focus` listener (desktop alt-tab/multi-window cases `visibilitychange` alone misses), and the `SW_UPDATE_POLL_MS` (15-minute) `setInterval` backstop for a tab that's never backgrounded or refocused at all. `sw.js`'s `install`/`activate` handlers must keep calling `self.skipWaiting()`/`self.clients.claim()` unconditionally (not gated behind a message from the page) — that's what lets the update banner's button (`#update-reload-button`) do a plain `window.location.reload()` and land on the new assets immediately, with no `postMessage` round-trip needed first. Whenever a change touches a cached static asset (`index.html`, any `static/js/*.js`, `static/css/*.css`, a locale JSON file), bump `SHELL_CACHE`/`RUNTIME_CACHE`'s version suffix in `sw.js` — skipping this means `checkForServiceWorkerUpdate()` has nothing new to actually find, and the deployed change silently won't reach anyone already running the app. `/sw.js` is also served with an explicit `Cache-Control: no-cache` response header (`internal/handlers/app.go`) so a browser's own HTTP heuristic caching can never hand `registration.update()`'s byte-comparison a stale copy of `sw.js` itself — see the "Manual 'check for updates' control" entry in [status.md](status.md) for why this was added.
2. **The list detail header stays exactly two rows — never a shelf of individual icon buttons.** Row 1 is back button + the full (truncatable) list title + one `⋮` "Options" button (`#list-options-button` → `#list-options-sheet`). Every list-level action that isn't Trier/Filtres (share, edit, reorder, the compact/detailed view toggle, and anything added later) belongs inside that sheet — never as its own new icon button bolted onto Row 1, since each one narrows the space left for the title until it starts truncating (exactly what happened when per-feature sessions each appended their own button directly to this row instead of extending the sheet). Row 2 is exactly the two actions actually used while browsing a list — Trier (`#sort-items-button` → `#sort-items-sheet`) and Filtres (`#filter-items-button` → `#filter-items-sheet`) — as labeled pill buttons, not bare icons, so they read clearly before a user has learned this app's iconography. Before adding any new list-level action, put it in `#list-options-sheet` (or, only if it's used as often as sort/filter, make the case for promoting it to its own Row 2 pill) rather than adding a seventh button to Row 1.

## Conventions

### Frontend (PWA, `static/`)

- Vanilla ES6+ JavaScript (`async`/`await`), **no dependencies, no build step, no framework**. Several classic `<script>` tags (`app.js`, `list_view.js`, `db.js`) share the same global scope instead of using ES modules — identifiers (`state`, `els`, `apiRequest`, etc.) are therefore shared implicitly across files.
- Every network call goes through the `apiRequest()` helper (never a raw `fetch` elsewhere), which centralizes error handling via an on-page error banner and redirects to `/auth/login` on a `401` (the single choke point that auth-gates the whole SPA). `/auth/...` endpoints (login, register, logout, OIDC) are classic form-`POST`s with full-page redirects instead, served from `templates/login.html` — not part of the `apiRequest()`/JSON world.
- DOM built exclusively via `document.createElement`/`textContent`, **never** `innerHTML` with interpolated data — defense in depth against XSS.
- Any URL rendered as an `<a href>` is re-validated client-side (`http(s)` scheme only) before use, mirroring the server-side validation (`internal/validate.URL`).
- CSS: Tailwind CSS via the "Play" CDN (`https://cdn.tailwindcss.com`), no local Tailwind build; supplemented by a minimum of custom CSS (`static/css/tokens.css` for design tokens, `static/css/base.css`).
- `db.js` never references `window`/`document` (only `indexedDB`/`self`) since it's loaded both as a page script and via the service worker's `importScripts()`.
- The service worker (`sw.js`) is the **sole writer** of the IndexedDB mirror and the offline write queue; `app.js`/`list_view.js` only read (`TrakkaDB.getQueue()`) to display a badge.
- Service worker caches are version-suffixed (`trakka-shell-v1`, etc.) — bump the suffix on every `APP_SHELL` change.
- **UI language: an FR/EN toggle, picked from the "Paramètres" modal, with a server-side per-account default** — `static/js/i18n.js` (loaded before every other page script) resolves the pre-auth first paint from `navigator.language` or a saved `localStorage['trakka:lang']` choice, fetches `static/locales/{fr,en}.json`, and applies it to any element flagged `data-i18n`/`data-i18n-placeholder`/`data-i18n-aria-label`; the interactive picker itself is the `#user-settings-language` `<select>` inside the "Langue" section of `#user-settings-modal` (`static/js/settings.js`, alongside the "Apparence" theme `<select>` — see the "Header cleanup" entry in [status.md](status.md) for why both moved there from the header). Once `GET /api/v1/me` resolves, `app.js`'s `init()` reconciles the account's own server-side `language` (always `"fr"`/`"en"`, resolved from `models.User.Language`/`internal/handlers.resolveUserLanguage`, defaulting to the instance's `DEFAULT_APP_LANGUAGE` env var — see [architecture.md](architecture.md)'s Config section — for an account that never set its own preference) against whatever the pre-auth guess already applied, so a brand-new account lands in the instance's configured default language rather than the browser's own. Static markup goes through those `data-i18n*` attributes; dynamic strings built in JS (`app.js`, `list_view.js`, `planning.js`) call `window.TrakkaI18n.t('some.key', vars)` (or the local `t()` wrapper in `app.js`) instead of hard-coding text — as of the "dynamic JS-built strings" fix (see [status.md](status.md)), this covers essentially every dynamic string in `app.js`/`list_view.js`/`planning.js` and every other frontend file — `templates/login.html` (French-only, unauthenticated, never loads `i18n.js`) and `i18n.js`'s own hardcoded-French bootstrap fallback object (used only for the brief window before the real `fetch()` resolves, already out of sync with `fr.json` and not worth fully reconciling) remain the two known exceptions. Still, grep for a literal French string before assuming new code is already wired up. Code, comments, and documentation stay in English regardless of UI language.

The Light/Dark/Auto theme system (`data-theme` attribute on `<html>`, `theme-init.js`/`theme.js`/`tailwind-config.js`, the same "Paramètres" modal picker as language) is documented in the "Light/dark theme" and "Header cleanup" entries in [status.md](status.md).
