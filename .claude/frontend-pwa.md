## PWA / offline design

- **PWA/offline (`static/sw.js`, `static/js/db.js`)**: full design in [docs/PWA.md](../docs/PWA.md) — read it before touching either file. The short version: `db.js` is loaded both as a page `<script>` and via the service worker's `importScripts()`, so it must never reference `window`/`document`, only `indexedDB` and `self`. `sw.js` transparently intercepts every `fetch()` from `app.js`; offline mutations get a temporary `temp-list-*`/`temp-item-*` id and are queued in IndexedDB, and `remapTempId()` patches any still-queued request that depended on one once it gets a real server id. `app.js` also reads (never writes) `TrakkaDB.getQueue()` directly, purely to show the "N en attente" badge — the service worker remains the only writer of the queue/mirror stores; don't add a second writer. Houses get the same read-only mirror (`TrakkaDB.getHouses`/`putHouses`/etc.) but are deliberately **not** offline-writable — creating/renaming/deleting a house while offline returns a `503` rather than being queued, because queueing it would require a second level of temp-id chaining (list → house, on top of the existing item → list) that the offline design explicitly doesn't support; see "Houses are read-mirrored but not offline-writable" in [docs/PWA.md](../docs/PWA.md). Session cookies are ambient/browser-managed, so a queued write replayed later by `flushQueue()` automatically carries whatever cookie is present at replay time — no header snapshotting needed — but `flushQueue()` special-cases a `401` reply (expired session) by leaving the entry queued instead of discarding it like an ordinary rejected `4xx`, so a session expiring mid-queue can't silently drop an offline edit; see "Session expiry vs. the offline queue" in [docs/PWA.md](../docs/PWA.md). `/auth/...` requests bypass the service worker entirely (checked first in the `fetch` handler) — never cache-first-served, never offline-queued. **Service workers require a secure context** (`https://` or exactly `http://localhost`) — they silently don't register anywhere else, which is why `compose.yml` serving plain HTTP is only enough for `localhost` testing (see [docs/DEPLOYMENT.md](../docs/DEPLOYMENT.md)).

A large number of offline-sync bugs and hardening passes (the reorder-queueing fix, the offline sync visual indicators, the "ghost item"/ orphaned-queue-entry fix, the `X-Trakka-Offline` error-banner-suppression fix, the dashboard order/count consistency fix, the `Cache-Control: no-store` hardening, etc.) were each found and fixed through scripted/manual testing across many sessions — the full root-cause account for each lives in [status.md](status.md); skim it before assuming a given offline-edge-case is unhandled.

## Web Push: frontend delivery & routing

The server side (VAPID, encryption, the two notification triggers) is documented in [backend.md](backend.md)'s "Web Push notifications" section. On the client: `static/sw.js`'s `push` listener parses the (already browser-decrypted) JSON payload (`{title, body, url, tag?, vibrate?}`) and calls `showNotification` — `silent: true`, unless the payload carries a `vibrate` pattern (the server adds one only for recipients with `users.vibrate_on_notification` on; a service worker can't read `localStorage`, so the preference is applied server-side), in which case it passes `vibrate` with `silent: false`, since the spec makes `showNotification` throw a `TypeError` for both together; its `notificationclick` handler closes the notification and either focuses an already-open tab — `postMessage`-ing it `{type: 'trakka-notification-click', url}` rather than relying on the unevenly-supported `WindowClient.navigate()`, handled by `app.js`'s `handleNotificationClickMessage` — or, with no tab open, calls `clients.openWindow(url)`, which lands on a fresh load of the SPA that itself reads the same `?list=` query param at boot (`app.js`'s `handleDeepLinkOrRestore`, spliced into `init()` in place of a bare `restoreLastView()` call: a `?list=` deep link takes priority over the ordinary last-visited-tab/list restore, and is stripped via `history.replaceState` once consumed so a later reload doesn't keep re-triggering it). Server-composed notification text is always French regardless of the recipient's own FR/EN choice — there was originally no per-user language preference stored server-side to localize it with, the same reasoning that leaves `templates/login.html` French-only; the later "Header cleanup" session (see [status.md](status.md)) added a per-account `users.language`, which this notification-composition code has not yet been revisited to use — a known, minor inconsistency.

**Task due dates & reminders**: the create-item form (`#create-item-form`) and the edit-item modal (`#edit-item-modal`) each gained a `data-item-field="due-date"`-gated `<input type="date">` (`#item-due-date`/`#edit-item-due-date`) plus a reminder `<select>` (`#item-reminder`/`#edit-item-reminder`, options "Par défaut"/"Le jour même"/"La veille"/"Personnalisé"/"Désactivé") — shown for `todo`/`recurring_shopping` lists (`FIELD_VISIBILITY_BY_TYPE`'s new `dueDate` flag, `static/js/list_view.js`), the same two types that already show the recurrence control. There was previously no frontend way to set a due date on any item at all, so this is the feature's first UI for it, not just for the reminder layered on top. `reminderSelectionToPayload`/`reminderItemToSelection` (`list_view.js`) convert between the select's value (plus, for "Personnalisé", its own inline offset/time inputs, revealed only then via `updateReminderCustomFieldsVisibility`) and the `reminder_enabled`/`reminder_offset_days`/`reminder_time` API fields (see [backend.md](backend.md)'s "Use case 2" and [docs/API.md](../docs/API.md#reminders)) — "Le jour même"/"La veille" are fixed, no-further-input presets (`(0, "09:00")`/`(1, "20:00")`); "Par défaut" deliberately sends `reminder_offset_days: null, reminder_time: ""` rather than omitting them, the one representation that means "use my current default" under both a POST/PUT full payload and a PATCH's absent/null/value convention. The user's own global default (`reminder_default_offset_days`/`reminder_default_time`, `PATCH /api/v1/me`) is set from a parallel preset select in the "Paramètres" modal (`#user-settings-reminder-preset`, `static/js/settings.js`) — there, unlike the per-item select, the time input stays visible and editable even for the two named presets (only the offset is fixed), since a personal default benefits from being tunable to a preferred hour without dropping into "Personnalisé".

**Scheduling UI (due time, custom recurrence, next-occurrence badge)**: both forms gained a `type="time"` input next to the due date (`#item-due-time`/`#edit-item-due-time`, cleared with the date since the server refuses a time on its own) and a row of one-tap shortcut chips ("Aujourd'hui"/"Demain"/"Dans une semaine") — any `[data-due-shortcuts="<input id>"]` container is wired by one delegated click listener in `list_view.js`, so new groups need no JS. The recurrence `<select>`'s fixed options carry canonical RRULE values (`FREQ=WEEKLY`…); "Personnalisée…" opens the custom recurrence sheet described below, and the reminder `<select>` gained "à l'heure de l'échéance" (`reminder_at_due_time`). In the edit modal the due date now comes first, then recurrence, then reminder. The quick-add bar's main row has a 📅 pill (`#quick-add-schedule-pill`, `data-item-field="due-date"`) — the "déclencheur rapide": it opens the advanced panel on the due date (calling `showPicker()` where allowed) and, once something is set, summarizes it (`updateQuickAddSchedulePill`: date only plus 🔁, since it shares the bar with the title input on a phone). A recurring item's row shows `buildNextDueBadge` under its title — "🔁 Échéance suivante : dim. 11 oct. à 18:00" (`formatDueLabel`: "aujourd'hui"/"demain" against `TrakkaRecurrence.localDateISO()`, the device's own day, else `Intl` short weekday/day/month, year only when different — through one cached `Intl.DateTimeFormat` per locale/year display, since it runs for every recurring row on every render; `intlLocale()` is the shared UI-language → `Intl` locale mapping, also used by `planning.js`'s `monthLabel`) — for an active item its own `due_date`, for a done one its `next_due_date` (or `computeNextDueDate` before the server copy lands); an active one without a date shows its cadence, a finished series shows nothing, and **an item without a recurrence rule never gets it**. The title and badge share a `flex-col` block taking the title's `flex-1 min-w-0` slot in `rowTop`; the badge wraps (`rounded-lg`) rather than truncating, because a phone-width task row is narrower than the full label. Outside multi-select it's a button opening the edit modal focused on the due date (`openEditItemModal(item, { focus: 'due-date' })`). The actions sheet meta shows the due date/time, cadence, next occurrence (done items) and "🔔 Rappel envoyé le …" (`notification_sent_at`). `toggleDone` and `selection.js`'s `bulkToggleDone` set `done`/`next_due_date` optimistically through the shared `setItemDoneOptimistic` and restore them on undo/failure; `updateQuickAddSchedulePill`/`updateRecurrenceSummary` run on every `renderItems`, so they write text through `setTextIfChanged` and leave the DOM untouched when nothing changed; server responses are merged through `mergeServerItem`, which nulls the schedule fields the Go `omitempty` response left out — a plain `Object.assign` kept a stale `next_due_date` after un-checking. The settings modal groups the push toggle and the reminder default under "🔔 Notifications de tâches" (since the notification-preferences sessions also a **"Types de notifications" matrix** between the vibration row and "Moment du rappel": a bordered `role="group"` of five rows, each a label/hint plus a real switch — an `sr-only` `peer` checkbox with `role="switch"` and a Tailwind track whose `after:` thumb moves with `peer-checked:` (keyboard focus ring via `peer-focus-visible:`) — `#user-settings-reminders-enabled`, `#user-settings-overdue-summary` (whose `#user-settings-overdue-summary-time` row only shows while it's on), `#user-settings-collaborator-actions`, `#user-settings-item-additions`, `#user-settings-list-sharing`; account-wide, saved with the form as `reminders_enabled`/`overdue_tasks_summary_enabled`/`overdue_tasks_summary_time`/`collaborator_actions_enabled`/`item_additions_enabled`/`list_sharing_enabled`; see [backend.md](backend.md#web-push-notifications). In the Android app only the first two have an effect (local notifications); the others are pushes. The form's submit now keeps `state.currentUser` when the PATCH comes back as sw.js's offline `{queued: true}` placeholder, merging what was saved into it, as the language picker already did) (the toggle still applies immediately; only the reminder default is saved by the form), with a fourth preset "À l'heure exacte de l'échéance" whose time input becomes the no-due-time fallback (`#user-settings-reminder-fallback-hint`); presets are now matched by offset alone (`reminderDefaultsToPreset`), since the time is editable under each. `planning.js` projects a done recurring item from its `next_due_date` (the completed occurrence is paid) and nothing for a finished series.

**Custom recurrence sheet** (`#recurrence-editor-sheet`, `static/js/recurrence-editor.js`): picking "Personnalisée…" in either recurrence select — or tapping the rule summary button shown under it once one is applied (`#item-recurrence-summary`/`#edit-item-recurrence-summary`, `updateRecurrenceSummary`) — opens "Répétition personnalisée": a frequency radiogroup (Quotidienne/Hebdomadaire/Mensuelle/Annuelle, 2×2 below `sm`, arrow keys move the choice), an interval with −/+ steppers and a pluralized unit, round 44px L M M J V S D weekday toggles (weekly only, multi-select; the start date's weekday is preselected, and "OK" stays disabled with a hint while none is picked), a "Date de début", and a live summary ("Toutes les 2 semaines le lun., mer., ven." / "Première échéance : ven. 2 oct."). All rule parsing, labels (`recurrenceBadgeLabel`: "Du lundi au vendredi", "Chaque semaine le lun., mer., ven.", "Tous les 2 ans"…) and occurrence arithmetic go through `static/js/recurrence.js`, which `sw.js` also loads via `importScripts` (both files are in `APP_SHELL`). Weekday names/initials are i18n keys (`items.weekday{Initial,Short,Long}{MO..SU}`), sheet strings are under `recurrenceEditor.*`.

## Admin console: encrypted backups tab

The "Sauvegardes" tab (`#admin-tab-backups`/`#admin-panel-backups`, the backups section at the end of `static/js/admin.js`) is the UI for [backend.md](backend.md#encrypted-webdav-backups)'s encrypted WebDAV backups. Things that differ from the other admin tabs:

- **Service-worker bypass**: `static/sw.js`'s `fetch` listener returns early (no `respondWith`) for every non-`GET` `/api/v1/admin/backups...` request, *before* the API routing. `handleApiWrite` would otherwise `request.clone().text()` the whole body to be able to queue it — a restore uploads an entire encrypted database as `multipart/form-data` — and none of these actions may ever be queued and replayed later. Offline they simply reject, and `admin.js` shows `common.networkError` inline. `GET`s (status, remote list) still take the normal network-first path. Keep this bypass above the `flushQueue()`/API branches if you touch the listener.
- **Multipart through `apiRequest`**: the restore passes `headers: {}` so the spread replaces `apiRequest`'s JSON `Content-Type` and the browser sets the multipart boundary itself. `apiRequest` also now copies a response body's `code` onto the thrown error (`err.code`); the backups tab maps codes to `modals.adminConsole.backups.errors.*` (`backupReason`), falling back to the raw message.
- **Non-blocking alerts**: `refreshBackupAlertIndicators()` (called un-awaited from `app.js`'s `init()` after `refreshAdminConsoleButtonVisibility()`, and whenever the console opens) reads the local-only status endpoint for admins and toggles three purely visual markers — `#user-settings-alert-dot` on the header gear (the button gained `relative`), `#admin-console-alert` (⚠️, `role="img"` with a translated `aria-label`) on the console button, `#admin-tab-backups-alert` on the tab. The explanations render inline at the top of the tab (`#admin-backups-alerts`). Per the spec, never a popup or a banner.
- **Status polling**: after "Sauvegarder maintenant" (`202`), `scheduleBackupPoll` re-reads the status every 2 s while `running` is set, and stops by itself once the modal closes or another tab is selected.
- **Key download** is built client-side (`Blob` + object URL + `a[download]`) from the `POST /key/export` response, so the key never appears in a URL, history or access log; "Copier la clé" uses `navigator.clipboard` with a fallback message.
- **Restore** uses the same "click again to confirm" pattern as `buildConfirmableDeleteButton` (no `confirm()`), then reloads `/` after success, since the restored database's sessions replace the current ones.
- **Narrow screens**: the console's tab strip wraps (`flex-wrap`) instead of scrolling sideways, so "Sauvegardes" and its alert dot are always visible; the dialog is `max-w-full sm:max-w-2xl min-w-0` and its body `overflow-x-hidden`; and a zero-specificity `:where(#admin-panel-backups) …` block in `base.css` caps every control/text block at the panel width, with `overflow-wrap: anywhere` so long URLs/paths/file names in errors wrap instead of widening the column.
- Verified functionally in a real headless Firefox, and for layout under Chromium mobile emulation at 320–412 px (see the "Encrypted WebDAV backups" and "Fix: sideways panning on phones" entries in [status.md](status.md)).

## Multi-select mode (bulk actions)

`static/js/selection.js` (loaded right after `reorder.js`). Things to keep in mind when touching it or the list view:

- **Entry points**: `#select-items-button` in `#list-options-sheet` (+ `#select-items-button-desktop` in `#list-desktop-actions`), and a long press anywhere on an item card except the 🔗 icon (`attachLongPress(li, …, { ignoreSelector: 'a[href]' })` at the end of `buildItemRow`). Selection and reorder mode are mutually exclusive; `selectList`/`showDashboard` exit it; Escape exits it only when no overlay is open (a capture-phase listener checks `OVERLAY_SELECTOR` before the overlays' own handlers close them).
- **Rendering**: `renderItems` keeps its normal active/done path. `buildItemRow` reads `isSelectionModeActive()` and builds a selection checkbox instead of the done checkbox/line marker, leaves out the ✏️/🗑️/⋮ actions, the title's tap handler and every long press, and skips `attachItemSwipeGestures`; `decorateSelectableRow` then makes every other control `inert` so a tap falls through to the card. Toggling repaints only that row and the bar (keyboard focus survives). `syncSelectionWithRender(active, done)` at the end of `renderItems` prunes the selection to rendered rows and shows/hides the bar. Selection is keyed by `String(item.id)` so it survives `refreshCurrentList` replacing every item object; `local-*` optimistic items aren't selectable yet.
- **An emptied selection exits the mode**: deselecting the last row (tap or checkbox), "Tout désélectionner", or a render pruning the last selected row away all call `exitSelectionMode()` instead of parking the bar on "Aucune sélection". Only a selection that *becomes* empty exits — entering through the "Sélectionner" button legitimately starts at 0 and stays in the mode. The pruning case exits from inside `syncSelectionWithRender`, i.e. mid-`renderItems`; the nested `renderItems` it triggers lands in the `!selectionMode` early return, so it can't loop. The bar is only ever hidden via the `hidden` attribute, which base.css forces to `display: none !important`, so a hidden bar leaves no invisible tap target over the bottom of the list.
- **No bulk endpoint, on purpose**: each item gets its own `PATCH`/`DELETE /api/v1/items/{id}` via `runWithConcurrency(…, BULK_REQUEST_CONCURRENCY)` after an optimistic update — so `sw.js` queues, mirrors and temp-id-resolves each one offline with no change on its side. `commitItemPatches` (list_view.js) is the shared optimistic-PATCH-with-per-item-rollback helper (labels, target month); bulk check/uncheck and delete each use one undo toast, and bulk check tags its `pendingToggles` entries with a batch symbol so a later single toggle/delete of one item takes that item over without cancelling the batch.
- **Label sheet**: `labelManageItems` is always an array (a single item is `[item]`); a label on only some of the items shows as a partial chip (`aria-pressed="mixed"`, "label · 2/5") and a tap adds it to the rest.
- **Layout**: `#bulk-actions-bar` is fixed at every width and replaces `#create-item-form-anchor`; `#items-section.is-selecting` adds matching bottom padding; `#toast-container`'s `bottom` is set to the bar's height while it's shown so undo toasts don't cover it. `#bulk-actions-bar` is excluded from the edge swipe-back gesture like the quick-add bar.

## Long press (touch)

- **One helper**: `attachLongPress` (list_view.js) — 500 ms hold, cancelled by a >10 px move or an early lift; prevents `contextmenu` (Android's native menu) while the gesture is live. Touch-only by construction (no `touchstart` from a mouse). Used on an item card (enters multi-select), its 🔗 icon (link actions), and every dashboard/Espaces/"Partagé avec moi" list card (`buildListCard`, opens `#list-card-actions-sheet`).
- **The click after the lift is swallowed globally, not just on the element**: Android Chrome still emits a `click` on release once `contextmenu` was prevented (preventing `touchend` doesn't stop it), and it's hit-tested where the finger is *then* — the backdrop of the sheet the long press just opened (which closed it instantly), or the re-rendered selection-mode row (which deselected the pressed item). `armLongPressClickGuard` adds a capture-phase `click` listener on `window` when the long press fires; it swallows one click and is removed by that click, by the next `touchstart`, or `LONG_PRESS_CLICK_GUARD_MS` (400 ms) after the lift. Headless Chromium emits no such click, so a test has to dispatch one at the finger's position itself; and a test that `.click()`s a sheet button right after the lift without a touch in between gets swallowed by the guard.
- **`#list-card-actions-sheet` mirrors the card's buttons**: Modifier/Partager/Supprimer for a list of the caller's own House, only Épingler/Retirer for a shared one (`list.access_source` set). Each entry closes the sheet, then calls the same handler as the card's inline button.
- **`.long-press-target` (base.css) blocks native selection/callout** (`user-select: none`, `-webkit-touch-callout: none` — iOS never fires `contextmenu`). It goes on every long-press element on touch devices (`IS_TOUCH_DEVICE`), and on **every** item row, including selection-mode rows: entering selection mode re-renders the list while the finger is still down, so the OS's own long-press selection lands on the *new* row. Inputs/textareas inside a target are reset to `user-select: text` (iOS won't let you type in a field whose computed `-webkit-user-select` is `none`).

## Emoji picker (list icon)

`static/js/emoji-picker.js` (loaded right after `undo.js`) drives `#emoji-picker-sheet` and exposes `window.TrakkaEmojiPicker.open({ onSelect, returnFocus })`. The new/edit list modal opens it from `#list-icon-picker-button`; `#list-icon` stays a free-text field (current-icon preview + paste anything), `#list-icon-clear-button` empties it, and the field's placeholder is the selected type's default icon (`setListTypeSelection`, app.js). The space modal still uses its fixed preset buttons. Things to keep in mind:

- **Data**: `static/emoji/{fr,en}.json`, generated by `go run tools/genemoji/main.go` from a pinned emojibase-data release (CLDR labels/keywords; the entry format is documented in that file). Fetched on first open in the current UI language, built into buttons once per language (`trakka:lang-changed` forces a rebuild on the next open). Both files and the script are in `APP_SHELL`, so the picker works offline. When regenerating, bump the SW cache version.
- **Font support**: `detectSupport` probes one emoji per Emoji version on a 1×1 canvas (a color glyph ignores `fillStyle`; a missing glyph follows it; an unsupported ZWJ sequence is too wide) and hides versions the device can't draw, plus the Flags category on Windows. If the canvas can't be read (anti-fingerprinting), nothing is filtered. `EMOJI_FONT` must match `.emoji-picker-cell`'s font stack in `base.css`.
- **Skin tones**: one tone flag per emoji instead of shipping every variant; `applyTone` (JS) mirrors the generator's `applyTone` (Go), which only emits a rule it has checked against the real variants. Couples whose two people can differ get no flag (they can still be pasted).
- **Layout**: bottom sheet under `sm`, centered dialog above. The panel height is `min(34rem, 85dvh)` and only `#emoji-picker-scroller` scrolls. The ten category tabs share one row (`flex: 1`), which fits at 320 px, and the grid is `auto-fill` 44 px cells. On touch devices the search field is not auto-focused, so the keyboard doesn't cover the grid.
- **Stacking**: z-50 above the z-40 list modal. Its Escape listener is on `window` in the capture phase and stops propagation, so Escape closes only the picker (after first clearing a non-empty search). System back and the edge back-swipe (`gestures.js`) close only the picker, leaving the list modal open (see "System back (history entries)" below).
- **Recents and tone** live in `localStorage` (`trakka:emoji-recents`, `trakka:emoji-tone`), wrapped in try/catch: they're conveniences that are simply not remembered when storage is blocked.
- **Icon length**: `#list-icon`'s `maxlength="32"` counts UTF-16 units, so it can never exceed the server's 32-code-point `validate.MaxIconLen`, while the longest emoji sequences need about 15. The old `maxlength="8"` was the only thing that blocked ZWJ families and toned couples; the backend never did (`internal/validate/text_test.go`, `internal/handlers/lists_icon_test.go`).

## System back (history entries)

Section 3 of `static/js/gestures.js`. Android's back action (the gesture-navigation edge swipe or the back button) pops a browser history entry, and an installed PWA with none of its own is closed by the system. Things to keep in mind:

- **One entry per open level**: the list detail view (`#items-section`) and each open overlay (`OVERLAY_SELECTOR`) above it get their own same-URL entry, whose state records its depth (`trakkaDepth`). At startup, the entry the page loaded on is anchored at depth 0 (`replaceState`). After a reload, the entries below it belong to the previous document, and going back to them reloads the page instead of firing `popstate`, so they are never counted. System back pops one entry, and `popstate` closes levels (`goBack()`) until the UI is no deeper than the entry it landed on. Closing levels any other way (✕, Cancel, Escape, the header back button) drops the extra entries with `history.go(-n)` in a `setTimeout(0)`, so a close followed by an open (a sheet handing off to a modal) reuses the entry instead.
- **Chrome's history manipulation intervention dictates the design** ([Chromium doc](https://chromium.googlesource.com/chromium/src/+/main/docs/history_manipulation_intervention.md)). A `pushState` without an honored user activation marks *every* entry of the document as skipped by the back button, so the next back leaves the app. After a back/forward, earlier activation no longer counts until a new one. So **nothing is ever pushed in response to a back**, and pushes wait for an activation-triggering event (`activationHonored`, set from capture-phase `pointerup`/`touchend`/`keydown`/`mousedown` listeners when `navigator.userActivation.isActive`, cleared on every `popstate`). The first version of this fix kept a single guard entry and re-pushed it from `popstate`: on a real Android phone the second back closed the app.
- **Consequence**: a list reopened at boot by `restoreLastView` has no entry until the first tap, so a back before any interaction still exits the app. A push can't fix that without making everything skippable.
- **No open/close function knows about it**: a `MutationObserver` on the `hidden` attribute of every `[id$="-modal"]`, `[id$="-sheet"]` and `#items-section` calls `syncHistory()`. A new overlay is covered if it follows that id convention and closes on a backdrop click (the same contract the edge swipe relies on). One that is created dynamically would also have to be observed.
- **One level per back**: `goBack()` closes the most recently opened overlay (`openOverlays`, open order kept by `refreshOpenOverlays()`, since the DOM doesn't reveal stacking), else leaves the list. The in-app edge swipe calls `requestBack()`, which goes through `history.back()` when the history and the UI are in step.
- **Testing**: Playwright's `page.goBack()` is not subject to the intervention (and CDP key events never reach Chrome's own Alt+Left), which is why the first version passed its tests. A test has to model the rule: wrap `pushState` in an init script and track honored activation and skippable entries per the doc above. A "system back" then leaves the app when every entry is skippable.
- **Other history writes** must keep `history.state` (as `handleDeepLinkOrRestore` does when it strips `?list=`), or they erase the depth marker.
- Not covered: reorder and multi-select modes are not back levels of their own, so back from either leaves the list, as the header back button does.

## Item filters & the budget summary

The Filtres sheet (`#filter-items-sheet`) is client-side only and per list (`trakka:filters:<listId>` in `localStorage`); `renderItems` (list_view.js) applies it. Things to keep in mind:

- **The budget summary follows the filters.** When `isFilterStateActive` is true, `renderItems` passes `updateFinanceSummary` exactly the rendered items (`[...active, ...done]`, i.e. after the status filter too, so "Restant" shows 0 € spent and "Acheté" 0 € remaining); with no filter it gets the whole list. A new filter category must be added to `isFilterStateActive`/`countActiveFilters`, or the summary will silently show a filtered total as if it were the whole list's.
- **The "filtered" indication**: `#finance-filtered-badge` (sky funnel pill, word `items.financeFilteredBadge` sr-only) *replaces* the 📊 icon (`#finance-summary-icon`) instead of sitting next to it, so the summary row keeps its width and the collapsed compact figures still fit at 320 px. The spelled-out warning is `#finance-filtered-note` in the expanded body (`items.financeFilteredNoteOne/Other`, "Calculé uniquement sur les N articles filtrés sur M").

## Inside the Android app (Capacitor)

The Android app (`android/`, [docs/MOBILE_BUILD.md](../docs/MOBILE_BUILD.md)) loads this PWA straight from the server in its own WebView, and its Capacitor bridge injects `window.Capacitor` into the server's pages. The PWA has three integration points with it (the third, task reminders, is the next paragraph). The sign-in page loads `static/js/login.js`: when `TrakkaApp` exists, the SSO button (`#oidc-login-link` in `templates/login.html`) calls `TrakkaApp.signInWithBrowser()`, which runs the OIDC flow in a Custom Tab and brings the session back into the WebView (why and how: [backend.md](backend.md#authentication--authorization), `internal/handlers/oidc_app.go`), and falls back to following the link if the call is rejected (no browser); an app without that method leaves the link alone (`typeof` check: the bridge exposes a native plugin as a plain object holding only its real methods, so calling a missing one throws synchronously). The other is in `static/js/settings.js`: when `window.Capacitor.Plugins.TrakkaApp` exists, `refreshAndroidAppSection()` (called each time the Paramètres modal opens) shows `#user-settings-android-app`, "Serveur de l'application", with the server and app version from `TrakkaApp.getServer()` and a "Changer de serveur" button calling `TrakkaApp.changeServer()` (the app then shows its own connect screen), and hides the browser installation help (`#install-help-button`). In a browser the plugin doesn't exist and nothing changes. The native side refuses every other `TrakkaApp` method to the server's pages, so the PWA cannot switch the app to another server. Keep any further app-specific behavior behind the same feature test, never user-agent sniffing (the app's WebView does append `TrakkaAndroid` to it, for server logs only).

**Task reminders in the app** (`static/js/local-reminders.js`, loaded after push.js, added to `APP_SHELL`): the WebView has no Web Push, so when Capacitor's `LocalNotifications` plugin is on the bridge (`localNotificationsPlugin()`; an app built with `@capacitor/local-notifications`), the Paramètres switch becomes "Rappels locaux (mode hors-ligne supporté)" (`#user-settings-local-reminders-label`/`-hint` swapped in by push.js's `showLocalRemindersTexts`; on/off per phone in `localStorage['trakka:localReminders']`, turning on calls `requestPermissions`), and the vibration row stays shown: it picks the Android channel (`trakka_reminders` or `trakka_reminders_quiet`, created natively by `ReminderChannels.java`, since a channel's vibration is fixed once created). `syncLocalReminders` replaces the whole schedule with `GET /api/v1/reminders/upcoming` (server-computed `remind_at`, push's text; see [backend.md](backend.md#web-push-notifications)) and keeps a copy in `localStorage['trakka:localRemindersScheduled']` — the plugin's `getPending` returns neither the channel nor a parseable date. It runs from `startLocalReminders()` (end of app.js's `init`), debounced after writes, on `trakka:sync-complete`, `online`, and on foreground at most once a minute; it never runs offline, and ignores `X-Trakka-Offline` answers. `apiRequest` calls `noteLocalReminderWrite(method, path, body)` after every write (queued offline or not): `done: true` or `DELETE /items/{id}` (and `DELETE /lists/{id}`, matched through the scheduled copy's `list_id`) cancel at once and record a per-occurrence suppression (`trakka:localRemindersSuppressed`, keyed by item, matched on `remind_at`, so a recurring task's next occurrence isn't blocked) that survives syncs racing the offline queue until the server stops returning that occurrence (7-day expiry); `done: false` restores it from the copy. Tapping a notification goes through `handleNotificationClickMessage` (the plugin retains a cold-start tap until the listener exists). **Notification preferences**: the server applies `reminders_enabled`/`overdue_tasks_summary_enabled` to what `/reminders/upcoming` returns, and `noteLocalReminderWrite` on `PATCH /me` (`applyNotificationPreferences`) cancels at once whatever a type switched off had scheduled. The response's `overdue_summary` (the next daily summary, or null) is scheduled under the fixed id `OVERDUE_SUMMARY_NOTIFICATION_ID` (2000000000; reminders use their item id) and copied to `localStorage['trakka:localOverdueSummaryScheduled']` as `{summary, done}`: checking off / deleting a task in its `item_ids` adds it to `done` (`markOverdueSummaryTasks`), which cancels the summary once none is left, and `done: false` brings it back; `done` survives a sync for the same `remind_at`, against the offline-queue race. Its text stays the server's until the next sync. In a browser `localNotificationsPlugin()` is null and none of this runs (checked: no request to `/reminders/upcoming`).

In the app's WebView, `PushManager` and `Notification` don't exist (Android's WebView has no Web Push): in an app built without the plugin, `refreshPushToggleUI` (push.js) reports push as unsupported there, with its own message when `androidAppPlugin()` finds the app (`modals.userSettings.pushUnsupportedAndroidApp`: not in the mobile app yet, use the PWA in a browser) rather than blaming "this browser". Wherever this device can't get push at all (unsupported, or not configured on the instance), it also hides `#user-settings-vibrate-row`; the hidden checkbox keeps the account's value, so saving Paramètres leaves `vibrate_on_notification` unchanged for the user's other devices. The service worker, IndexedDB, and `navigator.vibrate` (with a user gesture) work.

## Security & DOM conventions

- **Frontend DOM**: `static/js/app.js` builds all dynamic content with `textContent`/`createElement`, never `innerHTML` with interpolated data — defense in depth against XSS. Keep that pattern for any new UI code.
- Any URL rendered as an `<a href>` (or `<img src>`) is re-validated client-side (`http(s)` scheme only) before use, mirroring the server-side `internal/validate.URL` check — see [backend.md](backend.md)'s "URLs" security rule.
- This is one item in a larger, non-negotiable list — see [backend.md#security-rules](backend.md#security-rules) for the complete set (SQL, CSRF, SSRF, CSP, response caching, etc.), several of which directly constrain frontend code: in particular, the CSP's `script-src`/`style-src` exceptions exist *only* for the Tailwind Play CDN script — don't add another inline `<script>`/`<style>` tag without revisiting `internal/handlers.SecurityHeaders` first.

## PWA lifecycle & mobile layout rules

These rules exist because each was violated by a real regression — a stale branch that reintroduced a cluttered per-button header, and a service worker that stopped surfacing new deployments on mobile without a manual cache clear. Preserve both in anything new; don't let either drift back.

1. **Service worker update detection must stay proactive, never passive-only.** Don't rely solely on a browser's own opportunistic check of `sw.js` (which normally only happens on a full page navigation) to notice a new deployment — that's what let updates go unseen for days on a phone left open on its home-screen icon. `static/js/app.js`'s `registerServiceWorker()` keeps the active `registration` around specifically so `checkForServiceWorkerUpdate()` can force a real `registration.update()` from three independent triggers, and all three must keep firing: the `visibilitychange` listener (a backgrounded mobile PWA being resumed), the `focus` listener (desktop alt-tab/multi-window cases `visibilitychange` alone misses), and the `SW_UPDATE_POLL_MS` (15-minute) `setInterval` backstop for a tab that's never backgrounded or refocused at all. `sw.js`'s `install`/`activate` handlers must keep calling `self.skipWaiting()`/`self.clients.claim()` unconditionally (not gated behind a message from the page) — that's what lets the update banner's button (`#update-reload-button`) do a plain `window.location.reload()` and land on the new assets immediately, with no `postMessage` round-trip needed first. Whenever a change touches a cached static asset (`index.html`, any `static/js/*.js`, `static/css/*.css`, a locale JSON file), bump `SHELL_CACHE`/`RUNTIME_CACHE`'s version suffix in `sw.js` — skipping this means `checkForServiceWorkerUpdate()` has nothing new to actually find, and the deployed change silently won't reach anyone already running the app. `/sw.js` is also served with an explicit `Cache-Control: no-cache` response header (`internal/handlers/app.go`) so a browser's own HTTP heuristic caching can never hand `registration.update()`'s byte-comparison a stale copy of `sw.js` itself — see the "Manual 'check for updates' control" entry in [status.md](status.md) for why this was added.
2. **The list detail header stays exactly two rows — never a shelf of individual icon buttons.** Row 1 is back button + the full (truncatable) list title + one `⋮` "Options" button (`#list-options-button` → `#list-options-sheet`). Every list-level action that isn't Trier/Filtres (share, edit, reorder, the compact/detailed view toggle, "Sélectionner des articles", and anything added later) belongs inside that sheet — never as its own new icon button bolted onto Row 1, since each one narrows the space left for the title until it starts truncating (exactly what happened when per-feature sessions each appended their own button directly to this row instead of extending the sheet). Row 2 is exactly the two actions actually used while browsing a list — Trier (`#sort-items-button` → `#sort-items-sheet`) and Filtres (`#filter-items-button` → `#filter-items-sheet`) — as labeled pill buttons, not bare icons, so they read clearly before a user has learned this app's iconography. Before adding any new list-level action, put it in `#list-options-sheet` (or, only if it's used as often as sort/filter, make the case for promoting it to its own Row 2 pill) rather than adding a seventh button to Row 1.
3. **Nothing may be wider than the phone's screen.** On a mobile browser, a single element wider than the viewport doesn't just overflow locally: the browser widens the whole *layout viewport* to fit it, the page becomes pannable sideways, and every `position: fixed; inset: 0` overlay (all the modals, the toast container) then spans that wider viewport too — which is how a 34px-too-wide dashboard row (`#house-toolbar`) made the admin console slide sideways on every phone under ~430px. The usual culprit is a flex item that can't shrink below its content (a `<select>` sizes to its widest option, an input or button to its intrinsic width): give the item that should give way `min-w-0` (and `shrink-0`/`whitespace-nowrap` to the ones that shouldn't). `static/css/base.css` backs this with `overflow-x: clip` on both `html` and `body` — **`clip`, never `hidden`, on `html`**: `hidden` there stops body's value from propagating to the viewport, turns `<body>` into a scroll container, and silently breaks the sticky `<header>` (verified: it scrolled away with the page). That guard only hides overflow, it doesn't fix a row that doesn't fit, and it makes `document.documentElement.scrollWidth` useless as a test signal — to check a layout, emulate a real phone (Playwright/Chromium `is_mobile`) and assert `window.innerWidth === document.documentElement.clientWidth === <device width>` plus no visible element's right edge past the screen outside a scroll container. Measuring a panel's own `scrollWidth`, as the first backups-tab check did, misses this entirely.

## Conventions

### Frontend (PWA, `static/`)

- Vanilla ES6+ JavaScript (`async`/`await`), **no dependencies, no build step, no framework**. Several classic `<script>` tags (`app.js`, `list_view.js`, `db.js`) share the same global scope instead of using ES modules — identifiers (`state`, `els`, `apiRequest`, etc.) are therefore shared implicitly across files.
- Every network call goes through the `apiRequest()` helper (never a raw `fetch` elsewhere), which centralizes error handling via an on-page error banner and redirects to `/auth/login` on a `401` (the single choke point that auth-gates the whole SPA). `/auth/...` endpoints (login, register, logout, OIDC) are classic form-`POST`s with full-page redirects instead, served from `templates/login.html` — not part of the `apiRequest()`/JSON world.
- DOM built exclusively via `document.createElement`/`textContent`, **never** `innerHTML` with interpolated data — defense in depth against XSS.
- Any URL rendered as an `<a href>` is re-validated client-side (`http(s)` scheme only) before use, mirroring the server-side validation (`internal/validate.URL`).
- CSS: Tailwind CSS via the "Play" CDN (`https://cdn.tailwindcss.com`), no local Tailwind build; supplemented by a minimum of custom CSS (`static/css/tokens.css` for design tokens, `static/css/base.css`).
- `db.js` never references `window`/`document` (only `indexedDB`/`self`) since it's loaded both as a page script and via the service worker's `importScripts()`.
- The service worker (`sw.js`) is the **sole writer** of the IndexedDB mirror and the offline write queue; `app.js`/`list_view.js` only read (`TrakkaDB.getQueue()`) to display a badge.
- Service worker caches are version-suffixed (`trakka-shell-v1`, etc.) — bump the suffix on every `APP_SHELL` change.
- **UI language: an FR/EN toggle, picked from the "Paramètres" modal, with a server-side per-account default** — `static/js/i18n.js` (loaded before every other page script) resolves the pre-auth first paint from `navigator.language` or a saved `localStorage['trakka:lang']` choice, fetches `static/locales/{fr,en}.json`, and applies it to any element flagged `data-i18n`/`data-i18n-placeholder`/`data-i18n-aria-label`; the interactive picker itself is the `#user-settings-language` `<select>` inside the "Langue" section of `#user-settings-modal` (`static/js/settings.js`, alongside the "Apparence" theme `<select>` — see the "Header cleanup" entry in [status.md](status.md) for why both moved there from the header). Once `GET /api/v1/me` resolves, `app.js`'s `init()` reconciles the account's own server-side `language` (always `"fr"`/`"en"`, resolved from `models.User.Language`/`internal/handlers.resolveUserLanguage`, defaulting to the instance's `DEFAULT_APP_LANGUAGE` env var — see [architecture.md](architecture.md)'s Config section — for an account that never set its own preference) against whatever the pre-auth guess already applied, so a brand-new account lands in the instance's configured default language rather than the browser's own. Static markup goes through those `data-i18n*` attributes; dynamic strings built in JS (`app.js`, `list_view.js`, `planning.js`) call `window.TrakkaI18n.t('some.key', vars)` (or the local `t()` wrapper in `app.js`) instead of hard-coding text — as of the "dynamic JS-built strings" fix (see [status.md](status.md)), this covers essentially every dynamic string in `app.js`/`list_view.js`/`planning.js` and every other frontend file — `templates/login.html` (French-only, unauthenticated, never loads `i18n.js`) and `i18n.js`'s own hardcoded-French bootstrap fallback object (used only for the brief window before the real `fetch()` resolves, already out of sync with `fr.json` and not worth fully reconciling) remain the two known exceptions. Still, grep for a literal French string before assuming new code is already wired up. Code, comments, and documentation stay in English regardless of UI language.

The Light/Dark/Auto theme system (`data-theme` attribute on `<html>`, `theme-init.js`/`theme.js`/`tailwind-config.js`, the same "Paramètres" modal picker as language) is documented in the "Light/dark theme" and "Header cleanup" entries in [status.md](status.md).
