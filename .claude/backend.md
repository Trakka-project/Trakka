## API shape

- **API shape**: `/api/v1/houses` (groups lists; a list belongs to exactly one house via `house_id`; a house has one or more members via `house_members`), `/api/v1/houses/{id}/members` (roster + invite-by-email + remove), `/api/v1/lists` (filterable by `?house_id=`/`?type=`/`?shared_with_me=true`; a list `GET` by id embeds its `items`), `/api/v1/items` (filterable by `?list_id=`, with `PATCH` supporting partial updates like toggling `done` without resending the whole item), `/api/v1/custom-categories` (`GET`/`POST`/`PUT /{id}`/`DELETE /{id}`, no partial `PATCH`), and `/api/v1/custom-categories/{id}/share`/`/api/v1/lists/{id}/share` (granular sharing — see the dedicated section below). Full endpoint reference: [docs/API.md](../docs/API.md).

## Custom categories ("Spaces")

- **Custom categories ("Spaces")**: a `CustomCategory` (`id`, `user_id`, `name`, `icon`, `color`, `position`, `created_at`) is a personal, freeform way to organize lists beyond the fixed `lists.type` enum — e.g. "Vacances", "Anniversaire de Léo" — orthogonal to `type` rather than a replacement for it. Unlike every other grouping concept in this app (`houses`, shared by all `house_members`), a category is owned by exactly one user (`user_id`) and is never itself shared: `internal/db/custom_categories.go`'s `GetCustomCategoryForUser`/`UpdateCustomCategoryForUser`/`DeleteCustomCategoryForUser` all scope their `WHERE` clause on `user_id`, so a category can only ever be found, edited, or deleted by whoever created it — a mismatched owner comes back as the same `ErrNotFound` as a nonexistent id (never a separate 403), the same "don't let a lookup confirm another user's data exists" reasoning `UpdateCustomCategoryForUser` shares with `authorizeHouseAccess`'s sibling checks. `lists.custom_category_id` (`INTEGER`, nullable, `addColumnIfMissing`-guarded like `house_id`, `REFERENCES custom_categories(id) ON DELETE SET NULL`) is how a list attaches to one — `ON DELETE SET NULL` rather than `CASCADE` is deliberate, since deleting a category should only unassign it from any list that used it, not delete the list itself. Any member of the list's house can associate or dissociate a category via `POST`/`PUT /api/v1/lists` (`custom_category_id` in the request body; omitted/`null` on the `PUT` full-replace dissociates, matching how `type` already resets to its default when omitted there), but the id must reference a category the *requesting* user owns (`internal/handlers.validateCustomCategoryOwnership`, `internal/handlers/lists.go`) — a shared list can be tagged with one member's personal category, but not with a category belonging to someone else in the house. `GET /api/v1/lists`/`GET /api/v1/lists/{id}` embed the attached category's full row (`custom_category`) via a `LEFT JOIN` in `internal/db.listSelect`, visible to every house member regardless of who owns the category, since seeing a shared list's category tag doesn't require owning it. The frontend (`static/js/spaces.js`) is a fourth dashboard tab, "Espaces" (`#tab-spaces`/`#spaces-view`), rendering each category as a collapsible `<details>` section (mirroring `#done-section`'s chevron/`group-open:` idiom) holding every list attached to it regardless of `type` — see the "Custom categories frontend" entry in [status.md](status.md) for the full frontend design/verification history.

## Granular sharing (Spaces & Lists)

- **Granular sharing (Spaces & Lists)**: beyond house membership, a Space (a `custom_categories` row) or an individual List can be shared directly with one other user by email, giving them `read` or `write` access to it without adding them to the whole parent house — two new tables, `space_shares` and `list_shares` (`id`, `custom_category_id`/`list_id`, `shared_with_user_id`, `permission` ∈ `read`/`write`, `created_at`, each with a `UNIQUE (…, shared_with_user_id)` constraint so re-sharing with a different permission upserts via `internal/db.CreateOrUpdateSpaceShare`/`CreateOrUpdateListShare` rather than erroring). `internal/db.AccessLevelForList` is the single place that combines the three access sources into one verdict for a given user and list — house membership (always `write`, unchanged from before this feature), a `list_shares` grant on the list itself, and a `space_shares` grant on the list's `custom_category_id` if any, taking the higher of the two shares when both apply. `internal/handlers.authorizeListAccess`/`authorizeItemAccess` (`internal/handlers/rbac.go`) replace the old house-only checks on every list/item read and mutation handler, each now taking a `requireWrite bool` — read-only handlers (`GET`) accept `read`, mutating ones (`POST`/`PUT`/`PATCH`/`DELETE`) require `write` — with one deliberate exception: `DELETE /api/v1/lists/{id}` stays House-membership-only even for a `write` share holder, since destroying a whole list (and everyone else's items in it) is a house-management-level action, not just editing. Sharing a **Space** is the owning user's call alone (`internal/handlers.authorizeSpaceOwner`, the same check as renaming/deleting the category); sharing a **List** requires actual House membership of it (`authorizeHouseAccess`, not merely `write` access via another share), so access granted through a share can never itself be used to extend further access. `internal/handlers/shares.go` exposes `GET`/`POST /api/v1/{custom-categories,lists}/{id}/share` and `DELETE .../{id}/share/{userId}` (mirroring the roster/invite/remove shape of `/houses/{id}/members`); `GET /api/v1/lists?shared_with_me=true` (`internal/db.ListSharedListsForUser`) is the reverse query backing the "Partagé avec moi" dashboard tab — every list reachable via either share table, excluding any whose house the caller is already a plain member of (already visible the ordinary way). The frontend (`static/js/shares.js`) owns a shared create/revoke modal (`#share-modal`, opened via `openShareModal({kind, id, name})` from a 👥 button on every list card/space section and the list-detail header) and the fifth dashboard tab (`#tab-shared`/`#shared-view`, wired into `planning.js`'s `setActiveTab` switcher alongside the other four); a card reached via `?shared_with_me=true` shows a 👥 "Partagé" badge (from `list.access_source`, a response-only field like `Item.PriceStatus`) and no edit/share/delete controls, since managing a list requires actual House membership. Full design and endpoint reference: [docs/API.md](../docs/API.md#sharing) and [docs/DATABASE.md](../docs/DATABASE.md#space_shares-and-list_shares).

## Pinning shared lists (and shared Spaces) to the dashboard

- **Pinning shared lists (and shared Spaces) to the dashboard**: the recipient of a share can choose to have it show up alongside their own house's lists on the main dashboard, instead of having to go find it in the "Partagé avec moi"/"Espaces" tabs every time. Two independent pin flags, combined via OR: `list_shares.is_pinned_to_dashboard` (`INTEGER NOT NULL DEFAULT 0`, migration 11) pins one List, toggled via `PATCH /api/v1/lists/{id}/share/pin` (`internal/handlers.handleListSharePin`/`internal/db.SetListSharePinned`); `space_shares.is_pinned_to_dashboard` (migration 12) pins a whole Space — every List reachable through it, present and future, no per-list action needed — toggled via `PATCH /api/v1/custom-categories/{id}/share/pin` (`internal/handlers.handleSpaceSharePin`/`internal/db.SetSpaceSharePinned`). Both endpoints' only authorization check is "does the caller hold a share row for this List/Space at all" (surfaced as `404`, not `403`, matching this codebase's "don't distinguish nonexistent from unauthorized" convention) — there's no house-membership or ownership check, since this is the recipient's own preference about their own dashboard, not a change to who can access anything. A List reached *only* through a shared Space (no `list_shares` row of its own yet) can still be pinned individually: `SetListSharePinned` auto-creates that row on demand, scoped to exactly the permission the Space already grants for that List (via a `lists JOIN space_shares` lookup on `custom_category_id`), so the insert can never itself change the recipient's `AccessLevelForList` verdict — it just gives the individual pin flag somewhere to live. `db.ListSharedListsForUser` (the same query backing `?shared_with_me=true`) surfaces the combined state as `List.IsPinnedToDashboard`, a response-only field alongside `AccessSource`/`AccessPermission`: for a `space_share`-sourced row this now comes from `space_shares.is_pinned_to_dashboard` directly (pinning the Space) rather than a hardcoded `false`; when a List is reachable both via its own `list_shares` row and via its Space, whichever source says pinned wins — the same "OR", not "AND", the higher-of-two-permissions dedup already uses — so unpinning one List individually cannot override its parent Space being pinned as a whole; the Space-level pin is the "master" pin for everything reachable through it. `db.ListSpacesSharedWithUser` (backing `GET /api/v1/custom-categories?shared_with_me=true`) is the Space-level "shared with me" query, the category-level equivalent of `ListSharedListsForUser`, surfacing `AccessPermission`/`IsPinnedToDashboard` response-only fields on `CustomCategory` the same way. The frontend has no server-side "house lists plus pinned shares in one call" endpoint to lean on: `static/js/app.js`'s `loadDashboard` fetches its usual `?house_id=` listing, then separately calls `static/js/shares.js`'s `loadPinnedSharedLists` (a thin wrapper around `?shared_with_me=true`, filtered to `is_pinned_to_dashboard`) and merges the two client-side before splitting into the three dashboard grids — a best-effort merge (`.catch(() => [])`) so a failure fetching pinned shares can never block the rest of the dashboard from rendering, and, like the rest of the sharing feature, with no offline mirror (pinned shared cards simply aren't shown while offline). `buildListCard` (`app.js`) grows a 📌/📌-filled pin/unpin button (`toggleListPin`, a plain await-then-`refreshVisibleView()` mutation, not the coalesced-optimistic pattern item quantity/urgent toggles use, since this is an infrequent deliberate action rather than a rapid-fire control) shown for both `list.access_source === 'list_share'` and `'space_share'` — the same 👥 "Partagé" badge the granular-sharing feature already renders for any `access_source` is reused as-is for the "distinguish a pinned card from an owned one" requirement, plus a small 📌 "Épinglée" badge shown whenever `is_pinned_to_dashboard` is true, independent of the button's own state. `static/js/spaces.js`'s "Espaces" tab gains an "Espaces partagés avec moi" section (`buildSharedCategorySection`) listing every Space shared with the caller (pinned or not, so there's somewhere to discover and toggle the pin in the first place) with a `[⋮]` kebab opening `#space-card-actions-sheet` for the pin/unpin toggle — a Space's own lists there are drawn from `?shared_with_me=true`, filtered to `custom_category_id`s actually present in that shared-categories list (so a List shared *individually* that happens to sit in the owner's other, unshared category is never incorrectly grouped under a "shared space" section). Full design and endpoint reference: [docs/API.md](../docs/API.md#patch-apiv1listsidsharepin), [docs/API.md](../docs/API.md#patch-apiv1custom-categoriesidsharepin) and [docs/DATABASE.md](../docs/DATABASE.md#space_shares-and-list_shares).

Two follow-up bug reports and their resolutions (a false "not a member of this house" report that didn't reproduce, a real transient-race dashboard `403` flash, a real gap where a House-visible-but-not-explicitly-shared Space couldn't be pinned, and a stale-scroll/stale-refresh UI bug) are recorded with full root-cause analysis in [status.md](status.md) — read those before assuming "pinning is broken" is a new bug rather than one of these already-diagnosed ones.

## Recurring items

- **Recurring items**: an item can carry `recurrence_rule` (`TEXT`, nullable — a canonical iCalendar RRULE subset since migration 22: `FREQ=DAILY|WEEKLY|MONTHLY|YEARLY`, `INTERVAL` 1–999 (omitted when 1), and weekly-only `BYDAY` days Monday first, e.g. `FREQ=WEEKLY;INTERVAL=2;BYDAY=MO,WE,FR`. `internal/recurrence` owns the grammar — `Parse` (also accepts the legacy `DAILY`/…/`EVERY_X_DAYS:<n>`/`EVERY_X_MONTHS:<n>` forms and any equivalent RRULE spelling), `String` (the canonical spelling; `internal/validate.Recurrence` returns it, so only that form is ever written, and migration `0022_rrule_recurrence.sql` rewrote stored rows to match — `TestMigrationRewritesLegacyRecurrenceRules` checks the SQL against `Parse(...).String()`), and `After` (one step: BYDAY takes the next listed day later in the same Monday–Sunday week, else the first listed day `INTERVAL` weeks on, so stepping occurrence to occurrence keeps an "every 2 weeks" rule on its weeks; months/years keep the day of the month clamped to the month end — January 31 → February 28, no longer `time.AddDate`'s roll-over to March 3), and `Next` (the catch-up loop used on completion, below; the rule is parsed once for the whole loop). COUNT/UNTIL/BYMONTHDAY/ordinal days are rejected rather than ignored; there is no stored DTSTART — the series is anchored on the current `due_date`, which the frontend's "Date de début" sets to the first occurrence), `due_date` (`TEXT`, `YYYY-MM-DD`, validated by `internal/validate.Date`), an optional `due_time` (`HH:MM`, `internal/validate.TimeOfDay`, migration 21 — always cleared with `due_date`, `400` on its own) and `recurrence_end_date` (same format/validator). `items.is_recurring` (`INTEGER NOT NULL DEFAULT 0`) is never a separate input anywhere in the stack — `internal/db.CreateItem`/`UpdateItem` always write it as `recurrence_rule IS NOT NULL`, so the two columns can never disagree. **Lifecycle** (reworked in the "Recurring tasks, due times & task notifications" session — before it, completion un-checked the item on the spot with an advanced `due_date`): `internal/handlers.applyRecurrenceLifecycle` (`recurrence.go`), called from `handleItemsUpdate`/`handleItemsPatch` right before `db.UpdateItem` with the item's pre-request state as `before`, keeps `next_due_date` (migration 21) consistent — a done recurring item keeps `done: true` (so it shows in "Terminés"), keeps `due_date` on the occurrence just completed, and gets `next_due_date = nextOccurrence(due_date or today, rule, app.today())` — a thin `YYYY-MM-DD` adapter (`dateLayout`) over `recurrence.Rule.Next`: step once, then keep stepping until strictly after today (`APP_TIMEZONE`), so completing early still steps from the due date while a chore left overdue for several periods skips the missed ones instead of bouncing back overdue. An unchanged rule/due date/end date on an already-done item keeps its stored `next_due_date` (an unrelated edit never moves it); a not-done or non-recurring item never carries one, so un-checking by hand cancels the pending occurrence. Past `recurrence_end_date`, `next_due_date` stays `NULL` and the item simply stays done. `next_due_date`/`due_time` are written by `db.SetItemSchedule`, a separate method for the same "too many positional params" reason as `SetItemLabels`/`SetItemReminder`. **Coming back**: `Application.RunNextOccurrenceScan` (`recurrence.go`) lists done items with a `next_due_date` (`db.ListItemsAwaitingNextOccurrence`, served by the partial index `idx_items_next_due_date`) and, once `occurrenceStart` has passed — local midnight of `next_due_date`, or the item's reminder moment when earlier ("la veille à 20:00" brings it back the evening before, so the push never points at a task still in "Terminés") — calls `db.ActivateNextOccurrence`, a compare-and-swap `UPDATE ... WHERE done = 1 AND next_due_date = ?` that sets `done = 0, due_date = next_due_date, next_due_date = NULL` and can't override a user who edited the item meanwhile. It runs on `cmd/server/main.go`'s `runNextOccurrenceLoop` (fixed one-minute ticker, started **unconditionally** — this is task lifecycle, not a notification) and at the start of every `RunDueReminderScan`. Clearing `recurrence_rule` via `PATCH` now clears only `recurrence_end_date` (and, through the lifecycle, `next_due_date`) — it used to clear `due_date` too, which silently wiped the due date of any non-recurring task saved from the edit modal (which always sends `recurrence_rule`), since due dates apply to every item. The frontend offers the four fixed cadences (option values are the canonical rules) plus "Personnalisée…", the custom recurrence sheet (see [frontend-pwa.md](frontend-pwa.md)). The rule arithmetic has exactly one hand-kept JS port, `static/js/recurrence.js` (`TrakkaRecurrence`: `parseRule`/`formatRule`/`normalizeRule`/`occurrenceAfter`/`nextOccurrence`/`firstOccurrenceOnOrAfter`, plus the shared `localDateISO`/`addDaysISO` date helpers), importScripts()-safe like `db.js` so `static/sw.js` (`applyRecurrenceLifecycleOffline`, called from `applyOptimisticEdit`/`resolveAgainstPendingCreate` so an offline check-off gets the same `next_due_date`), `planning.js` (`projectRecurringOccurrences`, which parses the rule once per item) and `list_view.js` (`computeNextDueDate`, `recurrenceBadgeLabel`) all share it — it replaced three separate per-file ports. **Any change to `internal/recurrence` or `nextOccurrence` must be mirrored there by hand**; `applyRecurrenceLifecycleOffline` itself remains a port of `applyRecurrenceLifecycle`. The original advance-and-uncheck behavior was verified end-to-end in three Playwright sessions (see the "Recurring items" entry in [status.md](status.md)); the current lifecycle's verification is in the "Recurring tasks, due times & task notifications" entry there.

## Automatic price & image lookup (scraper)

- **Automatic price & image lookup**: when an item is created, or its `url` changes, `internal/handlers.scrapeProductInfo` (`internal/handlers/scrape.go`) kicks off a detached goroutine — never `r.Context()`, which is canceled the moment the response is written — that calls `internal/scraper.FetchProductInfo(ctx, url)` **once** and writes back whichever of `price`/`image_url` the item is still missing (an explicit `price` in the request only skips price detection — the image is still looked up) via `db.UpdateItemPriceIfMissing`/`db.UpdateItemImageIfMissing`. Both of those methods' `WHERE ... AND url = ? AND <column> IS NULL` guards are what makes this safe to run detached from the request: a slow scrape can never clobber a price/image the user already has, or one for a since-changed `url`, no matter how the race resolves. Unlike a purely fire-and-forget design, `handleItemsCreate`/`Update`/`Patch` (`internal/handlers/items.go`) each wait up to `syncScrapeTimeout` (2.5s) on that goroutine before responding: if it lands in time, the response already carries the real `price`/`image_url` and a response-only `price_status: "found"` field (`models.Item.PriceStatus`, `json:"price_status,omitempty"`, never persisted, never present on a plain `GET`); if not and a price was still needed, `scrapeProductInfo` returns `"pending"` and the goroutine keeps running in the background exactly as the original fully-async design always did — but if only the image was still outstanding (price was already known), it returns `"found"` instead, since price detection genuinely isn't pending; the image is treated as a best-effort enhancement that simply shows up next time the item is fetched if it's slow to arrive. `price_status` is `"none"` when there was nothing to scrape (no `url`, or no price found within the wait) — this is unaffected by whether an image was found. This bounded wait is what lets `static/js/list_view.js` update the DOM straight from the POST/PATCH response instead of reloading or polling, while still never blocking indefinitely on a slow or unresponsive site. `items.price_auto` (`INTEGER NOT NULL DEFAULT 0`, same 0/1-boolean convention as `done`) records whether the current `price` came from this lookup rather than a user — the frontend shows a small badge next to an auto-detected price, clickable to open the same edit-item modal used everywhere else; sending `price` in any request (including an explicit `null`) always resets it to `false`, since a manual value was supplied. `items.image_url` (`TEXT`, nullable) is scraper-only — there is no request field to set it manually — and is cleared back to `nil` whenever `url` changes to something new (both `PUT` and `PATCH` in `internal/handlers/items.go` compute this before calling `db.UpdateItem`), since an image found for the previous `url` no longer describes the item. `internal/scraper.FetchProductInfo` parses the page once (`extractProductInfo`) and looks for a price, an image, and a title using `golang.org/x/net/html` rather than regex-scraping raw HTML. The request carries a real desktop-Chrome `User-Agent` and an `Accept-Language: fr-FR,fr;q=0.9,en-US;q=0.8,en;q=0.7` header (`internal/scraper/scraper.go`'s `userAgent`/`acceptLanguage` consts) — several storefronts this targets (Reichelt and Amazon in particular) block or serve a stripped page to a generic/library User-Agent, and this is purely to see the same page an ordinary visitor's browser would for a URL the user themselves added to their own list. Price priority order: Schema.org JSON-LD (`price` inside an `Offer`), OpenGraph/`product:` meta tags (`og:price:amount`/`product:price:amount`), a Twitter Card `twitter:dataN` value whose paired `twitter:labelN` reads as "Price"/"Prix" (`resolveTwitterPrice` — some storefronts expose a price only this way), then classic microdata (`itemprop="price"`, read off either a `content` attribute or the element's text — checked on every element, including a `<meta itemprop="price" content="...">`, not just non-`<meta>` tags). On an Amazon host specifically, `resolveAmazonPrice` tries five Amazon-only selectors (buy-box `a-offscreen` spans, `priceblock_*` ids, `a-color-price`, `#price_inside_buybox`) *before* the generic chain, since Amazon's real displayed price mostly lives in page-specific markup its JSON-LD is often stale relative to; a script-state fallback (`amazonScriptStatePrice`) and an absolute-last-resort raw-body regex fallback (`amazonRawBodyPrice`) exist for pages that render price from embedded JS state or serve an anti-bot challenge page — see the "Amazon-specific price selectors" and "Amazon anti-blocking headers" entries in [status.md](status.md) for the full history and a debug-log hook (`logIfAmazonBlocked`) that flags when Amazon served its CAPTCHA page instead of the product page. Image priority order: on an Amazon host (`isAmazonHost` — `amazon.*`, `amzn.to`, `amzn.eu`) only, Amazon's own product-image element (`id="landingImage"`/`id="imgBlkFront"`)'s `data-old-hires` or `data-a-dynamic-image` attribute first (`amazonLandingImage`/`bestDynamicImage` — Amazon's own `og:image` is frequently the site logo or a nav icon, never trusted first there); then, on every host, Schema.org JSON-LD (`image`, as a string, array, or nested `ImageObject`), `og:image` (skipped when the URL contains an Amazon-chrome term — `amazon-logo`/`nav2`/`favicon`/`tile` — `isAmazonGenericImage`), classic microdata (`itemprop="image"`), and the Twitter Card tag (`twitter:image`) as a last resort. Title priority order: JSON-LD (`name`, preferring an object whose own `@type` is `"Product"`), `og:title`, then the page's own `<title>` — extracted but not yet consumed by any downstream handler/DB path. None of this changes how a price is *stored* or *displayed*: `ProductInfo.Price` stays a bare `float64` with no currency symbol — `parsePriceString` just has to parse the number correctly (it already tolerates both `"15,90 €"`-style and `"15.90"`-style input), and the frontend's existing hardcoded EUR `Intl.NumberFormat` (`static/js/list_view.js`'s `euroFormatter`) renders it with a currency symbol on display as it always has. A relative image URL is resolved to absolute against the page's own URL (`resolveImageURL`, `url.ResolveReference`) and only accepted if the result is `http`/`https` with a non-empty host — the same rule `internal/validate.URL` applies to `item.url` — so a `javascript:`/`data:` URI can never end up as an item's `image_url`. Because this makes the server fetch an arbitrary URL a user typed into the `url` field, its `http.Client`'s `Transport.DialContext` is replaced with an SSRF guard (`safeDialContext` in `internal/scraper/scraper.go`) that resolves the host itself and only ever dials a public IP (rejecting loopback/private/link-local/multicast, which also covers the `169.254.169.254` cloud metadata address) — dialing the checked IP literal directly, rather than letting the transport re-resolve the hostname, is what closes the DNS-rebinding TOCTOU gap a naive "check then dial" would leave open. Every failure mode (network error, timeout, blocked host, no recognizable price/image/title markup) is treated identically as "nothing found" — this feature must never fail item creation/update outright, and the bounded wait keeps it from blocking indefinitely either.

**Price tracking** (migration 28, `internal/handlers/price_tracking.go`, full behavior in [docs/API.md](../docs/API.md#price-tracking)): both background scans — `RunPriceAlertScan` (`PRICE_CHECK_INTERVAL_HOURS`, every tracked item without an active target price) and `RunTargetPriceScan` (`SCRAPE_INTERVAL`, those with one; disjoint populations) — and `POST /api/v1/items/{id}/price-check` run one per-item check, `trackItemPrice`: fetch the item's own page and record the price in `price_history` (`db.RecordPriceObservation`, appends only on change); if the price *follows the page* (none yet, `price_auto`, or an active target price) apply a different one via the compare-and-swap `db.UpdateItemPriceFromScan` — which also stamps `items.previous_price`/`price_changed_at`, the list's green/red indicator, cleared by a manual price/url edit in `UpdateItem` — then `notifyPriceChange` (drop/increase) and `checkPriceDropAlert`; a typed-in price is never overwritten, a lower page price is proposed as a `price_alerts` row instead (`proposeBetterPrice`, deduplicated by `HasPriceAlertForSource` so a rejected deal never comes back); finally, with `DEAL_SEARCH_ENABLED`, `internal/scraper.SearchDealabs` (`dealabs.go`: `/search?q=` only — robots.txt disallows its filter params; parses the `data-vue3` JSON of `ThreadMainListItemNormalizer` results; `DealSearchQuery`'s specificity gate, `BestDeal`'s all-words match and ≥50%-of-price floor) proposes the best cheaper deal. Idealo/LeDenicheur (bot wall, robots) and Google Shopping (no API) are deliberately not searched. `notifyPriceChange` always writes the per-user in-app inbox (`price_notifications`, `GET /api/v1/price-notifications`, `POST …/read`) for the recipients that want it, *then* pushes — that is what decouples price alerts from push, and the scans never depend on `PushEnabled()`. Accepting an alert switches the item to its source — `price` **and** `url` (`db.AcceptPriceAlert`, `price_auto = 1`, the handler re-checks `source_url` with `validate.URL` first, `409` otherwise) — so the scans follow the price the user chose. For a Dealabs deal that url is the deal page (the merchant link is only reachable via `/visit/`, which Dealabs' robots.txt disallows): `FetchProductInfo` recognizes a deal page (`isDealabsDealURL`) and reads the deal's own price/expiry from its `window.__INITIAL_STATE__.threadDetail` (`dealabsDealState`) instead of the generic extractors (the page shows other deals' prices too); an expired deal sets `ProductInfo.DealExpired`, its price is no longer followed, and `announceDealExpired` notifies once per url (`expired` inbox kind, `NotifyPriceDealGone` = master switch only). `PriceAlert.ChangesURL` (`items.url IS NOT source_url`) drives the drawer's "Appliquer ce prix et ce lien". The older history of the two jobs (false→true-transition semantics, the CAS guard) is in the "Price alerts / deal notifications", "Price drop alerts (per-item target price)", and "Target-price background scan" entries in [status.md](status.md).

## Authentication & authorization

- **Authentication & authorization**: local email+password (bcrypt) and generic OIDC/OAuth2 SSO (Authelia/Authentik/Keycloak/Google, ...) both establish the same opaque, server-side session — an HTTP-only, `SameSite=Lax` cookie whose value hashes to a row in the `sessions` table (`internal/auth.Service`); see the CSRF section below for why Lax is still safe here, and the "Mobile/PWA login loop fix" entry in [status.md](status.md) for why it isn't `Strict`. Every `/api/v1/...` request is gated as a whole behind `(*handlers.Application).RequireSession` (wrapped once around a sub-`http.ServeMux` in `Routes()`, not per-route) — deliberately **not** a separate `internal/middleware` package, since that middleware needs `*db.DB` and `internal/handlers` needs to call it to build routes, which would be an import cycle either direction; it lives as an `*Application` method next to every other handler instead. `/auth/...` (login page, register/login/logout submit, OIDC redirect/callback) and all static assets stay unauthenticated by design — gating static files would break the service worker's cache-first app-shell strategy, so the auth boundary is the JSON API, and `static/js/app.js`'s `apiRequest()` handles the client-side redirect-to-login on a `401`. A house's lists/items are only visible to its members (`internal/handlers/rbac.go`'s `authorizeHouseAccess`/`authorizeHouseOwner`, checked against `house_members` via `internal/db`); `CreateHouseWithOwner` (the only way a house gets created through normal use) is the one place in `internal/db` that opens an explicit `sql.Tx`, so a house is never left without an owner. The OIDC client (`internal/auth/oidc.go`, `jwt.go`) is hand-rolled — discovery, Authorization Code + PKCE, JWKS fetch/cache, RS256 id_token signature verification — using only the standard library plus `golang.org/x/crypto/bcrypt` (the one new dependency this feature added), rather than pulling in `coreos/go-oidc`/`golang.org/x/oauth2`, per the "standard library wherever possible" convention in [architecture.md](architecture.md).

- **SSO from the Android app** (`internal/handlers/oidc_app.go`): an Android WebView cannot run WebAuthn for an identity provider's site (only for sites tied to the app by Digital Asset Links, which a multi-server app signed by each builder can't be), so an Authentik passkey stage failed inside the app ("Error creating credential"). The app therefore runs the OIDC flow in a Custom Tab: `GET /auth/oidc/login?app_challenge=<S256(verifier)>` keeps the challenge in the flow cookie; the callback then opens no browser session but stores a single-use handoff code (`appHandoffStore`: in memory, by `HashToken`, 2-minute TTL, capped at 1000, consumed by the first attempt) and redirects to `io.github.trakka-project.app://sso?code=` (or `?error=` for a failure, so the app shows it); the app's WebView redeems code + verifier at `POST /auth/oidc/app-session`, which calls `finishLogin`. The verifier (PKCE reasoning) makes an intercepted deep link useless; `requireSameOriginWrite` stops a cross-site page from redeeming an attacker's own code+verifier pair in a victim's browser (login CSRF) while the WebView's native `postUrl` (`Origin: null`, `Sec-Fetch-Site: none`) passes. The provider's redirect URI is unchanged. Tests: `oidc_app_test.go`. App side: `BrowserSignIn.java`, docs in [docs/MOBILE_BUILD.md](../docs/MOBILE_BUILD.md#sso-oidc-passkeys-and-security-keys) and [docs/API.md](../docs/API.md#sso-sign-in-from-the-android-app).

## Web Push notifications

- **Web Push notifications**: `internal/webpush` is a from-scratch implementation of Web Push (RFC 8030), VAPID application-server identification (RFC 8292), and the `aes128gcm` payload encryption a push message is carried in (RFC 8291) — `GenerateVAPIDKeys`/`vapidPrivateKeyFromB64` build on `crypto/ecdh`/`crypto/ecdsa` (bridged via `ecdsa.PrivateKey.ECDH()`/`ecdh.PublicKey.Bytes()` rather than the deprecated `crypto/elliptic` point-arithmetic helpers), `signVAPIDJWT` hand-rolls the ES256 JWT the same way `internal/auth/jwt.go` already hand-rolls OIDC's, and `encryptPayload` hand-rolls HKDF (RFC 5869, on top of `crypto/hmac`/`crypto/sha256` rather than depending on exactly which Go toolchain version first shipped a dedicated `crypto/hkdf` package) plus AES-128-GCM framing — all per the "standard library wherever possible" convention, the same reasoning that already justified hand-rolling OIDC/JWT rather than pulling in a third-party Web Push library. `internal/webpush/webpush_test.go`'s `TestEncryptPayloadMatchesRFC8291Example` drives the encryption path with RFC 8291 Appendix A's own published key pairs/salt and asserts every intermediate value (ECDH secret, IKM, PRK, CEK, nonce) and the final ciphertext match the RFC's own worked example byte-for-byte — the strongest correctness signal available for this code short of a live push service, and how a subtle HKDF/framing bug would be caught here rather than only silently failing to deliver against a real browser. `Send`'s `http.Client` carries its own independent copy of `internal/scraper`'s SSRF dial guard (`internal/webpush/ssrf.go` — see the SSRF security rule in this file's Security rules section below for why a push subscription's `endpoint` needs the same defense as an item's `url`).

  A user opts in from the "Paramètres" modal's "Activer les notifications push" toggle (`static/js/push.js`, `#user-settings-push-toggle` in `static/index.html`): it calls the browser's own `Notification.requestPermission()` (nothing server-side can skip or pre-empt that native prompt), subscribes via `PushManager.subscribe({applicationServerKey: ...})` using the public key from `GET /api/v1/push/vapid-public-key`, and registers the resulting subscription (`endpoint`/`keys.p256dh`/`keys.auth`) via `POST /api/v1/push/subscribe` (`internal/handlers/push.go`, stored in the new `push_subscriptions` table, upserted on `(user_id, endpoint)` so a browser key rotation or re-enabling push refreshes the row rather than erroring). `refreshPushToggleUI` re-derives the toggle's checked/disabled state and an explanatory status line every time the settings modal opens — unsupported browser, push not configured on this instance (`{"enabled": false}` from the vapid-public-key endpoint), permission previously denied (only undoable via the browser's own site settings, never re-promptable from script), or the ordinary on/off state of an actual subscription — rather than caching a stale answer, since permission can change outside the app at any time. `internal/handlers.sendToUsers` (`push.go`) is the single delivery fan-out both use cases below call: best-effort and concurrent across every recipient's subscriptions (one slow/dead device never blocks another), deleting a subscription outright on `webpush.ErrSubscriptionGone` (RFC 8030 §7.3's `404`/`410` "this no longer exists" signal) and just logging anything else, since a push notification is always a secondary effect of an action that already succeeded and must never be able to make that action look like it failed.

  **Vibration** (migration 24): `users.vibrate_on_notification` (default on, `PATCH /api/v1/me`, the "Activer les vibrations des notifications" checkbox saved with the settings form) decides whether a push vibrates. It is applied server-side because a service worker has no `localStorage`: `ListPushSubscriptionsForUsers` joins `users` to set `models.PushSubscription.Vibrate`, and `sendToUsers` marshals the payload twice (`marshalPushBodies`, without and with `pushPayload.Vibrate = notificationVibratePattern`, `[200, 100, 200]`) and sends each device the variant its owner chose. `static/sw.js` shows a payload with a `vibrate` array as `silent: false` plus `vibrate` (the spec throws a `TypeError` for `silent: true` with a pattern), so the OS may also play its sound; without one it stays `silent: true` as before. Android Chrome only; iOS has no Vibration API, and on recent Android the notification channel settings can override the pattern.

  **Use case 1 — shared list changes**: `internal/handlers.notifyListChange` (`push.go`) fires, in a detached goroutine on its own bounded context (never `r.Context()`, the same "canceled the moment the response is written" reasoning `scrapeProductInfo` already follows), from exactly two call sites — `handleItemsCreate` (unconditionally, every created item) and `handleItemsUpdate`/`handleItemsPatch` (only on a `done` `false → true` transition, compared against the item's pre-request state — a recurring item now stays done on check-off, see "Recurring items" above). Deliberately scoped to just "added" and "checked off", per the feature's own spec, not every field edit (a price/quantity/rename edit stays silent). Recipients are every *other* user with access to the list — `internal/db.ListNotificationRecipients(ctx, listID, excludeUserID)`, a plain `UNION` of the same three sources `AccessLevelForList` already combines (House membership, `list_shares`, `space_shares` via the list's `custom_category_id`), inverted from "can this user see the list" to "who can see the list", excluding whoever's own action triggered it (an id of `0` — no real user ever has it — excludes nobody, the shape the due-date scan below uses instead). The notification's `Notification` options set `silent: true` (no sound/vibration, but still a real, visible notification — browsers restrict/penalize genuinely data-only "silent push" with no UI at all, so this is what satisfies "notification silencieuse" without going there) and `data: {url: "/?list={id}"}` for `notificationclick` routing (see [frontend-pwa.md](frontend-pwa.md) for the frontend side).

  **Use case 2 — configurable task due-date reminders**: originally scoped to recurring items only (a lead-time-in-minutes model), this was generalized to a Google-Tasks-style reminder on **any** item with a `due_date` — the frontend gained its first-ever due-date picker in the process, since none existed before this feature (see [frontend-pwa.md](frontend-pwa.md)). Three new `items` columns — `reminder_enabled` (`INTEGER NOT NULL DEFAULT 1`), `reminder_offset_days` (nullable `INTEGER`), `reminder_time` (nullable `TEXT`, `HH:MM` 24h, `internal/validate.TimeOfDay`) — replace the old lead-time model: a reminder fires `reminder_offset_days` whole days before `due_date`, at `reminder_time`. Migration 21 added a fourth mode, `reminder_at_due_time` ("à l'heure exacte de l'échéance"): with a `due_time` the reminder fires at `due_date` + `due_time`, and offset/time stay as the fallback for an item without one (`reminderMoment` in `push.go` is the single place the instant is computed, shared by the reminder scan and `recurrence.go`'s `occurrenceStart`). `recurrence_lead_minutes` (migration 15) is left in the schema/API for backward compatibility but no longer read by any scan. Two new `users` columns, `reminder_default_offset_days`/`reminder_default_time` (settable via `PATCH /api/v1/me`), are this feature's other half — a personal default expressing the named presets: offset `0` is "le jour même", `1` is "la veille", anything else "personnalisé" (the settings UI keeps the time editable under every preset), plus `users.reminder_default_at_due_time` (migration 21) for "à l'heure exacte de l'échéance", the offset/time pair then being its fallback. `PATCH /api/v1/me` only accepts the flag together with the pair, and the pair alone means `false`, so an older client still saves a plain offset default.

  The key design decision is **when** a task's reminder resolves from that default: `internal/handlers.resolveReminderDefaults` (`items.go`) substitutes the *acting* user's own current default into `reminder_offset_days`/`reminder_time` **once, at write time** — POST/PUT/PATCH `/api/v1/items` all call it right before `db.SetItemReminder` — rather than leaving a `NULL` to be re-derived live by whichever user later views the item. `reminder_at_due_time` resolves the same way, with one refinement: a request that spells out an offset or time but not the mode chose an explicit offset reminder, so it resolves to `false` rather than to the default mode. This is deliberate, not an oversight: a shared list's item is visible to multiple users who could each have a different personal default, so "notify every recipient at their own preferred time" has no single well-defined answer — resolving once keeps the existing single-moment, single-`sendToUsers`-fan-out design intact (every recipient is still notified together, exactly as [use case 1](#web-push-notifications) already does). A consequence: a later change to your own default only affects tasks you create/edit afterward, not retroactively, and the edit-item modal can never show "Par défaut" again for an existing item (`static/js/list_view.js`'s `reminderItemToSelection` shows whichever named preset the stored, already-resolved values happen to match instead, or "Personnalisé" if neither). `db.SetItemReminder` (`internal/db/items.go`) is a dedicated method, not another `CreateItem`/`UpdateItem` parameter — the same "already too many positional params" reasoning `SetItemLabels` (migration 18) established.

  `internal/handlers.RunDueReminderScan` (`internal/db/due_reminders.go`'s `ListItemsForDueReminderScan`/`MarkDueReminderSent`, generalized from the old `RunRecurringDueScan`/`ListItemsForRecurringNotifyScan`/`MarkRecurringReminderSent`), wired to a ticker in `cmd/server/main.go` (`runDueReminderScanLoop`, mirroring `runPriceAlertScanLoop`'s "run once immediately, then on `NOTIF_DUE_SCAN_INTERVAL_MINUTES`" shape, gated on both a positive interval and `Config.PushEnabled()`), fetches every not-done item with a `due_date`, `reminder_enabled = 1` (served by the partial index `idx_items_pending_reminder`, migration 23, since the scan runs every minute), and a `due_reminder_sent_for` that doesn't already match its due key (`due_date`, or `due_date || 'T' || due_time` — `dueReminderKeyExpr`, migration 21, so moving a task to another time re-arms it; rows marked before migration 21 have no `due_time` and keep matching) — dropping the old `recurrence_rule IS NOT NULL` filter entirely, since this now applies to any item — and, for each one whose computed reminder instant (`due_date` minus `reminder_offset_days`, at `reminder_time`, parsed via `time.ParseInLocation` in `app.location()`) has already passed, notifies every user with access to its list (via `ListNotificationRecipients`, no actor to exclude) and calls `db.MarkDueReminderSent(itemID, key)`, which also stamps `notification_sent_at` (exposed read-only as `models.Item.NotificationSentAt`, and only while the stored key still matches — `itemSelectColumns`' `CASE` in `internal/db/items.go` — so it needs no reset step either). The push carries a per-item `tag` (`trakka-reminder-<id>`, honored by `sw.js`) and a French relative date (`describeDueFR`: "Échéance aujourd'hui à 18:00", "Échéance le dim. 11 oct.", "Échéance dépassée (…)"). The scan's default interval dropped from 30 to 1 minute for the exact-time mode, and its per-tick log line moved to debug level. Storing the *due date value itself* rather than a boolean/timestamp flag is what makes this re-arm automatically the moment `due_date` next changes for any reason (a recurring item's own advance-on-completion, or a manual edit) — the stored value simply stops matching the new `due_date`, with no explicit "clear the flag" step needed anywhere in the codebase.

  Reminder times need a time zone to mean anything, and this codebase had no notion of one anywhere before this feature: `Config.AppTimeZone` (`APP_TIMEZONE`, default `Europe/Paris`) is resolved once at startup into `handlers.Application.Location` (`cmd/server/main.go`, falling back to `time.UTC` with a `logger.Warn` on an unrecognized zone name, the same graceful-degrade-rather-than-crash posture a broken OIDC discovery already gets) — a single instance-wide setting, not per-user, matching this app's one-household-per-instance design (see [architecture.md](architecture.md)).

  Server-composed notification text (both use cases) is always French, regardless of the recipient's own FR/EN choice — there is no per-user language preference stored server-side to localize it with, until the "Header cleanup" session added `users.language` (see [status.md](status.md)); this remains an open inconsistency worth revisiting. `trakka -generate-vapid-keys` (`cmd/server/main.go`) prints a fresh key pair for `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` and exits, needing no configuration itself. The frontend delivery/routing side (`static/sw.js`'s `push`/`notificationclick` listeners, `app.js`'s deep-link handling) is documented in [frontend-pwa.md](frontend-pwa.md). Verified: `internal/webpush`'s RFC 8291 conformance test above, DB-layer tests for the subscription upsert/batch-lookup, the recipient-resolution `UNION` across all three access sources, and `TestListItemsForDueReminderScan`'s filter/re-arm behavior (covering a plain non-recurring item alongside a recurring one, the generalization use case 2 above describes), plus handler tests for subscribe/unsubscribe validation and idempotency, and `internal/validate.TimeOfDay` — `go build`/`go vet`/`gofmt -l .`/`CGO_ENABLED=1 go test -race ./...` all clean. The full resolve-at-write-time/scan/mark-sent pipeline (including the `APP_TIMEZONE`-aware reminder-moment computation) was additionally exercised end-to-end via a local smoke test (register → set a personal reminder default → create items exercising "use my default"/an explicit override/disabled → confirm each resolves and round-trips correctly via the API → confirm the scan actually fires and marks a due item sent). **Not yet done**: never exercised against a real browser or a real push service, and the new due-date/reminder task-form UI (`static/js/list_view.js`/`settings.js`) has not been clicked through in an actual browser — see the "Web Push notifications" entry in [status.md](status.md) for the full caveat and a concrete verification recipe.
- **Local reminders for the Android app** (`internal/handlers/reminders.go`, `GET /api/v1/reminders/upcoming`; `db.ListActiveRemindersForUser`): the app's WebView has no Web Push, so the app schedules reminders on the phone (Capacitor `LocalNotifications`, [frontend-pwa.md](frontend-pwa.md#inside-the-android-app-capacitor)) from this endpoint, which keeps the reminder moment computed in one place (`reminderMoment`, `app.location()`) and returns the push's title/body (`describeDueFR` phrased as of `remind_at`)/url. Scope = the push scan's: not-done, reminder-enabled, not-yet-sent items on lists the user can access (house membership, list share, space share — `ListNotificationRecipients`' three sources, inverted), **plus done recurring items' next occurrence** (`next_due_date`): `occurrenceStart` brings a task back as late as its reminder moment, so waiting for it would leave the phone nothing to schedule ahead. Future only, 60-day horizon, at most 200, sorted. Doesn't depend on `PushEnabled()`. Tests: `reminders_test.go`.
- **Notification preferences** (migrations 26–27, `PATCH /api/v1/me`, `db.UpdateUserNotificationPreferences` — one `COALESCE(?, column)` update, nil = untouched): Paramètres' "Types de notifications" matrix, account-wide (not per device), one `users` column per type rather than a JSON blob, so recipient queries filter in SQL: `reminders_enabled`, `overdue_tasks_summary_enabled`/`_time`, `collaborator_actions_enabled`, `item_additions_enabled`, `list_sharing_enabled`. `db.NotificationKind` names the per-list ones; `db.ListNotificationRecipientsFor(listID, exclude, kind)` is `ListNotificationRecipients`' UNION (`listRecipientsQuery`) filtered by `wantsNotificationExpr` — a `CASE ? WHEN 'task_reminders' THEN reminders_enabled …` whose kind is a **bound parameter**, so the SQL text never varies. Used by `checkItemForDueReminder` (task reminders, still marked sent when nobody wants it, so re-enabling never replays) and `deliverListChange` (`notifyListChange`'s body: `itemAdded` → item additions; `itemChecked`/`itemUnchecked` → collaborator actions — unchecking notifies since migration 27, "a décoché un article"; `doneChange` picks between them in `handleItemsUpdate`/`Patch`). Price alerts have their own Paramètres section, "Alertes de prix" (migration 28): `price_alerts_enabled` (master, also gates the target-price push via `NotifyPriceTargets`), `price_drop_alerts_enabled` (`NotifyPriceDrops`, also better deals), `price_increase_alerts_enabled` (`NotifyPriceIncreases`, off by default), plus the display-only `price_change_indicators_enabled` — same `wantsNotificationExpr` mechanism, the price kinds multiplying the master column in. **Sharing**: `notifyInvitation` (after `CreatePendingInvitation` in the House-invite, List-share and Space-share handlers) runs detached — the reply mustn't depend on whether the address has an account, even by timing (AUDIT L-06) — and `deliverInvitation` looks the address up, checks `UserWantsNotification(…, NotifyListSharing)`, and sends "X a partagé la liste « … » avec vous" (`/?list=`), "… l'espace …" or "X vous a invité à rejoindre la maison « … »" (`/`); the invitation still takes effect at the invitee's next `/me`. `handleRemindersUpcoming` returns no reminders when `reminders_enabled` is off. - **Daily overdue-tasks summary** (`internal/handlers/overdue_summary.go`, `internal/db/overdue_summary.go`): `users.overdue_tasks_summary_enabled` (default **off** — a new daily notification) / `_time` (`HH:MM`, default `08:00`, `APP_TIMEZONE`). `RunOverdueSummaryScan` runs on `runDueReminderScanLoop`'s ticker right after `RunDueReminderScan` (so it needs push configured and a positive `NOTIF_DUE_SCAN_INTERVAL_MINUTES`): `ListUsersAwaitingOverdueSummary(today)` (summary on, `overdue_tasks_summary_sent_on != today`), and for each user whose time (via `reminderMoment(today, "", false, 0, time)`) has passed, `ListOverdueTasksForUser(user, today)` — not done, `due_date < today` **however long ago** (the first version only took `due_date = yesterday`, so a task four days late never showed up — migration 27 also reset `sent_on` for that fix), oldest first, any of the three access sources, regardless of the item's own reminder setting — then one push to that user alone (`overdueSummaryPayload(tasks, day)`: French; one task "« … » (liste), échue hier / le ven. 2 oct., n'est toujours pas cochée." via `overdueSinceFR`/`shortDateFR`; several "N tâches en retard ne sont pas cochées : A, B, C et N autres"; `/?list=` when all on one list else `/`; tag `trakka-overdue-summary`) and `MarkOverdueSummarySent(today)` — also when there was nothing to send, so the user is looked up once a day. ## Encrypted WebDAV backups

- **What it is**: `internal/backup` backs the whole database up to an admin-configured WebDAV folder — on demand ("Sauvegarder maintenant") or on a schedule (every 12h / nightly / weekly, wall-clock times in `APP_TIMEZONE`), pruning to a retention count — and restores from those backups, all behind `/api/v1/admin/backups/...` (`internal/handlers/admin_backups.go`, every handler gated by `authorizeAdmin` first). Operator docs: [docs/DEPLOYMENT.md](../docs/DEPLOYMENT.md#encrypted-webdav-backups); endpoint reference: [docs/API.md](../docs/API.md#admin-backups). Import direction: `internal/handlers` → `internal/backup` → `internal/db` (+ `internal/validate`, `internal/models`), the same shape as `internal/settings`; the backup package never touches `database/sql` itself.
- **Snapshot** (`db.SnapshotTo`): `VACUUM INTO` on a second, short-lived `mode=ro` connection rather than the shared `SetMaxOpenConns(1)` one — WAL mode gives that reader a fixed snapshot while writers on the main connection carry on, so a backup never queues ordinary requests behind it. It lands in `<DB_PATH dir>/backups/staging/` (on the data volume, not the container's 16 MB in-memory `/tmp`), is deleted after each run, and the staging dir is wiped at startup (`backup.New`).
- **Encryption** (`crypto.go`, format documented at the top of the file): server-side, before upload; AES-256-GCM in 64 KiB chunks under a per-file HKDF-SHA256 subkey (random 32-byte salt per file), nonce = chunk counter + final-chunk flag, whole 52-byte header as AAD — the age/Tink "STREAM" construction, so modification, reordering, truncation at a chunk boundary and trailing data all fail authentication, and memory stays at one chunk regardless of DB size (the <20 MB RAM target). `EncryptedSize` is exact, so the ciphertext is streamed straight into the `PUT` through an `io.Pipe` with a real `Content-Length` and never written to disk. `crypto/hkdf` (stdlib since Go 1.24) is used directly — unlike `internal/webpush`'s hand-rolled HKDF, which predates the pinned toolchain being new enough. The header carries a key fingerprint so a wrong key fails up front with both fingerprints (`WrongKeyError`) instead of an opaque auth failure. `Decrypt` writes plaintext progressively; only a nil return means the file was intact, which is why restore decrypts into a staging file first.
- **The key** (`key.go`): 32 random bytes in `<DB_PATH dir>/backup.key` (`0600`, written via temp-file + rename), generated on first config save or first export — deliberately **outside** the database so it never travels inside the backups it protects. Printable form `TRAKKA-BK1-XXXXX-…`: base32 of key + 2-byte SHA-256 checksum, and `ParseKey` requires the canonical encoding (the last base32 char carries only 2 data bits; without that check a "typo" there decoded silently). `ParseKey` tolerates the whole `.key` file pasted in (comment lines, case, dashes, whitespace). Export is a `POST` (`/key/export`), not a `GET`, because it records `backup_key_acknowledged` = fingerprint (clearing the `key_not_saved` alert) and no `GET` may change state (CSRF rule below). The WebDAV password is sealed with a separate HKDF subkey (`sealSecret`) before going into `system_settings`, and never returned — `webdav_password_set` only, like the OIDC client secret.
- **Configuration & state**: `system_settings` `backup_*` keys (`internal/backup/service.go` constants) — so a restore brings the backup setup back with the data. Run history is `backup_runs` (migration 20), inserted only once a run has **finished**; the in-progress state is in memory (`Service.busyKind`, one operation at a time, `ErrBusy` → `409`), because an "in progress" row would otherwise be captured inside the very snapshot being uploaded. `Status` is local-only (never contacts WebDAV) so the frontend can poll it and call it at startup for the alert dot.
- **Scheduler**: `runBackupSchedulerLoop` in `cmd/server/main.go` calls `RunScheduledIfDue` every minute (always started — a no-op until enabled). A slot is due once passed, if it is after `backup_schedule_anchor` (set whenever auto-backup is switched on or its timing changes, and after a restore — so an already-passed slot isn't run immediately), with no successful scheduled run since the slot, fewer than 3 attempts, and ≥30 min since the last attempt. `schedule.go` builds slots with `time.Date` in the configured zone, so they stay on the wall clock across DST.
- **Alerts** (`Status.Alerts`, non-blocking by design — dot on the header gear, ⚠️ on the admin console button, messages at the top of the tab; never a popup/banner): `last_backup_failed` (a scheduled run failed and nothing succeeded since), `no_recent_success` (auto-backup on and no success for `max(3 days, period + 2 days)`, counted from the later of last success and the anchor), `key_not_saved`.
- **Restore** (`Service.restore`): decrypt into staging → `db.PrepareRestoreFile` on the staged copy (`integrity_check`, must have a `users` table, `user_version` ≤ latest else `ErrRestoreTooNew`, then `migrateSchema(conn, logger, nil)` — `migrate` was split so the staged copy is migrated *without* a pre-migration backup, and opened with `trusted_schema(OFF)`) → `db.SnapshotBeforeRestore` (plaintext safety copy in `backups/`) → `db.RestoreFrom`: SQLite's online backup API run in reverse (`sqlite3_backup_init` with the live connection as destination), reached through `sql.Conn.Raw` and modernc's unexported-type `NewRestore` method, **over the one shared connection** — every other query just waits in the pool for the copy, nothing ever sees a half-copied file, and no `*sql.DB` is swapped under the handlers/workers sharing it; `journal_mode=WAL` is re-asserted afterward. Nothing before `RestoreFrom` touches the live database. Afterward: the supplied key is adopted as the instance key if it differs (old file kept as `backup.key.pre-restore-<ts>`) so the restored settings' sealed password still opens; the pre-restore `backup_runs` newer than the restored history are re-inserted (`carryOverRuns` — a backup never contains its own run); the handler rebuilds the live OIDC client from the restored settings (`reloadOIDCFromSettings`, mirroring `cmd/server`'s startup logic). Sessions are the backup's, so the admin is usually signed out; the frontend reloads `/`.
- **Restore upload** (`handleAdminBackupsRestore`): `multipart/form-data` read part by part with `MultipartReader` (never `ParseMultipartForm`, which would spill to `/tmp`), fields in any order — hence the encrypted upload is staged to disk (`StageUpload` → an opaque `*StagedUpload`, so handlers never handle filesystem paths; gosec G703 flagged the earlier path-returning version) until the key is known. 1 GiB cap, and `http.ResponseController` extends this one request's read/write deadlines to 15 min (the server-wide ones are 15 s). The restore itself runs on `context.WithoutCancel(r.Context())` + deadline, so a closed tab can't abandon it halfway. Offline disaster recovery with no web UI: `trakka -decrypt-backup <tkb> -backup-key <key or .key file> -decrypt-output <db>` (also installs the key as `backup.key` next to the output if none is there).
- **Error codes**: WebDAV failures are classified (`ErrorCode`: `auth_failed`, `not_found`, `blocked_address`, …) and restore refusals mapped (`writeRestoreError`: `wrong_key`, `corrupt`, `too_new`, …) into a `code` next to `error` (`writeCodedError`); the admin console translates codes (`modals.adminConsole.backups.errors.*`), and `apiRequest` exposes it as `err.code`. The connection test and remote listing report WebDAV-side failures as **`200` with `ok:false`/`error`**, never `502`/`503`/`504`, which `static/sw.js` and `apiRequest` treat as "Trakka itself is unreachable".
- **Verified**: unit tests for the stream format (chunk-boundary sizes, tampering/truncation/trailing data, wrong key), key parsing, scheduling (incl. DST), the dial guard's IP policy; service tests against an in-test WebDAV server (end-to-end backup→restore, disaster recovery onto a fresh instance with key adoption, retention leaving unrelated files alone, scheduler retries/caps and alert lifecycle, config validation); DB tests for snapshot/live restore/older-schema migration/refusals; handler tests for admin gating on every route and multipart restore. Plus a real headless-Firefox (Selenium) run of the whole tab against a live server and `golang.org/x/net/webdav` server — see the "Encrypted WebDAV backups" entry in [status.md](status.md).

## Personal calendar feed

- **What it is**: each user can generate one secret link, `GET /api/v1/calendar/feed.ics?token=…` (`internal/handlers/calendar_feed.go`), that calendar apps subscribe to as an iCalendar feed of every dated task the user can access — the three sources `AccessLevelForList` combines, in `db.ListCalendarFeedItems`: not-done tasks with a `due_date`, plus done recurring tasks at their `next_due_date`. It replaced the Radicale sidecar `compose.yml` used to ship (removed; it never synced with Trakka). User/operator guide: [docs/CALENDAR_EXPORT.md](../docs/CALENDAR_EXPORT.md); endpoint reference: [docs/API.md](../docs/API.md#calendar-feed).
- **Auth**: the feed is the **one `/api/v1/...` route outside `RequireSession`** — registered on the outer mux in `Routes()`, a more specific pattern than `"/api/v1/"` — because a calendar app polling in the background can't log in or follow SSO. The token (`auth.RandomToken(32)`) is the credential: stored only as `auth.HashToken` in `calendar_feed_tokens` (migration 25, one row per user, `ON DELETE CASCADE`), so it's returned once, by `POST /api/v1/calendar/feed-token`; regenerating upserts a new hash (revoking the old link), `DELETE` removes it. `GET`/`POST`/`DELETE /api/v1/calendar/feed-token` stay behind the session gate and `requireSameOriginWrite`. Unknown tokens get `404`, not `401` (Apple Calendar answers a `401` with a password prompt). `UseCalendarFeedToken` bumps `last_used_at` on each fetch — a write on a `GET`, but pure bookkeeping no cross-site request can turn into a state change (it needs the secret token anyway), shown in Paramètres so users can tell whether a subscription works. `Logging` records `r.URL.Path` only, so the token never reaches the logs; the response carries `Cache-Control: no-store`.
- **Encoding**: `internal/ical` is a stdlib-only RFC 5545 writer (content lines folded at 75 octets without splitting UTF-8, TEXT escaping that also drops control characters, DATE/UTC/DURATION formatting); the handler decides what to write. One `VEVENT` per task, not `VTODO`: Google and Apple ignore to-dos in subscriptions and Nextcloud's Tasks app doesn't show subscriptions. All-day (`VALUE=DATE`) without `due_time`; with one, `TZID=<APP_TIMEZONE>` plus a `VTIMEZONE` that `newVTimezone` derives from Go's zone data (finds the year's offset transitions, expresses each as `BYMONTH`+`BYDAY` nth/last weekday, `DTSTART` in 1970) so recurring timed events keep their wall-clock time across DST; zones with other than 0 or 2 transitions a year fall back to UTC `…Z` times. `RRULE` is the stored canonical rule as-is plus `UNTIL` from `recurrence_end_date` (a UTC date-time for timed events, as RFC 5545 requires with a TZID'd `DTSTART`) — **except** `MONTHLY` on days 29–31 and `YEARLY` on Feb 29, where `recurrence.addMonthsClamped` clamps while RFC 5545 skips the month; those show only the next occurrence. **If `internal/recurrence`'s stepping semantics ever change, re-check `calendarFeed.rrule`** against RFC 5545 the same way. Reminders become a `VALARM` whose `TRIGGER` is relative to the event start, computed in wall-clock minutes from the stored offset/time (`reminderMoment`'s inputs), so it holds for every occurrence. UIDs are `trakka-item-<id>@<BASE_URL host or request host>`.
- **Frontend**: `static/js/calendar-feed.js` (section `#calendar-feed-*` in the Paramètres modal, refreshed from `openUserSettingsModal`); `sw.js` lets `/api/v1/calendar/` go straight to the network — never mirrored, never queued (the new link only exists in the live `POST` response). See [frontend-pwa.md](frontend-pwa.md).
- **Verified**: `internal/ical` unit tests (escaping, folding, durations); handler tests through the real router with no cookie (token lifecycle and revocation, access scoping across house/share/stranger lists, all-day vs timed, RRULE/UNTIL, the day-31 exclusion, alarm triggers, VTIMEZONE for Paris/New York/Sydney/Tokyo, UTC fallback without `BASE_URL`); a live-server smoke test whose feed parsed cleanly with the Python `icalendar` library; and a headless-Firefox (Selenium) run of the Paramètres section at 390 px — see the "Calendar feed" entry in [status.md](status.md). **Not verified**: subscribing from the real Nextcloud/Google/Apple/Thunderbird clients.

## Security rules

These are standing constraints for this codebase, not just how the current code happens to be written — preserve them in anything new. (The root [CLAUDE.md](../CLAUDE.md) has the condensed, quick-reference version of this list.)

- **SQL**: every query goes through `database/sql` parameter placeholders (`?`), exclusively inside `internal/db`. Never build a query string by concatenating or `fmt.Sprintf`-ing a user-supplied value into it.
- **URLs**: any user-supplied URL (currently: an item's `url` field) must pass `internal/validate.URL`, which requires an absolute `http://` or `https://` URL with a non-empty host — this blocks `javascript:`, `data:`, and similar schemes from ever being persisted. Apply the same validator to any future field that accepts a URL. The frontend (`static/js/app.js`) re-checks the scheme client-side before ever setting an `<a href>`, as defense in depth — keep that check if you touch the rendering code (see [frontend-pwa.md](frontend-pwa.md)).
- **Response encoding**: JSON responses rely on `encoding/json`'s default `SetEscapeHTML(true)` behavior (escaping `<`, `>`, `&`) — never call `SetEscapeHTML(false)` on the encoder in `internal/handlers/json.go`.
- **Response caching**: `writeJSON` (`internal/handlers/json.go`) sets `Cache-Control: no-store` on every `/api/v1/...` JSON response — never remove this or add a competing `Cache-Control`/`Expires` header elsewhere for an API route. It exists so the browser's own HTTP disk cache (a layer entirely separate from the service worker's Cache Storage API, which `static/sw.js` never uses for `/api/v1/...` at all) can never hand `fetch()` a stale `GET` response instead of a genuine network round trip or, offline, the service worker's IndexedDB-backed fallback — see the "Offline consistency hardening" entry in [status.md](status.md).
- **Frontend DOM**: `static/js/app.js` builds all dynamic content with `textContent`/`createElement`, never `innerHTML` with interpolated data. Keep that pattern for any new UI code (full frontend conventions in [frontend-pwa.md](frontend-pwa.md)).
- **HTTP security headers**: `internal/handlers.SecurityHeaders` sets `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, a `Content-Security-Policy`, and `Referrer-Policy: no-referrer` on every response, including static files. The CSP has two deliberate exceptions: `script-src` trusts `https://cdn.tailwindcss.com` (the Tailwind Play CDN script `static/index.html` and `templates/login.html` both load), and `style-src` allows `'unsafe-inline'` because that script generates utility CSS into a `<style>` tag at runtime rather than an external file — there was no way to use Play CDN without it; and `img-src` trusts any `http:`/`https:` source (not just `'self' data:'`) because an item's scraped product thumbnail (`items.image_url`, see the price & image lookup section above) can point at any storefront's CDN, with no fixed host list to name in advance — the same reasoning that already lets `item.url` link out anywhere, just extended to `<img src>` now that thumbnails render inline instead of only linking out. Everything else stays strict: no `'unsafe-eval'`, no other inline scripts, no other allowlisted hosts. If you add any other inline `<script>`/`<style>`, move it to an external file instead of widening this further. If Play CDN's ~400KB runtime cost ever needs to go away, switch to a precompiled Tailwind build (Tailwind CLI, output to `static/js/` or a new `static/css/`) instead of the CDN script — that would let `style-src` drop `'unsafe-inline'` again. The OIDC login flow is entirely server-mediated redirects (never a page-JS `fetch` to the IdP), so none of this needed loosening for OIDC support.
- **Passwords & sessions**: passwords are hashed with `golang.org/x/crypto/bcrypt` (`internal/auth.HashPassword`/`VerifyPassword`) — never store or log a plaintext password. Session tokens are `crypto/rand`-generated and stored **hashed** (`internal/auth.HashToken`, SHA-256) in the `sessions` table — the raw token exists only in the cookie and in-flight, so a database leak alone can't hand out live sessions. `Authenticate()` runs a dummy bcrypt comparison even on an unknown email/OIDC-only account, so failed-login timing doesn't reveal whether an email is registered. The calendar feed's per-user token follows the same rule (random, stored hashed, see [Personal calendar feed](#personal-calendar-feed)) — it's the only credential besides the session cookie that opens an `/api/v1/...` route, and the only route outside `RequireSession`; don't add another.
- **CSRF**: two independent layers, both in `internal/handlers/csrf.go`. Layer 1 — the session cookie is `SameSite=Lax` (changed from `Strict` — see the "Mobile/PWA login loop fix" entry in [status.md](status.md)), which is the app's primary CSRF defense for `/api/v1/...`: Lax omits the cookie from every cross-site request except a top-level GET navigation, and it's never attached to a cross-site `fetch`/XHR (the only way this SPA issues `POST`/`PUT`/`PATCH`/`DELETE`) or a cross-site form POST. Every `GET` route this app exposes is a pure read (`internal/handlers/app.go` — no route mutates state on `GET`), so the one thing Lax additionally allows over Strict — a cookie attached to a cross-site top-level GET navigation — cannot be turned into a state change. `requireSameOriginWrite` backs this up on every `/api/v1/...` write (and on `/auth/logout`) by rejecting a `POST`/`PUT`/`PATCH`/`DELETE` whose `Origin` (or, when `Origin` is absent/`"null"`, `Sec-Fetch-Site`) says the request came from another site — see the "Fix: `/auth/login`/`/auth/register` rejected with 'cross-origin request rejected'" entry in [status.md](status.md) for the `Origin: "null"`-on-a-legitimate-navigation edge case this had to account for. Layer 2 — `/auth/login` and `/auth/register` are the one place `SameSite=Lax` protects nothing, since neither carries a pre-existing session cookie for Lax to withhold: a cross-site form POST there can't steal a session, but it can still silently sign a victim into an *attacker-chosen* account ("login CSRF"), after which anything the victim subsequently enters lands in a house the attacker controls. `ensureCSRFToken`/`checkCSRFToken` defend against exactly that with a signed-nothing, compare-everything double-submit: `GET /auth/login` mints (or reuses) a token, sets it as an HttpOnly `trakka_csrf` cookie (scoped to `/auth`, 12h `MaxAge`), and renders it into both forms' hidden `csrf_token` field; the `POST` handlers reject the request (`?error=csrf_failed`) unless the submitted field matches the cookie. A scripted login/registration (curl, a test harness, `docs/DOC_TEST_PRICE_ALERTS.md`'s bootstrap) must therefore `GET /auth/login` first and carry both the cookie and the extracted token into its `POST` — see [docs/API.md](../docs/API.md#authentication) for the exact two-step curl recipe. Don't loosen either layer (e.g. `SameSite=None`, or dropping the `csrf_token` requirement) without adding an equivalent defense first, and don't add a state-mutating `GET` handler without revisiting this reasoning.
- **OIDC id_token verification**: hand-rolled in `internal/auth/jwt.go`/`oidc.go` — hard-rejects any `alg` other than `RS256` *before* any key lookup (alg-confusion defense), verifies the RSA signature before ever trusting the claims, and checks `iss`/`aud`/`exp`/`iat` afterward. If you touch this code, preserve that ordering; don't reorder "check claims" before "verify signature".
- **SSRF (server-side request forgery)**: `internal/scraper.FetchPrice` (and `SearchDealabs`, a fixed host but the same guarded client), `internal/webpush.Send` and `internal/backup`'s WebDAV client are the three places this server makes an outbound HTTP request to a URL supplied at runtime (an item's `url` field; a Web Push subscription's `endpoint`, submitted via `POST /api/v1/push/subscribe`; the admin-entered backup folder URL) rather than one hard-coded at deploy time. The WebDAV guard (`internal/backup/dial.go`'s `dialGuard`) is the one with a knob: private/loopback/CGNAT addresses are refused like the other two unless the operator sets `BACKUP_WEBDAV_ALLOW_PRIVATE=true` (a LAN Nextcloud is the common case), and link-local (cloud metadata), multicast and unspecified addresses stay refused regardless; that client also never uses an environment proxy and never follows redirects (which would resend the Basic credentials). It's the same category of risk as a Slack/Discord link-unfurler, and all three are defended the same way: each package's `http.Client` uses its own custom `Transport.DialContext` (`safeDialContext`) that resolves the target host itself and only ever connects to a public IP — rejecting loopback, private/ULA ranges, link-local (including the `169.254.169.254` cloud metadata address), multicast, and unspecified addresses — and dials that checked IP literal directly rather than letting the transport re-resolve the hostname, closing the DNS-rebinding TOCTOU gap a "resolve, check, then dial the hostname" approach would leave open. `internal/webpush` and `internal/backup` each carry their own independent copy of this guard rather than importing `internal/scraper`'s (the packages have no other reason to depend on each other; the reserved-range lists are kept in lockstep by hand) — any future feature that makes the server fetch a user-supplied URL must reuse an existing guard or add an equivalent one, never call `http.Get`/`http.Client.Do` directly against untrusted input.
