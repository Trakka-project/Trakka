# PWA (offline support)

Trakka is installable and works offline on iOS, iPadOS, and Android, via three static files plus a small amount of glue in `static/index.html` and `static/js/app.js`:

| File | Role |
|---|---|
| `static/manifest.json` | App identity/appearance for the browser's install prompt (mainly Android/desktop Chrome) |
| `static/sw.js` | Service worker: caches the app shell, serves it offline, and queues API mutations made while offline |
| `static/js/db.js` | IndexedDB layer shared by the service worker (reads and writes) and the page (`app.js`, read-only — see below) |

## Requirement: HTTPS

Service workers only register in a [secure context](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts) — `https://` or exactly `http://localhost`. **None of this works over plain `http://` from another device** (e.g. `http://192.168.1.20:8080` from a phone on the same network) — `navigator.serviceWorker.register()` will simply be unavailable, silently disabling offline support and installability, with no error surfaced to the user. `compose.yml` exposes Trakka over plain HTTP by design (it expects a TLS-terminating reverse proxy in front for anything beyond local testing — see [docs/DEPLOYMENT.md](DEPLOYMENT.md)). Testing on `localhost` (including via `docker run -p 8080:8080` on the same machine as the browser) works without TLS.

## iOS/iPadOS Safari: what's different

iOS Safari implements service workers and IndexedDB, but **not** the Web App Manifest (for icons/display mode) or the Background Sync API. `static/index.html` therefore carries iOS-specific tags that duplicate what the manifest provides for other platforms:

- `<link rel="apple-touch-icon" href="/icons/apple-touch-icon-180.png">` — iOS never reads `manifest.json`'s `icons` array.
- `<meta name="apple-mobile-web-app-capable" content="yes">` — launches full-screen (no browser chrome) once added to the home screen.
- `<meta name="apple-mobile-web-app-status-bar-style">` and `apple-mobile-web-app-title` — status bar appearance and the name shown under the home-screen icon.

Because iOS has no Background Sync API (`'sync' in self.registration` is simply `false` there), the offline write queue can only be flushed while the page is open. `sw.js` covers this with two triggers instead of relying on `sync`:
1. The page listens for the browser's `online` event (`static/js/app.js`, near the bottom of the file) and posts `{type: 'flush-queue'}` to the active service worker.
2. `sw.js`'s `fetch` handler opportunistically calls `flushQueue()` (cheap no-op if the queue is empty) whenever `navigator.onLine` is true, on every same-origin request — so simply using the app again after reconnecting is enough to drain the queue.

On Android/Chrome, `self.registration.sync.register()` (in `scheduleSync()`) additionally lets the browser flush the queue even if Trakka isn't open at all when connectivity returns.

## Caching the Tailwind CDN script

`static/index.html`'s entire visual design depends on `https://cdn.tailwindcss.com` (the Tailwind Play CDN script) loading successfully — there is no fallback stylesheet. That script is cross-origin, and `sw.js`'s general rule is to let cross-origin requests pass straight through uncached (see the `fetch` handler). Without an exception, opening the installed PWA offline would still load Trakka's own cached app shell, but render it completely unstyled, because the browser's own HTTP cache for a third-party CDN script is not something a PWA can rely on staying warm.

`sw.js` therefore treats `CDN_ASSETS` (currently just the one URL) as a special case: cached with `mode: 'no-cors'` (so caching succeeds even though the CDN doesn't send CORS headers — the resulting "opaque" response can be replayed but never inspected, which is fine since it's only ever handed back to a `<script>` tag) and served cache-first with a background refresh, the same strategy as the rest of the app shell. This precache is deliberately **not** part of the atomic `cache.addAll(APP_SHELL)` call in `install` — it runs as a separate, best-effort step afterward, so a CDN hiccup at install time can't prevent Trakka's own app shell from installing.

If you ever add another cross-origin script/stylesheet dependency, add its URL to `CDN_ASSETS` rather than leaving it to fall through the generic cross-origin bypass — otherwise it will silently break offline styling/behavior exactly like this.

## How offline reads and writes work

For the actual list/item CRUD, `static/js/app.js` needs **no offline-specific code at all** — every `fetch()` it makes is transparently intercepted by `sw.js`'s `fetch` event handler, and a queued/offline response looks enough like a normal one (any 2xx-range status, JSON body) that `apiRequest()` handles it the same way as talking to the real server.

- **Reads** (`GET /api/v1/...`): network-first. A successful response is mirrored into IndexedDB (via `TrakkaDB.putLists`/`putList`/`putItems`/`putCustomCategories`) before being returned. If the network fetch fails, `sw.js` reconstructs an equivalent JSON response directly from that IndexedDB mirror and returns it with an `X-Trakka-Offline: true` header.
- **Writes** (`POST`/`PUT`/`PATCH`/`DELETE` on `/api/v1/...`): also network-first. On failure, the request is recorded in an IndexedDB `queue` store and an optimistic response is returned immediately (HTTP `202`) so the UI updates right away, without the frontend needing to know it was queued rather than actually sent.

The one place `app.js` does talk to IndexedDB directly is the header's sync indicator and the per-list/per-item "unsynced changes" dots described below: `refreshPendingChangeIndicators()` calls `TrakkaDB.getQueue()` purely to read the current queue's contents. It never writes to any `TrakkaDB` store — the service worker remains the sole writer of both the mirror and the queue, which is what keeps this a single-writer system instead of two independent copies that could drift out of sync.

Every GET-driven loader across the frontend (`loadDashboard`/`loadHouses`/`loadMembers` in `app.js`; `selectList`/`refreshCurrentList` in `list_view.js`; `loadPlanningView`/`loadUrgentView`/`loadSpacesView`/`loadCustomCategories` in `planning.js`/`urgent.js`/`spaces.js`) follows the same two-part rule when its `apiRequest()` call fails: first fall back to whatever the IndexedDB mirror last saw (via `cachedDashboardLists()`/`cachedHouses()`/`cachedListDetail()`/`cachedCustomCategories()`, all thin wrappers around `TrakkaDB`'s getters) so the view stays populated instead of going blank; then only raise the blocking error banner (`showError()`) if the failure *wasn't* a plain connectivity problem. `apiRequest()` tags that case by setting `err.isNetworkError = true` when `fetch()` itself throws (no route to the server at all), as opposed to the server actually answering with a non-2xx status — `isNetworkError(err)` (defined in `app.js`) is what every one of those loaders checks before calling `showError()`. The header's network dot + "Hors-ligne" label already communicate "you're offline" on their own; popping a banner on top of an already-repainted cached view during ordinary navigation would be a redundant, intrusive false alarm. A genuine server-side error (a `5xx`, a bug) has no such flag and still surfaces the banner as before.

## Keeping a dashboard card's total in sync with its items

A list's dashboard/Espaces card shows its `total_amount` (the "reste à dépenser" figure — every priced, not-yet-`done` item's `price * quantity`, computed server-side by `internal/db.listSelect`'s `SUM(...) WHERE done = 0`) directly from whatever `TrakkaDB.getList()`/`getListWithItems()` last mirrored, while the list detail view computes the same figure independently and live, straight from `state.currentList.items`, on every render (`updateFinanceSummary`/`lineTotal` in `list_view.js`) — so it's never stale regardless of where its items came from. The server only ever includes `total_amount` on a list-shaped response (`GET /api/v1/lists`, `GET /api/v1/lists/{id}`); an item-shaped response (`POST`/`PUT`/`PATCH`/`DELETE /api/v1/items/{id}`) never carries it. Without anything correcting for that, checking an item off (or editing its price/quantity, or deleting it) would update the item itself in the mirror but leave the parent list's cached `total_amount` untouched until the next full list refetch — silently showing a different number on the dashboard card than the list detail view reports for the very same list.

`sw.js`'s `recomputeListTotalAmount(listId)` closes that gap: it re-sums every item currently mirrored under `listId` (skipping done or unpriced ones, `null` when nothing qualifies — mirroring the SQL exactly) and writes the result back onto the list's IndexedDB row. It's called after every item mutation this file mirrors, both when the request actually reached the server (`mirrorWriteResult`) and when it didn't (`applyOptimisticEdit`, `resolveAgainstPendingCreate`, and the offline item-create path in `queueOfflineWrite`) — so a dashboard card reopened from the IndexedDB mirror always agrees with the list detail view, whether the edit that produced it happened online or offline. `app.js`'s `dashboardOptimisticOverrides` (the live, same-session snapshot `notifyItemsChanged` uses so the dashboard doesn't lag behind an edit still sitting in `toggleDone`'s 5s undo grace period) gets the equivalent client-side treatment: `applyDashboardOverrides` recomputes `total_amount` from the overridden items via its own `remainingAmount()` helper, rather than reusing whatever `total_amount` the list had before the override was applied.

## Per-account mirror isolation

Everything described above assumes the IndexedDB mirror belongs to exactly one authenticated account at a time. On an ordinary single-user browser that's true by construction, but Trakka is designed to be self-hosted for a household, and a household commonly means a shared device (a family tablet, a kitchen kiosk) where two different accounts log in sequentially without ever really "logging out" of the browser in between (the session simply expires, or someone just closes the tab). Without an explicit guard, `sw.js` would happily go on mirroring whichever account's requests it happens to intercept into the *same* unscoped `houses`/`lists`/`items`/`custom_categories` stores — the server's own RBAC always scopes each individual response correctly to whoever's session cookie is attached to that request, but nothing stopped two different accounts' responses from being merged into one mirror over time, and `getHouses()`/`getLists()`/etc. have no way to tell the two apart afterward.

Two independent layers close this:

1. **A page-side check** (`app.js`'s `init()`): `CACHED_USER_STORAGE_KEY` in `localStorage` records which account's id the local mirror was last confirmed to belong to. Every time `GET /api/v1/me` resolves, `init()` compares it against `state.currentUser.id`; on a mismatch it calls `purgeLocalUserData()` (wipes `TrakkaDB`, the service worker's runtime cache, and every per-account `localStorage` key) before painting anything further. This also runs on an explicit logout (the `logoutForm` submit handler), so signing out on a shared device leaves nothing behind for the next person. Its blind spot: it can only ever run once `/api/v1/me` actually resolves, which never happens while genuinely offline — so on its own it can't help a browser that switches accounts and then goes offline before this check gets a chance to run even once.
2. **A service-worker-side check** (`sw.js`'s `enforceMirrorOwnership`), which is what actually closes that blind spot. The mirror's `meta` IndexedDB store (`db.js`, `getActiveUserId`/`setActiveUserId`) records the same "whose data is this" fact the service worker itself trusts. `GET /api/v1/me` is the one response in the whole API that carries the requesting session's own identity, so `handleApiRead()` intercepts it specially: instead of the usual fire-and-forget `mirrorReadResponse()`, it *awaits* `reconcileMirrorOwnershipFromMeResponse()` before the response is ever handed back to the page — on a mismatch this calls `TrakkaDB.clearAll()` (which now also clears the `meta`/`queue` stores) before recording the new owner. Because this is awaited, by the time `apiRequest('/me')` resolves in `app.js`, the mirror is *already* either untouched (same account as before) or already wiped (different account) — nothing downstream (including `hydrateFromCache()`'s own direct IndexedDB reads) can observe a half-purged or still-foreign mirror. Since logging in always requires a real round trip to the server, this means the mirror is reliably re-scoped to whichever account most recently logged in on this browser *before* that account could ever go offline with someone else's data still sitting in it — what point (2) exists to protect against is really "was this browser ever online even once since this login", which login itself guarantees.

`flushQueue()` gets its own variant of the same check (`verifyMirrorOwnership()`, a direct `fetch('/api/v1/me')`) whenever there's anything queued to replay, for a subtler reason: `flushQueue()` is also called opportunistically on *every* same-origin fetch while online — including the very first `GET /api/v1/me` a freshly-logged-in session issues — so without its own check it could race `reconcileMirrorOwnershipFromMeResponse()` above and replay a previous account's still-queued write under the newly-authenticated account's session cookie before the mismatch was caught. If `verifyMirrorOwnership()` does purge (which empties the queue along with everything else), the queue re-read right after it simply comes back empty and there's nothing left to replay.

As defense-in-depth beyond both of these, `custom_categories` — the one mirrored entity that actually carries a `user_id` field (houses/lists have no equivalent to filter on; a house's membership isn't embedded in its own JSON, since the server's RBAC-scoped query is what already limits which houses a response can ever contain) — is also filtered by `state.currentUser.id` at read time wherever it's consulted (`spaces.js`'s `cachedCustomCategories()`), whenever the current account is already known.

Finally, `flushQueue()`'s existing "any non-`401` status resolves the queue entry" rule (see "Session expiry vs. the offline queue" below) already covers the case of an orphaned queue entry surviving all of the above: if a previous account's queued write somehow still reaches the server (e.g. it slipped through the ownership race, or the account genuinely lost access to that house between queueing and replay for an unrelated reason), the server's own RBAC rejects it with `403` ("not a member of this house"), and `flushQueue()` dequeues it immediately and moves on to the next entry rather than getting stuck retrying it forever or blocking the rest of the queue.

## Offline sync indicators (header badge + per-list/per-item dots)

Beyond the network dot + "Hors-ligne"/"En ligne" label, three pieces of UI tell the user their own changes are still waiting to reach the server, all driven by the same queue and all defined in `static/js/app.js` unless noted otherwise:

1. **The header's `#pending-badge`** cycles through four states (`data-sync-state` on the element itself): `idle` (hidden — nothing queued, nothing to report), `pending` (☁️⏳, amber, pulsing — at least one write is queued and nothing is being sent right now), `syncing` (🔄, spinning — `sw.js`'s `flushQueue()` is actively replaying the queue), and `synced` (☁️✓, shown for 2.5s then auto-hidden — a flush attempt just emptied the queue). `setSyncIndicatorState()` renders each state; Tailwind's built-in `animate-spin`/`animate-pulse` utilities provide the motion, no custom CSS.
2. **A small "⏳ Non synchronisé" dot** on a specific list's dashboard/Espaces card (`buildListCard`) and on its detail header (`list_view.js`'s `renderItems()`, `#list-sync-indicator`), plus on a specific item's row (`list_view.js`'s `buildUnsyncedItemBadge`, appended in `buildSecondaryRow`) — shown whenever that list (or one of its items) still has a write sitting in the offline queue, and cleared automatically the next time the queue empties out. Backed by `pendingListIds`/`pendingItemIds`, two `Set`s rebuilt on every queue change by `refreshPendingChangeIndicators()` and consulted via `hasPendingListChanges(id)`/`hasPendingItemChanges(id)`.
3. **Public `trakka:sync-pending`/`trakka:sync-complete` `window` events** (`detail: { count, syncing }` / `detail: {}`), dispatched from `handleSyncStatusMessage()`, so any other code can react to the queue changing without knowing about IndexedDB or the service worker at all.

This only works because every queue entry `sw.js` writes (`queueOfflineWrite`/`queueOfflineReorder`/`resolveAgainstPendingCreate`) is tagged with a `listId` (and, for an item-scoped write, an `itemId`) — resolved *before* `applyOptimisticEdit()` runs, since a queued `DELETE`'s optimistic apply removes the row from the mirror and there would be nothing left to look `list_id` up from afterward (`resolveQueueTargetIds()`). A list-create's own entry is tagged with its own `temp-list-*` id; an item-create's entry is tagged with its (possibly still-temp) parent list id and its own `temp-item-*` id. This is what lets `refreshPendingChangeIndicators()` derive both id sets with a single read of the queue, instead of re-parsing every entry's HTTP path.

`sw.js`'s `broadcastQueueState(syncing, pendingOverride?)` posts a `{ type: 'trakka-sync-status', pending, syncing }` message to every open tab after every point that adds to or removes from the queue, and at the start/end of `flushQueue()` itself — `app.js`'s `handleSyncStatusMessage()` is the single place that turns those messages into the header badge's state transitions, the two public events, and a network-free repaint of whatever's currently on screen (`repaintPendingChangeIndicators()`, which calls `list_view.js`'s `renderItems()` or this file's own `renderDashboardFromCache()` — both pure local re-renders, no network call). One thing worth knowing if you touch `flushQueue()` again: it's also called opportunistically on *every* same-origin fetch while online (see the top-level `fetch` listener), so the broadcast at its end is guarded behind `hadEntries` (was the queue non-empty when this attempt started) — without that guard, a fully-synced, ordinary online session would post (and repaint from) a `trakka-sync-status` message on every single API call.

Separately, `apiRequest()` (`app.js`) checks every response for an `X-Trakka-Queued: true` header (set on every response `queueOfflineWrite`/`resolveAgainstPendingCreate` return) and, when present, awaits `refreshPendingChangeIndicators()` *before* returning — this is what makes the dot for the list/item an action just affected already correct by the time the calling function's own success path re-renders, rather than only catching up a moment later once the service worker's `postMessage` round-trip arrives.

## Web Push notifications

`sw.js` also carries two Web Push listeners, unrelated to the offline sync queue above (a push arrives from the OS's push service, independent of whether the page is even open) — full design (VAPID/`aes128gcm`, the two notification triggers, the settings-modal opt-in) is in CLAUDE.md's "Web Push notifications" Architecture bullet; this is just the service-worker-specific half. `push` parses the already-decrypted JSON payload (`{title, body, url}` — decryption itself happens in the browser/OS push stack before this event ever fires, nothing in this codebase implements the receiving side of RFC 8291) and calls `showNotification` with `silent: true` (a real, visible notification with no sound/vibration — browsers restrict genuinely data-only "silent push"). The exception is a payload carrying a `vibrate` pattern, which the server only adds for a recipient who left "Activer les vibrations des notifications" on (`users.vibrate_on_notification`): that one is shown with `vibrate` and `silent: false`, since the Notifications spec rejects the two together, so the OS may also play its notification sound. `notificationclick` closes the notification and either `postMessage`s an already-open tab `{type: 'trakka-notification-click', url}` (handled by `app.js`'s `handleNotificationClickMessage`, which just calls `selectList` — deliberately not `WindowClient.navigate()`, which has uneven support and which an already-loaded SPA has no real need for) or, with no tab open, calls `clients.openWindow(url)`, landing on a fresh load that reads the same `?list=` query param at boot via `app.js`'s `handleDeepLinkOrRestore` (spliced into `init()` in place of a bare `restoreLastView()` call, taking priority over the "keep last page" restore since a user who tapped a notification clearly wants the list it names).

Subscribing/unsubscribing (`static/js/push.js`) is a page-script concern, not `sw.js`'s — it talks to `PushManager` via `navigator.serviceWorker.ready` and to `POST`/`DELETE /api/v1/push/subscribe` directly, with no offline-queue involvement at all (there is no sensible way to "queue" a permission prompt or a subscription while offline, and both actions need a live round-trip to be meaningful).

## The tricky part: creating things offline

Newly created lists/items don't have a server id yet while offline, so `sw.js` assigns a temporary string id (`temp-list-<uuid>` / `temp-item-<uuid>`) and returns that in the optimistic response. Two situations need special handling as a result, both in `static/sw.js`:

1. **Adding an item to a list that was itself created offline.** The queued item-create entry records `dependsOnListTempId`. When the list's own queued create later succeeds and gets a real id, `remapTempId()` rewrites that item entry's `body.list_id` **in place, in the in-memory queue array `flushQueue()` is iterating** (not just in IndexedDB) — this is what makes the item request, sent later in the same flush pass, carry the real list id instead of the temp one. `remapTempId()` also has to re-parent any locally-mirrored items to the new real list id *before* calling `TrakkaDB.deleteList(tempId)`, because `deleteList` cascades to every item still filed under that `list_id` — get the order wrong and the flush silently deletes the very item it's about to sync (this was caught by testing, not inspection; see the git history for `remapTempId` if you're touching this again).
2. **Editing or deleting something that never reached the server.** A `PATCH`/`PUT`/`DELETE` against a `temp-*` id can't be sent to the API — there's nothing there yet. `resolveAgainstPendingCreate()` instead folds the change into the still-queued create (for edits) or cancels it outright (for deletes). Deleting a pending **list** this way must also cancel any queued item-creates that depended on it (`dependsOnListTempId`), or they'd later be replayed against a list id that will never exist.

What's deliberately **not** handled: chains deeper than one level (there's no scenario in this data model where an item depends on another item), and retrying a request the server rejected outright (a 4xx while flushing is dequeued, not retried — see the comment in `flushQueue()`).

### Session expiry vs. the offline queue

Authentication (see [docs/API.md](API.md#authentication)) is cookie-based, and cookies are ambient/browser-managed rather than something `sw.js` has to snapshot per request — a queued write, replayed later by `flushQueue()`, automatically carries whatever session cookie is present in the browser *at replay time*, not whatever was present when it was queued. Nothing needed to change in `queueOfflineWrite()`/the queue's stored shape for this to work.

What *did* need a fix: `flushQueue()`'s original logic treated every non-2xx replay response as "the server rejected this, drop it" — reasonable for an ordinary `4xx`, but wrong for a `401`. If the session expired while a write sat in the queue (e.g. the user closed their laptop offline for a few weeks), the old behavior would silently and permanently discard that edit the moment connectivity came back, before the user ever got a chance to log back in. `flushQueue()` now special-cases `401`: it stops processing immediately and leaves that entry — and everything queued after it, to preserve ordering — in place, rather than dequeuing it. Once the user logs back in (a normal page load, which re-establishes the session cookie), the next `flushQueue()` trigger (the opportunistic per-fetch check, the `online` event, or a Background Sync retry) picks the queue back up automatically.

`sw.js`'s `fetch` handler also passes `/auth/...` requests straight through, unintercepted (checked before the shell/API branching) — a login/register/logout navigation is neither cache-first-served like a shell asset nor offline-queued like an API write. A queued login could never meaningfully "come back true" later the way a queued list/item edit can, and the server-rendered login page's error/mode state can't be meaningfully cached either.

### Houses are read-mirrored but not offline-writable

Houses (`/api/v1/houses`) get the same read-through mirror as lists/items — `TrakkaDB.putHouses`/`putHouse`/`getHouses`, a `houses` IndexedDB store — so the "Maison" selector and the dashboard (now scoped by `?house_id=`) still show something while offline. But creating, renaming, or deleting a house while offline is deliberately **not** queued: `queueOfflineWrite()` returns a `503` for any `/api/v1/houses` request that reaches it. The reason is the one-level-only limit described above — a list can now depend on a house the same way an item depends on a list, and since houses can only ever be created online, `list.house_id` in a queued list-create is always a real id, never a `temp-house-*` one. Making house creation queueable too would require a second level of temp-id chaining (list → house) on top of the existing one (item → list), which is exactly the kind of chain this design explicitly doesn't support; houses are also created rarely enough that requiring connectivity for it is a reasonable trade rather than a real limitation.

### Custom categories are read-mirrored but not offline-writable

Custom categories (`/api/v1/custom-categories`, see CLAUDE.md's "Custom categories" bullet) get the same read-through mirror treatment as houses: a `custom_categories` IndexedDB store, kept up to date by `mirrorReadResponse()`/`mirrorWriteResult()` in `sw.js` on every successful `GET`/`POST`/`PUT`/`DELETE`, with `offlineReadFallback()` serving `GET /api/v1/custom-categories` straight from that store (status `200`, not a `503`) when the network fetch fails — this is what lets the "Espaces" tab (`static/js/spaces.js`) keep showing a user's spaces and their attached lists while offline instead of going blank. Unlike houses, though, there's no explicit `503` rejection wired up for a category `POST`/`PUT`/`DELETE` made while offline — it simply falls through `queueOfflineWrite()`'s generic bottom branch (the same one an already-synced list/item edit uses), gets queued, and returns whatever `applyOptimisticEdit()` produces, which today doesn't recognize `/api/v1/custom-categories` paths and so returns `{ queued: true }` with no `id`/`name`/`icon` — not a crash, but not a materialized optimistic category either. Creating/editing/deleting a category while offline is therefore not a supported flow yet (only *reading* the last-synced set is); teaching `applyOptimisticEdit()` a category shape (and, for creates, a `temp-category-*` id scheme mirroring `temp-list-*`) would be the way to close that gap if it's ever needed.

## Undo/rollback and the offline queue

`static/js/undo.js` (`window.TrakkaUndo.schedule()`) is a small, generic bottom-snackbar module used by `app.js` (deleting a list) and `list_view.js` (deleting an item, toggling an item's `done` state) to give every easily-mistaken mutation a 5-second "Annuler" grace period. The optimistic DOM/state change (hiding the list card, filtering the item out of `renderItems()` via a `pendingDelete` flag, moving the checkbox to the other section) happens immediately and unconditionally; the real `apiRequest()` call is deferred into the toast's `onCommit` callback, which only runs once the countdown actually reaches zero without the user clicking "Annuler" (`onUndo`, which just reverts the optimistic change with no network call at all).

This needs **no changes to `sw.js`** and no special-casing for offline: because the deferred `apiRequest()` call is the same call that used to happen immediately, `sw.js`'s `fetch` handler can't tell the difference between a mutation sent right away and one sent five seconds later. If the device is offline when the grace period expires, `queueOfflineWrite()` queues it exactly as it would have if the user had never seen an undo option at all — including the `temp-item-*`/`temp-list-*` special-casing in `resolveAgainstPendingCreate()` for something created and then deleted, both while offline, before the create ever reached the server. The one thing `TrakkaUndo` deliberately has no opinion on is *when* the deferred request goes out — only that it eventually does, via the exact same `apiRequest()` path as any other mutation.

## IndexedDB schema versioning

`db.js`'s `DB_VERSION` must be bumped whenever an object store is added or its shape changes (e.g. adding the `houses` store bumped it from `1` to `2`; adding the `custom_categories` store bumped it from `2` to `3`; adding the `meta` store used for per-account mirror ownership — see "Per-account mirror isolation" above — bumped it from `3` to `4`) — `indexedDB.open(DB_NAME, DB_VERSION)` only re-runs `onupgradeneeded` (where stores/indexes are created) when the requested version is higher than what's already on disk in that browser. `onupgradeneeded` is purely additive — every `createObjectStore` call is guarded by `objectStoreNames.contains`, so it only ever adds a new store, never drops or recreates an existing one — which is what lets a `DB_VERSION` bump ship without wiping a user's offline mirror/sync queue.

A browser only lets one `IDBDatabase` connection at a given version be open per origin at a time; if an older tab is still holding a connection open when a newer tab (running post-deploy code with a higher `DB_VERSION`) calls `indexedDB.open`, that newer call's `onupgradeneeded`/`onsuccess` won't fire at all until the older connection closes — instead the newer request's `onblocked` fires (logged as a warning) and just sits there. `db.js`'s `open()` handles this the standard way: every connection it successfully opens gets a `db.onversionchange` handler that proactively closes it and clears the memoized `dbPromise`, so an *older* tab gets out of a *newer* tab's way automatically the moment that newer tab needs to upgrade, instead of requiring the user to manually close every other tab first.

## Cache versioning

`SHELL_CACHE`/`RUNTIME_CACHE` in `sw.js` are version-suffixed (`trakka-shell-v1`, etc.). Bump the suffix whenever `APP_SHELL`'s contents change; `activate()` deletes any cache name it doesn't recognize, which is what evicts the old version — it only ever touches the Cache Storage API (`caches.delete`), never IndexedDB, so evicting stale assets on a deploy can never wipe the offline mirror/sync queue db.js maintains. Every URL listed in `APP_SHELL` must resolve with a 2xx status — `cache.addAll()` fails the entire install atomically if even one doesn't.

`sw.js`'s `install` handler calls `self.skipWaiting()` and its `activate` handler calls `self.clients.claim()`, so a newly-deployed worker takes over every open tab almost immediately rather than sitting `waiting` until every tab running the old one closes. This is what makes `app.js`'s update banner meaningful: `registerServiceWorker()` calls `watchForServiceWorkerUpdate(registration)`, which listens for the installing worker reaching `'installed'` while `navigator.serviceWorker.controller` is already set — the standard signal that this is a genuine update replacing a worker that's already controlling the page, not the very first install on a fresh visit — and shows `#update-banner` ("Une nouvelle version est disponible." / "Mettre à jour"). Deliberately not an automatic reload: the page never forces one on the user's behalf, since that could discard whatever they're mid-typing in a form: the banner just sits there (no auto-dismiss, no timeout) until the user clicks its button, which calls `window.location.reload()` — by which point the already-claimed new worker means the reload really does pick up the new assets rather than reloading into the same old ones.

## Testing changes to sw.js / db.js

There's no Node-based test suite committed to the repo (consistent with the rest of the project having no test tooling — see [docs/DEVELOPMENT.md](DEVELOPMENT.md)), but both files are written to be loadable outside a browser: `db.js` only touches `indexedDB` and `self`, so it runs unmodified against a Node IndexedDB polyfill (e.g. `fake-indexeddb`) inside a `vm` context; `sw.js`'s top-level `function` declarations become properties of that same `vm` context, so its queue logic (`queueOfflineWrite`, `flushQueue`, `remapTempId`, `resolveAgainstPendingCreate`) can be called directly with a mocked `fetch`/`caches`/`registration`/`clients`, without needing a real browser. This is how the temp-id remapping bug described above was actually caught — reasoning through the code did not catch it, a scripted scenario did.
